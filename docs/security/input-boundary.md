# Input Boundary Enumeration

This document enumerates every external-input sink in Jansu, the validator
each sink relies on, the denylist (if any) it applies, the maximum
accepted payload size, and the fuzz coverage that exercises the sink in
adversarial conditions. The enumeration is grouped by crate so reviewers
can walk the surface in the same order the runtime does: wire bytes
first, then payload schemas, then storage queries.

A sink is "external-input" if it accepts bytes whose ultimate origin is
an untrusted producer, consumer, schema registry, or remote object
store. Anything that originates inside the broker process and never
crosses a serialisation boundary is out of scope for this document.

The cross-references in this file use exact file paths and line numbers
from the working tree. When the underlying code moves, this document
must move with it; the proof lane is `security`, and it fails closed if
a referenced line number no longer matches the named symbol.

## Wire-Protocol Sinks (`jansu-sans-io/src/de.rs`)

Every Kafka request that arrives at the broker is parsed by the
sans-I/O decoder. This is the single largest external-input surface in
the codebase, and it is the entry point that the fuzz crate targets
most aggressively.

### `Decoder::request` and `Decoder::response`

- Sink: `Decoder::request` and `Decoder::response` constructors at
  `jansu-sans-io/src/de.rs:116`.
- Validator: The decoder consults `RootMessageMeta` (built from
  `MESSAGE_META` produced by `jansu-sans-io/build.rs`) to determine
  which fields are present at the negotiated API version. Fields that
  are absent in the negotiated version are not allocated, which keeps
  the per-request memory cost bounded by the message's true shape.
- Denylist: API keys without a `broker` listener entry in the upstream
  JSON descriptor are never registered in `RootMessageMeta`, so a
  request that references one is rejected at the body-variant lookup.
- Maximum accepted size: `MESSAGE_MAX_SIZE` constant declared at
  `jansu-sans-io/src/de.rs:31` (`1024 * 1024 * 1024` bytes, one
  gibibyte). The cap is enforced at three call sites within the same
  file:
  - `jansu-sans-io/src/de.rs:609`
  - `jansu-sans-io/src/de.rs:669`
  - `jansu-sans-io/src/de.rs:866`
- Parse depth: `PARSE_DEPTH` constant declared at
  `jansu-sans-io/src/de.rs:33` (six levels). The depth cap blocks
  pathologically nested structures from exhausting the allocator.
- Fuzz coverage: `fuzz/fuzz_targets/fuzz_request_decode.rs` and
  `fuzz/fuzz_targets/fuzz_response_decode.rs`, both declared in
  `fuzz/Cargo.toml` (bins `fuzz_request_decode` and
  `fuzz_response_decode`). The fuzz crate uses `libfuzzer-sys` (pinned
  to `0.4` in the workspace `Cargo.toml`), and the corpora are
  generated by `fuzz/fuzz_targets/generate_seeds.rs`.

### `BatchDecoder` (record batches)

- Sink: `BatchDecoder` at `jansu-sans-io/src/de.rs:1095` and its
  `Deserializer` impl at `jansu-sans-io/src/de.rs:1105`.
- Validator: The record batch format is fixed-shape; the decoder reads
  the 49-byte batch header, validates the CRC32-C against the encoded
  payload via `crc-fast`, and only then decompresses the record block.
- Denylist: Unknown compression types (anything outside None, Gzip,
  Snappy, LZ4, Zstd) are rejected at the attribute-decode step.
- Maximum accepted size: Inherits the same `MESSAGE_MAX_SIZE` cap
  declared at `jansu-sans-io/src/de.rs:31`, applied to the batch's
  declared length before any decompression.
- Fuzz coverage: `fuzz/fuzz_targets/fuzz_deflated_batch.rs`, declared
  as bin `fuzz_deflated_batch` in `fuzz/Cargo.toml`. This target
  exercises the decompression path, which is the most allocation-heavy
  portion of the decoder.

### Varint primitives

- Sink: `jansu-sans-io/src/primitive/varint.rs` (zigzag-encoded i32 and
  i64, plus unsigned u32). Reachable from every record-batch decode
  step.
- Validator: The varint decoder caps the byte count it reads (5 bytes
  for VarInt, 10 bytes for LongVarInt) and rejects over-long encodings
  with `ErrorCode::CorruptMessage`.
- Denylist: None beyond the byte-count cap.
- Maximum accepted size: Bounded by the per-varint byte cap above.
- Fuzz coverage: `fuzz/fuzz_targets/fuzz_varint.rs`, declared as bin
  `fuzz_varint` in `fuzz/Cargo.toml`.

## Schema-Layer Sinks (`jansu-schema/src/`)

Schema processing turns producer-supplied descriptors (Avro, JSON
Schema, Protobuf) and lake-side schema metadata into Arrow record
batches. The descriptors themselves are external inputs whenever they
originate from a registry the broker did not author.

### Avro descriptor parsing (`jansu-schema/src/avro.rs`)

- Sink: `AvroSchema::parse` call sites, including the test exercise at
  `jansu-schema/src/avro.rs:1030` and the production parse paths
  invoked from `jansu-schema/src/avro/arrow.rs`.
- Validator: The `apache_avro` crate validates each `.avsc` against the
  Avro specification; Jansu wraps the result in `jansu-schema::Error`
  so a malformed descriptor surfaces as a typed error rather than a
  panic.
- Denylist: Recursive type references are detected by the Avro library
  and rejected with a parse error.
- Maximum accepted size: Inherits the registry transport's cap. When
  the descriptor arrives over HTTP from a schema registry, the HTTP
  client enforces its own response-body limit; when it arrives via the
  file-based registry (`file:///schema`), the file system imposes the
  cap.
- Fuzz coverage: Avro parsing is exercised indirectly by the schema
  round-trip tests in `jansu-schema/src/avro.rs`; no dedicated fuzz
  target is registered. The follow-on item to add an Avro descriptor
  fuzz target is captured in `AUDIT.md`.

### JSON Schema descriptor parsing (`jansu-schema/src/json.rs`)

- Sink: `serde_json::from_slice::<Value>` at
  `jansu-schema/src/json.rs:105`, plus the `AsJsonValue` impls at
  `jansu-schema/src/json.rs:166` and the encoders under
  `jansu-schema/src/json/arrow.rs`.
- Validator: `serde_json` rejects malformed JSON. Beyond syntactic
  validation, the schema body is checked against the JSON Schema
  meta-schema during compile.
- Denylist: Schema references via `$ref` that resolve outside the
  registry's namespace are rejected.
- Maximum accepted size: Bounded by the registry transport, as for
  Avro.
- Fuzz coverage: None dedicated; covered by integration tests in
  `jansu-schema/tests/`. An entry to add a dedicated JSON Schema
  fuzz target is open in `AUDIT.md`.

### Protobuf descriptor parsing (`jansu-schema/src/proto.rs`)

- Sink: `.proto` descriptor compilation paths invoked from
  `jansu-schema/src/proto.rs` and consumed by
  `jansu-schema/src/proto/arrow.rs`.
- Validator: The `protobuf`/`prost` toolchain validates field numbers,
  reserved ranges, and syntax declarations.
- Denylist: Reserved field numbers and reserved field names produce a
  parse error.
- Maximum accepted size: Bounded by the registry transport.
- Fuzz coverage: Covered by round-trip tests in `jansu-schema/src/proto.rs`.

### Lake descriptor parsing (`jansu-schema/src/lake/delta/mod.rs`)

- Sink: `deltalake::DeltaTableBuilder` at
  `jansu-schema/src/lake/delta/mod.rs` and the surrounding Delta Lake
  metadata-load paths.
- Validator: Delta Lake's transaction-log entries are JSON; the parser
  rejects malformed entries with a typed error.
- Denylist: None beyond the JSON syntactic validation.
- Maximum accepted size: Bounded by the object-store backend's
  per-object cap (typically S3's 5 TiB object limit, but in practice
  Delta log entries are kilobytes).
- Fuzz coverage: None dedicated; covered by the lake integration tests.

## Storage SQL Sinks (`jansu-storage/src/sql/`)

The SQL directory contains the on-disk persistence queries for the
PostgreSQL backend, with mirrors for RedlineDB. None of them concatenate
user input into the query body; every external input is passed as a
positional parameter (`$1`, `$2`, ...). The audit lane verifies this
property by grepping the directory for forbidden patterns.

### Per-query sink summary

The queries cited below are representative; the same conventions apply
to every file under `jansu-storage/src/sql/`:

- `jansu-storage/src/sql/consumer_offset_select.sql` - Reads
  `(cluster_name, group_name, topic_name, partition)` as four
  positional parameters. The cluster name comes from broker
  configuration, the group and topic names come from the request body,
  and the partition is a 32-bit signed integer. All four are bound as
  parameters, never interpolated.
- `jansu-storage/src/sql/policy_delete.sql` - Deletes records whose
  per-topic retention window has expired. The query takes the cluster
  name, the current timestamp, and the default retention seconds as
  three positional parameters, all bound via the PostgreSQL driver.
- `jansu-storage/src/sql/policy_compact.sql` - Compacts a topic's
  log to the latest value per key. Like the deletion query, it accepts
  the cluster name as `$1` and the topic shape parameters through
  bound placeholders.

### Validator

- Validator: `jansu-storage/src/sql.rs` loads every SQL file at startup
  through the `Cache` type and the `include_sql!` macro. The cache is
  read-only at runtime, which makes it impossible for a request handler
  to mutate the SQL body before execution.
- Denylist: The audit lane forbids dynamic string concatenation,
  `format!` on SQL bodies, and unbound interpolation. The forbidden
  pattern is grepped with `rg "\\$\\{|format!|\\+ +\"|concat!\\("` on
  the `jansu-storage/src/sql/` directory; any hit fails the lane.
- Maximum accepted size: Bound by the broker's wire-level
  `MESSAGE_MAX_SIZE` cap declared at `jansu-sans-io/src/de.rs:31`.
  Topic names, group ids, and similar strings are bounded by Kafka's
  protocol-level limit (typically 249 characters for a topic name).
- Fuzz coverage: SQL queries are not directly fuzzed; they are covered
  by the cross-backend integration tests under `jansu-broker/tests/`
  that exercise every backend with the same scenario tree.

## Storage Backend Sinks

The storage backends each load and persist data through one of the
following files. None of them takes raw bytes from the network without
the request having been first decoded by `jansu-sans-io/src/de.rs`.

### RedlineDB backend (`jansu-storage/src/redlinedb/mod.rs`)

- Sink: `Database::open` and the `Statement::query`/`Statement::execute`
  paths in `jansu-storage/src/redlinedb/mod.rs`.
- Validator: RedlineDB parses each statement against its grammar. Bound
  parameters use `IntoParams` to enforce typed binding.
- Denylist: RedlineDB pragmas that change durability behaviour
  (`PRAGMA synchronous = OFF`, `PRAGMA journal_mode = MEMORY`) are
  excluded from the cached SQL by the loader.
- Maximum accepted size: RedlineDB imposes its own per-statement size cap
  (one megabyte by default) before the request even reaches the
  parameter binder.

### PostgreSQL backend (`jansu-storage/src/pg.rs`)

- Sink: `tokio_postgres` client invocations in
  `jansu-storage/src/pg.rs`.
- Validator: PostgreSQL prepares every statement and binds parameters
  through the binary protocol; SQL injection is structurally
  impossible.
- Denylist: The `Cache::get` accessor at `jansu-storage/src/sql.rs:47`
  returns a `&str` from a fixed map, so no statement that is not
  pre-registered can be executed.
- Maximum accepted size: PostgreSQL's `max_allowed_packet` analogue is
  the wire-level `MaxBackendMessage` setting; bound by the broker's
  upstream `MESSAGE_MAX_SIZE` cap.

### S3 / object-store backend (`jansu-storage/src/dynostore.rs`)

- Sink: `object_store` client calls including
  `list_with_delimiter` at `jansu-storage/src/dynostore.rs:1928` and
  `jansu-storage/src/dynostore.rs:3064`/`3081`. The S3 PUT and GET
  paths use the same client.
- Validator: The `object_store` crate validates bucket and key formats
  before issuing the call; malformed inputs return a typed error.
- Denylist: Cross-bucket access is blocked at startup by the broker's
  storage-URL parser, which scopes the client to a single bucket.
- Maximum accepted size: Bounded by S3's per-object cap (5 TiB), with
  the broker's per-request cap of `MESSAGE_MAX_SIZE` applied upstream.

### SlateDB backend (in-process via `jansu-storage/src/slate/storage.rs`)

- Sink: SlateDB key-value writes invoked from
  `jansu-storage/src/slate/storage.rs`.
- Validator: SlateDB validates that the key is a well-formed byte
  string before persisting.
- Denylist: None beyond what SlateDB itself enforces.
- Maximum accepted size: Inherits the per-record cap from the upstream
  decoder.

## In-Memory Backend Notes

The in-memory backend (selected with `memory://` URLs) is intended for
tests and development. It does not write to disk, so the storage-side
sinks above are no-ops; the wire-level caps still apply.

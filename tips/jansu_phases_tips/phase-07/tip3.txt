## Current Phase 07 state

Phase 07 is **in-progress**, owns API key `0` / `ProduceRequest`, and its manifest explicitly lists the primary files for this work: `jansu-storage/src/service/produce.rs`, `jansu-service/src/frame.rs`, `jansu-service/src/stream.rs`, `jansu-broker/tests/produce_exactness.rs`, `jansu-storage/tests/produce_exactness.rs`, `jansu-broker/tests/compatibility_contract.rs`, and the compatibility ledger. 

`AUDIT-003` is the blocker: Produce is routed but must remain unadvertised until stable Java/librdkafka differential proof is recorded in the compatibility ledger. 

The Phase 07 spec says the target is Kafka-exact Produce behavior for normal producer configs before idempotence and transactions are claimed. It calls out acks semantics, partition existence, message and request size validation, timestamp/magic/CRC/compression validation, per-partition error exactness, schema failure mapping, quota/throttle fields, and Java/librdkafka proof. 

Produce is already routed through `jansu-broker/src/service/storage.rs`, but `jansu-broker/src/service.rs` currently advertises only `ApiVersions` and `Metadata`, not Produce.  

The ledger row for `ProduceRequest` is currently `semantic_status: "partial"`, with `current_advertised_versions: null`, `approved_advertised_versions: null`, and notes saying Produce remains pre-advertisement because no stable Java/librdkafka differential harness exists. 

Kafka 4.x’s public protocol starts Produce at version 3, and the protocol defines valid `acks` as `0`, `1`, and `-1`; Kafka’s KIP-896 also removed Produce v0-v2 in Kafka 4.0 and says librdkafka needs v3 in `ApiVersions` to avoid older record-version behavior. ([Apache Kafka][1])

## Definition of done for Phase 07

Phase 07 is finished only when all of this is true:

1. `ProduceRequest` is advertised in `ApiVersions` for the proven modern range, **not** for every descriptor version. The right advertised range is **v3..=11**, because v0-v2 are legacy/removed in Kafka 4.x and should not be part of the Kafka 4.2 compatibility claim. The route may continue decoding v0..=11 for internal tests, but advertised compatibility should be v3..=11. ([Apache Kafka][1])

2. `acks=0`, `acks=1`, and `acks=-1` match Kafka-visible behavior. Invalid acks returns `InvalidRequiredAcks` per partition. `acks=0` appends normally but emits no wire response.

3. Produce validation happens **before mutation** wherever possible: topic/partition existence, record-batch magic, CRC, batch length, record count, timestamp consistency, compression support, request size, batch size, and schema preflight.

4. Per-partition failures are independent: one bad partition must not poison a good partition in the same request.

5. Per-partition response fields are version-correct: `base_offset`, `log_append_time_ms`, `log_start_offset`, `record_errors`, `error_message`, and throttle are populated with stable values matching the protocol fields for advertised versions. Kafka’s protocol includes `log_start_offset` starting in Produce response v5 and record errors/error message starting in v8. ([Apache Kafka][1])

6. The optional produce batcher is made offset-exact or disabled for advertised profiles. Right now it can combine multiple queued Produce requests and return the same base offset to every original request, which is not Kafka-exact. 

7. Snappy is truly supported end-to-end. The `Compression` enum and inflator include Snappy, and the workspace already depends on `snap`, but `deflated::into_record_data` currently only supports None/Gzip/Lz4/Zstd, so a Snappy round-trip must be added. ([GitHub][2])  

8. Java and librdkafka normal producer configs pass a stable client matrix and those tests are recorded in the compatibility ledger.

9. `AUDIT-003` is resolved, the Phase 07 log and manifest are updated, and the ledger row is upgraded from partial/unadvertised to compatible/advertised.

### Required behavior in `ProduceService::serve`

```rust
async fn serve(&self, ctx: Context<G>, req: ProduceRequest) -> Result<Self::Response, Self::Error> {
    let ack = match Ack::try_from(req.acks) {
        Ok(ack) => ack,
        Err(_) => return self.invalid_acks_response(&req),
    };

    let limits = ProduceLimits::from_storage(ctx.state()).await?;
    self.validate_request_size(&req, &limits)?;

    let topics = req
        .topic_data
        .unwrap_or_default()
        .into_iter()
        .map(|topic| self.topic(ctx.clone(), req.transactional_id.as_deref(), ack, topic, &limits))
        .collect::<FuturesOrdered<_>>()
        .try_collect::<Vec<_>>()
        .await?;

    Ok(ProduceResponse::default()
        .responses(Some(topics))
        .throttle_time_ms(0)
        .node_endpoints(None))
}
```

### Required behavior per topic/partition

```rust
async fn partition(
    &self,
    ctx: Context<G>,
    transaction_id: Option<&str>,
    topic: &str,
    partition: PartitionProduceData,
    limits: &ProduceLimits,
) -> Result<PartitionProduceResponse> {
    let index = partition.index;
    let topition = Topition::new(topic, index);

    let Some(frame) = partition.records else {
        return Ok(partition_error(index, ErrorCode::InvalidRecord, 0));
    };

    let log_start_offset = ctx
        .state()
        .offset_stage(&topition)
        .await
        .map(|stage| stage.log_start_offset())
        .unwrap_or(0);

    self.validate_partition_exists(ctx.state(), topic, index).await?;
    self.validate_partition_size(&frame, limits)?;
    self.validate_all_batches_before_append(&frame.batches, limits)?;

    let append = ctx
        .state()
        .produce_partition(transaction_id, &topition, frame.batches)
        .await?;

    Ok(PartitionProduceResponse::default()
        .index(index)
        .error_code(ErrorCode::None.into())
        .base_offset(append.base_offset)
        .log_append_time_ms(append.log_append_time_ms)
        .log_start_offset(append.log_start_offset)
        .record_errors(Some(vec![]))
        .error_message(None)
        .current_leader(None))
}
```

The crucial change is `produce_partition(...)`: appending a vector of batches atomically for one partition, not looping one batch at a time in the service. The current implementation appends batches sequentially; if a storage/schema failure happens after the first append, a later batch can fail after offsets moved. That is not Phase 07-safe.

## 3. Add an atomic partition append storage API

Current `Storage::produce(...)` returns only a base offset for a single deflated batch. ([GitHub][3])

Add a backward-compatible default method to the `Storage` trait:

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub struct ProduceAppendResult {
    pub base_offset: i64,
    pub log_start_offset: i64,
    pub log_append_time_ms: i64,
}

#[async_trait]
pub trait Storage {
    // existing method remains
    async fn produce(
        &self,
        transaction_id: Option<&str>,
        topition: &Topition,
        batch: deflated::Batch,
    ) -> Result<i64>;

    async fn validate_produce(
        &self,
        _transaction_id: Option<&str>,
        _topition: &Topition,
        _batches: &[deflated::Batch],
    ) -> Result<()> {
        Ok(())
    }

    async fn produce_partition(
        &self,
        transaction_id: Option<&str>,
        topition: &Topition,
        batches: Vec<deflated::Batch>,
    ) -> Result<ProduceAppendResult> {
        self.validate_produce(transaction_id, topition, &batches).await?;

        let log_start_offset = self
            .offset_stage(topition)
            .await
            .map(|stage| stage.log_start_offset())
            .unwrap_or(0);

        let mut first_offset = None;

        for batch in batches {
            let offset = self.produce(transaction_id, topition, batch).await?;
            first_offset.get_or_insert(offset);
        }

        Ok(ProduceAppendResult {
            base_offset: first_offset.unwrap_or(-1),
            log_start_offset,
            log_append_time_ms: -1,
        })
    }
}
```

Then override `produce_partition` in storage engines that can do transactional/multi-batch atomic mutation:

* Postgres: use a DB transaction around schema validation, producer-state validation, leader-epoch/log-row insert, and offset-stage update.
* RedlineDB/redlinedb/redlinedb: use a SQL transaction.
* SlateDB/dynostore: if there is no native transaction, prevalidate all schema and all batch semantics before mutation; document limited parity if crash-atomic multi-key commit cannot be guaranteed.
* Null/memory: return unsupported or development-only behavior according to current capability certification.

This retains existing callers while giving Phase 07 a storage hook that can be truly atomic where the backend supports it.

## 7. Fix produce batcher exactness: `jansu-storage/src/batch.rs`

This is the most important hidden Phase 07 correctness bug.

Current batcher behavior:

* Queues multiple produce requests.
* Combines them into one batch.
* Calls storage once.
* Stores the same returned base offset for every waiting ticket. 

That is wrong. If request A has two records and request B has one record, and the combined append starts at offset 10, A’s response base offset is 10 and B’s response base offset must be 12.

Change `BatchResponse` to carry a result:

```rust
#[derive(Clone, Debug)]
enum BatchResponse {
    Waker(Waker),
    Ready(Result<i64, Error>),
}
```

Change ticket polling:

```rust
match responses.remove(&self.id) {
    Some(BatchResponse::Ready(response)) => Poll::Ready(response),
    Some(BatchResponse::Waker(_)) | None => {
        _ = responses.insert(self.id, BatchResponse::Waker(cx.waker().clone()));
        Poll::Pending
    }
}
```

Track per-owner deltas before combining:

```rust
#[derive(Clone, Debug)]
struct OwnerOffset {
    id: Uuid,
    first_delta: i64,
}

fn owner_offsets(queued: &[BatchRequest]) -> Result<Vec<OwnerOffset>> {
    let mut next_delta = 0_i64;
    let mut owners = Vec::with_capacity(queued.len());

    for request in queued {
        owners.push(OwnerOffset {
            id: request.id,
            first_delta: next_delta,
        });

        let records = i64::from(request.batch.last_offset_delta) + 1;
        next_delta = next_delta.checked_add(records).ok_or(Error::Overflow)?;
    }

    Ok(owners)
}
```

Return correct offsets per ticket:

```rust
let owners = owner_offsets(&queued)?;
let append_result = combine(queued.into_iter().map(|q| q.batch).collect())
    .and_then(|combined| {
        combined
            .map(|batch| async move {
                self.storage.produce(transaction_id, topition, batch).await
            })
            .transpose()
    })
    .await;

self.responses.lock().map(|mut responses| {
    for owner in owners {
        let response = append_result
            .clone()
            .map(|base| base + owner.first_delta);

        if let Some(BatchResponse::Waker(waker)) =
            responses.insert(owner.id, BatchResponse::Ready(response))
        {
            waker.wake();
        }
    }
})?;
```

Also fix grouping. The current key uses only `Topition` and `producer_id`. 

Use:

```rust
#[derive(Clone, Debug, Default, Eq, Hash, Ord, PartialEq, PartialOrd)]
struct ProduceBatchKey {
    topition: Topition,
    transaction_id: Option<String>,
    producer_id: i64,
    producer_epoch: i16,
    attributes: i16,
}
```

This prevents mixing transactional/non-transactional batches, different producer epochs, or different compression/control attributes in one combined append.

If this cannot be made robust quickly, set `maximum_delay: None` for every compatibility profile and mark batching as an optimization gated behind a non-compat profile until fixed.

## Phase 08 completion definition

Phase 08 should be considered finished only when all of these are true:

1. **ListOffsets v9 wire path is fixed** for mixed success/error partitions and produced leader epochs.
2. **ListOffsets semantics are Kafka-equivalent** for earliest, latest, timestamp lookup, max timestamp, log-start movement, isolation level, mixed partition errors, and current-leader-epoch fencing.
3. **Fetch semantics are exact enough for the advertised version range**: `max_wait_ms`, `min_bytes`, `max_bytes`, `partition_max_bytes`, empty fetch, cancellation, offset-out-of-range, high watermark, LSO, log start offset, leader epoch fencing, and topic IDs or a lower advertised version cap.
4. **OffsetForLeaderEpoch / API 23 uses real leader-epoch history**, including current, stale, future, unknown, truncation, and recovery behavior.
5. **API advertisement is truthful**: advertise ListOffsets/Fetch/API23 only at versions backed by tests and differential proof.
6. **Phase 04 differential proof is added for this read path**, even if Phase 04 remains broadly reopened under AUDIT-012.

The Phase 08 doc says the goal is exact Fetch, ListOffsets, and OffsetForLeaderEpoch behavior, including timestamp lookups, log start offsets, high watermark, LSO, leader epoch history, and fencing; it also says API 23 must stay unadvertised until semantics exist. ([GitHub][3]) AUDIT-004 currently lists the remaining blockers as the broker ListOffsets mixed-partition wire failure, differential/client proof, API 23 advertisement proof, and truncation/recovery/read-committed integration. ([GitHub][4])

## The main defects to fix

### 1. ListOffsets currently drops request shape and epoch-validation data

`ListOffsetsService` flattens request partitions into `Vec<(Topition, ListOffset)>`, using only topic name, partition index, and timestamp. It drops `current_leader_epoch`, original topic grouping, duplicate topic-group shape, and request order. It then rebuilds response topics through a `BTreeSet`, which sorts and deduplicates topic names. ([GitHub][5]) It also swallows leader-epoch-history errors with `unwrap_or_default`, which can silently turn missing or broken history into `leader_epoch = -1`. ([GitHub][5])

**Required fix:** preserve request order and grouping, validate each partition’s current leader epoch before calling storage, never swallow history errors for existing partitions, and build responses slot-by-slot.

### 2. Fetch long polling and byte accounting are wrong

`FetchService` loops while `elapsed <= max_wait && bytes <= min_bytes`, clears responses each iteration, and accumulates `bytes += responses.byte_size()` across attempts. That can count the same fetched data multiple times instead of evaluating the current response. ([GitHub][6]) The service also accepts request-level `max_bytes`, but the current path does not enforce each partition’s `partition_max_bytes`; Apache Kafka’s protocol defines both request `max_bytes` and per-partition `partition_max_bytes`. ([GitHub][6])

**Required fix:** compute bytes from the current response only, return when current visible bytes satisfy `min_bytes` or `max_wait_ms` expires, respect cancellation, and pass `min(global_remaining, partition_max_bytes)` into storage fetches.

### 3. OffsetForLeaderEpoch response epoch is subtly wrong for older epochs

The current API 23 service finds the first record with `record.epoch > requested_epoch` and returns `leader_epoch = next_epoch.epoch` with `end_offset = next_epoch.start_offset`. ([GitHub][7]) KIP-279 says the leader should respond with the **largest epoch less than or equal to the requested epoch** and the end offset of that epoch. ([Apache Cwiki][8])

So, with history `[0@0, 1@5]` and request epoch `0`, the end offset should be `5`, but the response leader epoch should be `0`, not `1`.

### 4. Storage still allows fake empty leader history

The `Storage` trait has a default `leader_epoch_history` implementation returning `Ok(vec![])`. ([GitHub][9]) That is directly against Phase 08’s “don’t fake history with constant zero / empty” requirement. ([GitHub][3])

**Required fix:** remove the default, make every storage engine implement real history, and add engine conformance tests.

### 5. The v9 wire failure is probably response-header/flexible-version encoding

Apache Kafka documents ListOffsets v9 as using compact strings/arrays and response header version 1. ([Apache Kafka][10]) In Jansu, response serialization is driven by `Frame::response(header, body, api_key, api_version)`, and the bytes layer reuses the request API key/version to encode the response. ([GitHub][11]) If the v9 response header tag buffer is omitted, the client decoder will treat the first body byte as the header tag buffer, shift the body by one byte, and then produce overflow/UnexpectedEof-style failures. That exactly matches the mixed-partition v9 failure shape.

**Required fix:** add a direct sans-io v9 response round-trip test first. If it fails, fix response header version 1/tag-buffer encoding. If it passes, fix the full stack layer that chooses or propagates response API version/header version.

```rust
#[derive(Clone, Debug)]
struct PendingListOffset {
    topition: Topition,
    partition_index: i32,
    request: ListOffset,
    current_epoch: i32,
}

#[derive(Clone, Debug)]
enum PlannedListOffset {
    Ready(ListOffsetsPartitionResponse),
    Pending(usize),
}

fn list_offsets_error(
    partition_index: i32,
    error_code: ErrorCode,
    leader_epoch: i32,
) -> ListOffsetsPartitionResponse {
    ListOffsetsPartitionResponse::default()
        .partition_index(partition_index)
        .error_code(i16::from(error_code))
        .old_style_offsets(None)
        .timestamp(Some(-1))
        .offset(Some(-1))
        .leader_epoch(Some(leader_epoch))
}

fn list_offsets_success(
    partition_index: i32,
    offset: &ListOffsetResponse,
    leader_epoch: i32,
) -> Result<ListOffsetsPartitionResponse> {
    Ok(ListOffsetsPartitionResponse::default()
        .partition_index(partition_index)
        .error_code(i16::from(offset.error_code()))
        .old_style_offsets(None)
        .timestamp(offset.timestamp()?.or(Some(-1)))
        .offset(offset.offset().or(Some(-1)))
        .leader_epoch(Some(if offset.error_code() == ErrorCode::None {
            leader_epoch
        } else {
            -1
        })))
}

async fn validate_current_leader_epoch<G>(
    ctx: &Context<G>,
    topition: &Topition,
    partition_index: i32,
    requested: Option<i32>,
) -> Result<Result<i32, ListOffsetsPartitionResponse>>
where
    G: Storage,
{
    let history = match leader_epoch_history(ctx, topition).await {
        Ok(history) => history,
        Err(Error::Api(ErrorCode::UnknownTopicOrPartition)) => {
            return Ok(Err(list_offsets_error(
                partition_index,
                ErrorCode::UnknownTopicOrPartition,
                -1,
            )));
        }
        Err(err) => return Err(err),
    };

    let current = current_leader_epoch(&history)
        .map(|record| record.epoch)
        .unwrap_or(-1);

    if let Some(requested) = requested {
        if requested != -1 {
            if current == -1 {
                return Ok(Err(list_offsets_error(
                    partition_index,
                    ErrorCode::UnknownLeaderEpoch,
                    -1,
                )));
            }

            if requested < current {
                return Ok(Err(list_offsets_error(
                    partition_index,
                    ErrorCode::FencedLeaderEpoch,
                    current,
                )));
            }

            if requested > current {
                return Ok(Err(list_offsets_error(
                    partition_index,
                    ErrorCode::UnknownLeaderEpoch,
                    current,
                )));
            }
        }
    }

    Ok(Ok(current))
}
```

```rust
#[instrument(skip(ctx, req))]
async fn serve(
    &self,
    ctx: Context<G>,
    req: ListOffsetsRequest,
) -> Result<Self::Response, Self::Error> {
    let throttle_time_ms = Some(0);
    let isolation_level = req
        .isolation_level
        .map_or(Ok(IsolationLevel::ReadUncommitted), IsolationLevel::try_from)?;

    let Some(request_topics) = req.topics else {
        return Ok(ListOffsetsResponse::default()
            .throttle_time_ms(throttle_time_ms)
            .topics(None));
    };

    let mut pending = Vec::<PendingListOffset>::new();
    let mut planned_topics = Vec::<(String, Vec<PlannedListOffset>)>::new();

    for topic in request_topics {
        let mut planned_partitions = Vec::new();

        for partition in topic.partitions.unwrap_or_default() {
            let topition = Topition::new(topic.name.clone(), partition.partition_index);
            let request = ListOffset::try_from(partition.timestamp)?;

            match validate_current_leader_epoch(
                &ctx,
                &topition,
                partition.partition_index,
                partition.current_leader_epoch,
            )
            .await?
            {
                Err(response) => planned_partitions.push(PlannedListOffset::Ready(response)),
                Ok(current_epoch) => {
                    let slot = pending.len();
                    pending.push(PendingListOffset {
                        topition,
                        partition_index: partition.partition_index,
                        request,
                        current_epoch,
                    });
                    planned_partitions.push(PlannedListOffset::Pending(slot));
                }
            }
        }

        planned_topics.push((topic.name, planned_partitions));
    }

    let lookup_request: Vec<_> = pending
        .iter()
        .map(|p| (p.topition.clone(), p.request))
        .collect();

    let lookup_response = if lookup_request.is_empty() {
        Vec::new()
    } else {
        ctx.state()
            .list_offsets(isolation_level, &lookup_request)
            .await
            .inspect_err(|err| error!(?err, ?lookup_request))?
    };

    let mut completed = Vec::<ListOffsetsPartitionResponse>::with_capacity(pending.len());

    for (index, pending_partition) in pending.iter().enumerate() {
        let response = lookup_response
            .get(index)
            .filter(|(tp, _)| tp == &pending_partition.topition)
            .map(|(_, offset)| {
                list_offsets_success(
                    pending_partition.partition_index,
                    offset,
                    pending_partition.current_epoch,
                )
            })
            .unwrap_or_else(|| {
                Ok(list_offsets_error(
                    pending_partition.partition_index,
                    ErrorCode::UnknownTopicOrPartition,
                    -1,
                ))
            })?;

        completed.push(response);
    }

    let response_topics = planned_topics
        .into_iter()
        .map(|(name, partitions)| {
            let partitions = partitions
                .into_iter()
                .map(|planned| match planned {
                    PlannedListOffset::Ready(response) => response,
                    PlannedListOffset::Pending(slot) => completed[slot].clone(),
                })
                .collect::<Vec<_>>();

            ListOffsetsTopicResponse::default()
                .name(name)
                .partitions(Some(partitions))
        })
        .collect::<Vec<_>>();

    Ok(ListOffsetsResponse::default()
        .throttle_time_ms(throttle_time_ms)
        .topics(Some(response_topics)))
}
```

```rust
pub fn validate_leader_epoch_history(history: &[LeaderEpochRecord]) -> Result<()> {
    if history.is_empty() {
        return Err(Error::Message("empty leader epoch history".into()));
    }

    for window in history.windows(2) {
        let prev = window[0];
        let next = window[1];
```

## Patch 4 — Correct OffsetForLeaderEpoch semantics

Add a shared helper in `jansu-storage/src/service/leader_epoch.rs`:

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub enum EpochLookup {
    Found {
        leader_epoch: i32,
        end_offset: i64,
    },
    Unknown,
}

pub fn lookup_epoch_end_offset(
    history: &[LeaderEpochRecord],
    requested_epoch: i32,
    high_watermark: i64,
) -> EpochLookup {
    let Some(current) = history.last() else {
        return EpochLookup::Unknown;
    };

    if requested_epoch > current.epoch {
        return EpochLookup::Unknown;
    }

    let Some(matched) = history
        .iter()
        .rev()
        .find(|record| record.epoch <= requested_epoch)
        .copied()
    else {
        return EpochLookup::Unknown;
    };

    let end_offset = history
        .iter()
        .find(|record| record.epoch > matched.epoch)
        .map(|record| record.start_offset)
        .unwrap_or(high_watermark);

    EpochLookup::Found {
        leader_epoch: matched.epoch,
        end_offset,
    }
}
```

## Patch 5 — Fix Fetch long polling, byte limits, and offset boundaries

The Apache protocol says `max_wait_ms` is the maximum wait, `min_bytes` is the minimum bytes to accumulate, `max_bytes` is the maximum fetch size, and `partition_max_bytes` is the maximum per partition. ([Apache Kafka][10]) It also defines current-leader-epoch fencing: a larger epoch returns `UNKNOWN_LEADER_EPOCH`, and a smaller epoch returns `FENCED_LEADER_EPOCH`. ([Apache Kafka][13])

Change long polling to avoid accumulated duplicate byte counts:

```rust
pub(crate) async fn fetch<G>(
    &self,
    ctx: &Context<G>,
    max_wait: Duration,
    min_bytes: u32,
    max_bytes: u32,
    isolation: IsolationLevel,
    topics: &[FetchTopic],
) -> Result<Vec<FetchableTopicResponse>>
where
    G: Storage,
{
    if topics.is_empty() {
        return Ok(vec![]);
    }

    let cancellation = Self::cancellation_token(ctx);
    let start = Instant::now();

    loop {
        let mut remaining_max_bytes = max_bytes;
        let mut responses = Vec::with_capacity(topics.len());

        for (index, fetch) in topics.iter().enumerate() {
            responses.push(
                self.fetch_topic(
                    ctx,
                    max_wait,
                    min_bytes,
                    &mut remaining_max_bytes,
                    isolation,
                    fetch,
                    index == 0,
                )
                .await?,
            );
        }

        let response_bytes = u32::try_from(responses.byte_size())?;
        let elapsed = start.elapsed();

        if min_bytes == 0
            || response_bytes >= min_bytes
            || has_partition_error(&responses)
            || elapsed >= max_wait
        {
            return Ok(responses);
        }

        let remaining = max_wait.saturating_sub(elapsed);
        if remaining.is_zero() {
            return Ok(responses);
        }

        let delay = remaining.min(Duration::from_millis(250));

        if let Some(cancellation) = cancellation.as_ref() {
            tokio::select! {
                _ = sleep(delay) => {}
                _ = cancellation.cancelled() => return Err(Error::Cancelled),
            }
        } else {
            sleep(delay).await;
        }
    }
}

fn has_partition_error(responses: &[FetchableTopicResponse]) -> bool {
    responses
        .iter()
        .flat_map(|topic| topic.partitions.as_deref().unwrap_or_default())
        .any(|partition| partition.error_code != i16::from(ErrorCode::None))
}
```

## Patch 6 — Truthful API advertisement

The broker currently builds an explicit advertised-version map with only `ApiVersions` and `Metadata`, while storage routes include Fetch, ListOffsets, OffsetForLeaderEpoch, Produce, and others. ([GitHub][14]) That means these APIs can be routable but unadvertised, which matches the current “partial/unadvertised” state.

After the above tests pass, change `jansu-broker/src/service.rs` like this:

```rust
use jansu_sans_io::{
    ApiVersionsRequest,
    FetchRequest,
    ListOffsetsRequest,
    MetadataRequest,
    OffsetForLeaderEpochRequest,
};

pub fn advertised_versions() -> BTreeMap<i16, ApiVersionRange> {
    let mut versions = BTreeMap::from([
        (
            ApiVersionsRequest::KEY,
            ApiVersionRange {
                min_version: 0,
                max_version: 4,
            },
        ),
        (
            MetadataRequest::KEY,
            ApiVersionRange {
                min_version: 12,
                max_version: 12,
            },
        ),
    ]);

    // Advertise only after ListOffsets v9 wire + semantic + differential proof passes.
    versions.insert(
        ListOffsetsRequest::KEY,
        ApiVersionRange {
            min_version: 1,
            max_version: 9,
        },
    );

    // Advertise API 23 only after historical epoch, truncation, recovery,
    // and broker-wire tests pass. For current Kafka-compatible clients,
    // v2..=v4 is the practical range to prove first.
    versions.insert(
        OffsetForLeaderEpochRequest::KEY,
        ApiVersionRange {
            min_version: 2,
            max_version: 4,
        },
    );

    // Fetch sessions/topic IDs determine this cap.
    // If sessions remain unsupported, keep max below incremental sessions.
    versions.insert(
        FetchRequest::KEY,
        ApiVersionRange {
            min_version: 4,
            max_version: 5,
        },
    );

    versions
}
```

If you implement fetch sessions and topic-ID-only fetch in this phase, raise Fetch to the highest proven version. If not, cap Fetch below the session-dependent range and keep higher versions routable only for internal tests.

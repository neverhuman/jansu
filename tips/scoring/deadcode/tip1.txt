I treated “dead code” broadly: **anything in a live repo that is no longer part of the product, build, release, test signal, runtime contract, or current docs truth, but still consumes attention or risk budget.** MITRE defines dead code narrowly as code that can never execute and recommends removing it before deployment; OWASP goes broader and explicitly recommends removing unused dependencies, unnecessary features, components, files, and documentation as part of preventing vulnerable/outdated components. ([CWE][1])

I sampled GitHub docs/discussions, StackExchange/StackOverflow, Reddit-indexed discussions, X/Twitter-indexed snippets, LinkedIn posts, vendor/tool docs, and academic papers. I could not directly access Quora pages from this environment because Quora was blocked by robots.txt, so I did not rely on Quora as a source.

## The hard rule

In a professional repo, **the source tree is not a museum**. Git history, tags, branches, releases, package registries, artifact stores, and archived repositories exist so the active repo can stay active. Git’s own documentation covers recovering lost commits, and GitHub has a first-class repository archive workflow; GitHub also recommends closing issues/PRs and updating the README/description before archiving a repository. ([Git][2])

A defensible exception must have: **owner, purpose, expiry, retrieval path, exclusion from builds/tests/packages, no secrets, no vulnerable dependencies, and no ambiguity for a new maintainer.** Anything else belongs on the inexcusable list.

## 30. Cultural/process behaviors that create dead-code swamps

These are the root behaviors. They are more inexcusable than any one file.

Inexcusable examples:

* “Don’t delete it, we might need it later.”
* “Keep it for reference.”
* “Just comment it out.”
* “Move it to archive.”
* “Rename it to `.old`.”
* “Disable the test for now.”
* “We’ll clean it after launch.”
* “The cleanup ticket is in the backlog.”
* “Everyone knows not to touch that folder.”
* “Ask Alice; she knows why it exists.”
* “It’s legacy, leave it.”
* “It’s safer not to remove it.”
* “It doesn’t hurt anything.”
* “Storage is cheap.”
* “The compiler/tree-shaker removes it.”
* “The bundle excludes it, so it’s fine.”
* “It’s not deployed, so it’s fine.”
* “It’s internal, so it’s fine.”
* “It’s only docs, so it’s fine.”
* “It’s only tests, so it’s fine.”
* “It’s only dev dependency, so it’s fine.”
* “It’s behind a flag, so it’s fine.”
* “It’s in an archived folder, so it’s fine.”
* “It’s useful for onboarding,” when it is not current truth
* “We need a big cleanup sprint someday,” instead of deleting in normal PRs
* accepting PRs that add new code without deleting replaced code
* accepting PRs that add flags without cleanup criteria
* accepting PRs that add dependencies without usage proof
* accepting PRs that disable tests without issue/expiry
* accepting PRs that suppress warnings without owner/expiry
* accepting PRs that leave TODOs without issue/expiry
* no ownership for dead-code cleanup
* no CI enforcement for unused exports/deps/files
* no dependency inventory
* no code-owner review for deletions
* no telemetry to prove runtime usage
* no deprecation policy
* no archive policy
* no retention policy for docs/specs/plans
* rewarding feature delivery while punishing deletion/refactoring
* treating deletion as risky but addition as safe

# The deletion standard I would enforce

A file, folder, function, dependency, config key, flag, test, doc, or script may stay only if it satisfies at least one of these:

1. It is built, tested, packaged, deployed, or executed.
2. It is part of a documented public compatibility contract.
3. It is an intentionally maintained example/fixture/test asset.
4. It is generated by a documented reproducible process and required in-repo.
5. It has an owner, purpose, expiry date, and cleanup issue.

Everything else should be deleted, moved to a proper archived repository/release/tag, or placed in external documentation/artifact storage with a clear retention policy.

## Scope note

I can’t honestly claim an internet-wide exhaustive scrape. Quora was blocked from direct access, and many X pages exposed little or no readable page text. I treated platform anecdotes as weak signal and weighted official docs, GitHub/StackOverflow discussions, engineering writeups, and current vendor/security docs more heavily. The result below is an **exhaustive audit checklist** of “inexcusable” dead-code behavior I’d expect to find in sloppy repos.

The core principle: **old code is not automatically bad; ambiguous old code is bad.** A clean repo can have legacy code, versioned public APIs, old DB migrations, or generated code. A sloppy repo leaves people unable to tell whether something is active, retired, experimental, generated, sensitive, or owned.

# The exhaustive dead-code behavior checklist

## 1. “Archive as a folder” behavior

This is the classic sloppy-repo smell: using the active source tree as a junk drawer instead of using version control, tags, branches, documentation, or a real archived repo.

Inexcusable patterns:

1. `/archive`, `/archived`, `/attic`, `/graveyard`, `/old`, `/old2`, `/old_old`, `/legacy`, `/backup`, `/bak`, `/bkp`, `/copy`, `/copy_of_copy`, `/save`, `/temp`, `/tmp`, `/scratch`, `/unused`, `/deprecated`, `/obsolete`, `/disabled`, `/hold`, `/maybe`, `/future`, `/parking_lot`, `/do_not_delete`.
2. “Old implementation kept for reference” inside the active app.
3. Entire previous apps nested under `/old-app`, `/client_old`, `/server_old`.
4. “Final,” “final2,” “final_final,” “new,” “newer,” “latest,” “current2” directories.
5. Archive folders that are still included by glob patterns, test discovery, Docker build context, package publishing, bundlers, or deployment scripts.
6. Archive folders with their own package manifests, lockfiles, Dockerfiles, workflows, or credentials.
7. Archive folders whose README says “do not use” but no ticket, date, owner, or deletion plan.
8. Storing abandoned experiments in `main` because “we may revive it.”
9. Keeping a copy of a third-party library “just in case.”
10. Keeping a zip/tarball backup of the old repo inside the repo.

Real repository archival should make the repo’s status clear. GitHub recommends updating the README and description and closing issues/PRs before archiving; archived repos become read-only. Google’s open source guidance similarly says to update the README to say the repo is no longer maintained and then use GitHub’s archive feature rather than pretending the project is still active. ([GitHub Docs][1])

## 2. Commented-out-code behavior

This is the most socially common dead-code smell.

Inexcusable patterns:

1. Blocks of commented-out code committed to `main`.
2. “Uncomment this when X is ready.”
3. “Leaving this here in case we need it later.”
4. Commented-out imports.
5. Commented-out routes.
6. Commented-out SQL.
7. Commented-out JSX/HTML/CSS components.
8. Commented-out validation rules.
9. Commented-out auth checks.
10. Commented-out old API calls.
11. Commented-out config.
12. Commented-out Docker/Kubernetes YAML sections.
13. Commented-out CI steps.
14. `#if 0` blocks with no owner/date.
15. `if (false) { ... }`.
16. `if (FEATURE_DISABLED_FOREVER)`.
17. “Temporary disable” comments older than one release.
18. Old algorithm kept below the new algorithm.
19. Commented-out code that no longer compiles.
20. Commented-out code that references renamed variables, deleted functions, or old APIs.

The common objection is “version control remembers it.” That is mostly true; the real problem is that commented-out code becomes untested, unlinted, misleading, and mentally expensive. Multiple engineering sources make the same point: unused code clutters developers’ mental models; commented-out code rots because names, APIs, and conventions change while the commented block is not maintained. ([Stack Overflow][2])

## 3. Unreachable and inert source code

This is dead code that still looks like real code.

Inexcusable patterns:

1. Code after `return`, `throw`, `break`, `continue`, `process.exit`, `panic`, or fatal logging.
2. Branches guarded by constants that are always false.
3. Branches guarded by constants that are always true, leaving the other path dead.
4. Old `switch` cases for enum values that cannot exist.
5. Legacy error handling for exceptions no longer thrown.
6. Old retry logic around clients no longer used.
7. Fallbacks for services that no longer exist.
8. No-op functions pretending to do work.
9. Empty classes kept for compatibility without a compatibility contract.
10. Empty catch blocks from removed behavior.
11. Unregistered CLI commands.
12. Unregistered routes.
13. Unsubscribed event handlers.
14. Queue consumers for queues with no producers.
15. Producers for queues with no consumers.
16. Cron handlers no scheduler calls.
17. Webhook handlers not configured anywhere.
18. Feature modules not imported by the application.
19. React/Vue/Svelte/Angular components not routed, imported, or used.
20. Public exports in private apps with no consumers.
21. “Utility” functions not called anywhere.
22. Private methods never called.
23. Classes never instantiated.
24. Dead abstract interfaces after a single implementation remains.
25. Dead adapters after migration.
26. Dead compatibility shims after all callers moved.
27. Dead test helpers not imported by any test.
28. Dead benchmark code not run by any benchmark command.
29. Dead scripts not present in `package.json`, Makefile, CI, or docs.
30. Dead generated clients for APIs no longer called.

Static analysis tools exist precisely because this category is common: ESLint’s `no-unused-vars` rule targets unused variables, functions, and parameters; Pylint has warnings for unused imports and variables; Meta describes using static, runtime, and application analysis to automatically remove dead code. ([ESLint][3])

## 4. Feature-flag rot

Feature flags are useful when temporary. They become dead code when nobody removes the losing branch.

Inexcusable patterns:

1. Flags left after 100% rollout.
2. Flags left after experiment conclusion.
3. Flags whose “off” branch can never run.
4. Flags whose “on” branch is universal.
5. Nested flags where nobody can reason about combinations.
6. Flag names that no longer describe the feature.
7. Flags with no owner.
8. Flags with no creation date.
9. Flags with no expiration date.
10. Flags with no cleanup ticket.
11. Flags removed from dashboard but not from code.
12. Flags removed from code but still in config.
13. Dead flag values in `.env.example`.
14. Dead flag values in Helm/Terraform/CloudFormation.
15. Old kill switches for incidents long over.
16. Old A/B test branches.
17. Old gradual-rollout code paths.
18. Old “temporary fallback” behavior.
19. Old dark-launch endpoints.
20. Old pricing/checkout/permission branches that product forgot existed.

Unleash explicitly recommends archiving stale feature flags and removing them from the codebase to keep technical debt low; LaunchDarkly similarly says flag cleanup should be scheduled and that a feature is done when the flag is archived. ([Unleash Documentation][4])

## 5. Duplicate implementation behavior

This is where migration happened but cleanup did not.

Inexcusable patterns:

1. `service`, `service_new`, `service_v2`, `service_final`.
2. `utils`, `utils2`, `helpers`, `helpers_new`.
3. Old REST client beside new GraphQL client.
4. Old ORM beside new ORM.
5. Old payment provider code after provider migration.
6. Old auth provider code after auth migration.
7. Old email/SMS provider code after vendor migration.
8. Old frontend framework left after rewrite.
9. Old routing system beside new routing system.
10. Old validation layer beside new validation layer.
11. Old permissions model beside new permissions model.
12. Old settings system beside new settings system.
13. Old telemetry/logging pipeline beside new one.
14. Old build tool beside new build tool.
15. Old package layout beside new monorepo layout.
16. Copy-pasted modules diverging over time.
17. Forked dependency code with no patch tracking.
18. “Temporary adapter” that becomes permanent.
19. Two ways to perform the same migration.
20. Two SDKs for the same API with no documented consumers.

A migration is not “done” when the new path works. It is done when the old path is removed, or when the old path has a documented owner, consumer, and sunset condition.

## 6. Dead dependency behavior

Unused dependencies are not harmless. They increase install time, audit noise, attack surface, license obligations, and upgrade complexity.

Inexcusable patterns:

1. Dependencies in `package.json`, `requirements.txt`, `go.mod`, `pom.xml`, `build.gradle`, `Gemfile`, `composer.json`, etc. that no code imports.
2. Dev dependencies for tools no longer run.
3. Lockfile entries kept alive only by old unused packages.
4. Multiple lockfiles from different package managers.
5. `node_modules`, `vendor`, `venv`, `.venv`, `.tox`, `.gradle`, `.m2`, `target`, `build` committed accidentally.
6. Vendored libraries duplicated with package-manager dependencies.
7. Old JAR/DLL/SO files committed with no provenance.
8. Submodules pointing to abandoned repos.
9. Forked dependencies with no upstream link or patch notes.
10. Deprecated packages kept because “nothing broke yet.”
11. Old dependency pins that block runtime upgrades.
12. Transitive dependency bloat from deleted features.
13. Vulnerable dependencies dismissed because “that code path is dead.”
14. Dependabot/Renovate disabled because alerts are noisy.
15. Security scanner suppressions with no expiry.
16. License scanner suppressions with no explanation.
17. Local tarball packages checked into the repo.
18. Old private registry packages still required by lockfiles.
19. Bundled minified vendor JS/CSS checked into source.
20. Dependency aliases hiding duplicate versions.

OWASP lists vulnerable and outdated components as a Top 10 web application security risk and explicitly includes unsupported/outdated libraries and unmaintained third-party components. GitHub Dependabot alerts and `npm audit` both exist to find vulnerable dependencies before they become security risks. ([OWASP Foundation][5])

## 7. Generated-file and build-artifact behavior

Generated outputs belong outside the repo unless there is a strong reason and a clear source of truth.

Inexcusable patterns:

1. `dist/` committed without a publish reason.
2. `build/`, `target/`, `bin/`, `obj/`, `.next/`, `.nuxt/`, `.turbo/`, `coverage/` committed accidentally.
3. Compiled `.class`, `.pyc`, `.o`, `.so`, `.dll`, `.exe` committed.
4. Minified bundles committed alongside source.
5. Generated SDKs committed with no generator version.
6. Generated protobuf/OpenAPI clients duplicated across services.
7. Generated docs committed while docs generation also runs in CI.
8. Generated snapshots not tied to tests.
9. Generated DB schema dumps with no restore process.
10. Generated lock/cache folders committed.
11. IDE project files committed unintentionally.
12. OS junk such as `.DS_Store`, `Thumbs.db`.
13. Local logs committed.
14. Local test reports committed.
15. Local screenshots from debugging committed.
16. “Temporary” generated files used by CI.
17. Build artifacts inside Docker context making images huge.
18. Generated files modified by humans.
19. Generated files not reproducible.
20. Generated files that conceal dead source code because nobody knows which is authoritative.

GitHub and Git both document `.gitignore` for files that should not be checked in; Git’s documentation specifically says project `.gitignore` files commonly contain patterns for files generated by the build. ([GitHub Docs][6])

3. API keys in old config.
4. API keys in commented-out code.

7. Certificates in old directories.
8. OAuth client secrets in mobile/web config.
9. Database URLs in old docs.
10. Cloud credentials in CI examples.
11. Tokens in old shell scripts.
12. Secrets in notebooks.
13. Secrets in logs.
14. Secrets in workflow artifacts.
15. Secrets in archived branches.
16. Secrets in git history after “deleting” the file.
17. Production data dumps.
18. PII/PHI/PCI data in fixtures.
19. Customer data in “sample” CSVs.

GitHub’s secret scanning documentation says hardcoded credentials become targets for unauthorized access and that scanning covers full Git history on all branches. GitHub’s sensitive-data removal guide says secrets should first be revoked or rotated and warns that rewriting history requires careful coordination and can reintroduce the secret if old clones push again. ([GitHub Docs][8])

# Repo behaviors that make dead code “inexcusable”

These are not files; they are team behaviors.

1. Merging replacement code without deleting the replaced code.
2. Calling a migration “done” before old path deletion.
3. Accepting “we might need it later” as justification.
4. Treating `main` as storage.
5. Treating branches as archive.
6. Treating PRs as archive.
7. Treating comments as backlog.
8. Treating TODOs as tickets.
9. Treating disabled tests as fixed tests.
10. Treating warnings as harmless.
11. Treating `archive/` as documentation.
12. Treating “not currently called” as “safe to ignore” instead of “delete or prove retained.”
13. Keeping dead code because deletion is emotionally uncomfortable.
14. Keeping dead code because the owner left.
15. Keeping dead code because nobody knows what it does.
16. Keeping dead code because it is scary.
17. Keeping dead code because a customer “might” use it, with no telemetry.
18. Keeping dead code because it is “public API,” with no consumers.
19. Keeping dead code because “it passes CI.”
20. Keeping dead code while disabling the checks that would catch it.
21. Letting old dependencies block upgrades.
22. Letting old code dictate architecture.
23. Letting skipped tests define quality.
24. Letting stale docs define product behavior.

26. Letting dead endpoints remain exposed.

# The highest-severity “red flag” list

If I were auditing a sloppy repo, these would be immediate escalation items:

1. Secrets in old files, comments, examples, logs, artifacts, or Git history.
2. Old auth/debug/admin endpoints still reachable.
3. Vulnerable dependencies kept because “the feature is dead.”
4. Archive folders included in builds, Docker images, packages, or deploys.
5. Commented-out auth, validation, payment, or permission logic.
6. Stale feature flags around security, billing, permissions, or checkout.
7. Dead CI/security scans disabled.
8. Deprecated public APIs with no telemetry or removal plan.
9. No owner for legacy code.
10. Abandoned repo not archived or marked unmaintained.
11. Old production data dumps.
12. Unknown-license copied code.
13. Old infrastructure configs that can still deploy.
14. Stale branches with privileged workflows.
15. Dead tests masking removed coverage.

# The clean-repo standard

A repo is clean when every old-looking thing satisfies one of these:

1. **Active:** it is built, tested, deployed, documented, and owned.
2. **Compatibility:** it has known consumers, telemetry, owner, and sunset date.
3. **Generated:** it has a source generator, command, and “do not edit” marker.
4. **Historical:** it lives in Git history, release tags, or an archived repo—not active source.
5. **Experimental:** it lives on a branch or separate sandbox, not `main`.
6. **Deleted:** it is gone, with the removal reason discoverable from commit/PR history.

Anything else is repo litter.

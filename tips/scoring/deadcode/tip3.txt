I’m using **“inexcusable”** to mean: dead, obsolete, unused, unreachable, unowned, undocumented, untested, or undeployed material that still lives in an active repo, package, image, build, deploy path, search path, or review path. Legitimate archival is different: GitHub’s own archive feature makes a repository read-only and signals that it is no longer actively maintained; burying old code inside `/archive`, `/old`, or `/backup` in an active repo is not the same thing. ([GitHub Docs][1])

Dead code is not just “mess.” MITRE’s CWE-561 defines dead code as code that can never be executed and explicitly says it indicates poor quality and should be removed before deployment. OWASP similarly notes that leftover code from prior iterations complicates logic and confuses developers. GitHub CodeQL points to the CERT guidance to detect and remove code that has no effect or is never executed. ([CWE][2])

## Exhaustive taxonomy of sloppy-repo dead-code behavior

### 1. Fake archive behavior

These are the classic repo rot signals:

`/archive`, `/archives`, `/old`, `/old_src`, `/older`, `/backup`, `/backups`, `/bak`, `/previous`, `/legacy`, `/deprecated`, `/obsolete`, `/unused`, `/dead`, `/graveyard`, `/attic`, `/junk`, `/trash`, `/temp`, `/tmp`, `/scratch`, `/sandbox`, `/experiment`, `/experiments`, `/prototype`, `/poc`, `/spike`, `/wip`, `/draft`, `/save`, `/copy`, `/copy2`, `/final`, `/final2`, `/new`, `/newer`, `/v1`, `/v2`, `/migration_backup`, `/rollback`, `/do_not_use`, `/remove_me`, `/delete_me`.

Inexcusable behavior:

* Moving dead code into `/archive` instead of deleting it.
* Keeping an old implementation beside a new one: `UserService`, `UserServiceNew`, `UserServiceOld`.
* Keeping “reference” implementations that no code calls.
* Copying entire old app versions into a subfolder.
* Keeping obsolete framework migrations “just in case.”
* Keeping old generated clients, SDKs, or API stubs after switching providers.
* Keeping abandoned prototypes inside the production repo.
* Keeping `/backup_2024_03_17` folders in source control.
* Keeping “temporary” migration copies after the migration shipped.
* Keeping rollback code forever instead of using version control, release artifacts, or database backups.
* Keeping old vendored library drops after the package manager replaced them.
* Keeping old monolith code inside the new service repo.
* Keeping a dead package in a monorepo workspace because “someone may need it.”
* Keeping “attic” folders searchable, buildable, packageable, or deployable.
* Keeping abandoned branches as the real archive instead of deleting or tagging.
* Keeping stale forks that look official.
* Keeping internal archive repos linked from current docs as if supported.

Robert C. Martin’s “Clean Code” guidance is blunt about the commented-out version of this: source control already remembers deleted code, so commented-out code should not survive in the working codebase. ([InformIT][3])

* Dead “migration mode” paths after migration completion.

## The shortest “inexcusable behavior” checklist

A repo is sloppy if it does any of this:

1. Uses source control as a junk drawer instead of deleting code.
2. Keeps `/old`, `/archive`, `/backup`, `/legacy`, `/deprecated`, or `/unused` inside active source.
3. Comments code out instead of deleting it.
4. Leaves unreachable branches.
5. Leaves unused files, functions, imports, exports, components, routes, configs, or dependencies.
6. Lets temporary feature flags become permanent architecture.
7. Ships old code paths that are not tested.
8. Keeps skipped tests forever.
9. Keeps deprecated APIs with no removal date.
10. Keeps generated artifacts, local caches, logs, or build output in the repo without an explicit release reason.
11. Leaves old CI, Docker, Terraform, Helm, or deployment files after migration.
12. Carries old dependencies after the code stopped using them.
13. Suppresses lint/type/security warnings instead of removing the cause.
14. Keeps stale docs that point engineers at dead behavior.
15. Keeps retired repos, branches, packages, or services looking active.

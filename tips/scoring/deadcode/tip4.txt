Here’s the audit-grade list. I’m treating **“inexcusable”** as: code or repo content that lives on the default branch or normal release path; has no current runtime, build, test, documentation, legal, or reproducibility purpose; has no owner, expiry, or removal plan; creates search/build/security/onboarding noise; and could instead be recovered from Git history, release artifacts, package registries, or a properly archived repository.

Dead code is generally unused or unreachable code; the recurring theme in research and maintainer guidance is that it is not “harmless clutter” because it increases comprehension cost, maintenance cost, and risk. ([Refactoring Guru][1]) GitHub also has a first-class repo archival mechanism for inactive repositories, and Git can recover deleted code through history searches such as `git log -S` and `git log -G`, so keeping a live `archive/` or `old/` directory inside the product tree needs a very high burden of proof. ([GitHub Docs][2])

I checked broadly across official docs, OSS issue trackers, developer forums, LinkedIn posts, and research. Quora pages were not reliably accessible through the browsing tool, so I did not use Quora as evidence. The pattern names that show up repeatedly are **dead code**, **obsolete code**, **lava flow**, **hoarder syndrome**, **stale repositories**, and **self-admitted technical debt**. ([Stack Overflow][3])

## Real sloppy-repo behaviors seen in the wild

Openverse maintainers discussed deleting an `archive` directory because retired DAGs and large artifacts were creating false positives in search, presenting non-idiomatic code as examples, and adding little value beyond what Git history already provided. ([GitHub][4]) Renovate had cleanup work around stale TODOs where closed or merged issues were still referenced from many places in the codebase. ([GitHub][5]) Storybook had an issue calling out a near-duplicate file as unused/dead code and recommending deletion to reduce maintenance and bug risk. ([GitHub][6]) Magma maintainers proposed removing stale top-level directories and legacy components because they added confusion, attack surface, and made the project appear larger than it was. ([GitHub][7])

# Search terms worth grepping immediately

```bash
git grep -nE '\b(TODO|FIXME|HACK|XXX)\b'
git grep -nEi 'temporary|workaround|for now|later|remove once|delete after|should be removed|will remove'
git grep -nEi 'deprecated|legacy|obsolete|unused|dead|do not use|not used|keep for reference|just in case'
git grep -nEi 'archive|old|backup|bak|copy|final|graveyard|attic|scratch|spike|prototype|experiment'
git grep -nEi 'USE_LEGACY|ENABLE_OLD|DISABLE_NEW|ROLLBACK|DUAL_WRITE|MIGRATION_MODE|AB_TEST|EXPERIMENT'
```

```bash
find . -iname '*old*' \
  -o -iname '*legacy*' \
  -o -iname '*archive*' \
  -o -iname '*backup*' \
  -o -iname '*deprecated*' \
  -o -iname '*unused*' \
  -o -iname '*dead*' \
  -o -iname '*copy*' \
  -o -iname '*tmp*' \
  -o -iname '*scratch*' \
  -o -iname '*prototype*'
```

```bash
git log --all --name-status --diff-filter=D -- path/to/file_or_dir
git log -S 'SomeSymbolOrString' --all -- path/to/search
git log -G 'regex_for_old_behavior' --all -- path/to/search
```

The last two are useful because Git’s `-S` searches for changes in the number of occurrences of a string, while `-G` searches patch text matching a regex. ([Git][19])

# What is not automatically inexcusable

Some things look dead but can be legitimate when they are clearly owned, tested, documented, and time-bounded:

* Compatibility code for actively supported clients.
* Database migrations required for a supported upgrade path.
* Fixtures used by active tests.
* Example code that is tested and published as documentation.
* Generated code required by consumers, when the generator and verification are documented.
* Vendored code required for air-gapped, licensing, or reproducible-build reasons, with a patch/update policy.
* Archived repositories that are correctly marked read-only, documented as inactive, stripped of live secrets, and removed from deploy/scanning assumptions.
* Feature flags during an active rollout with owner, expiry, metrics, and cleanup issue.
* Legal or compliance retention artifacts stored in the right system, not mixed into live source.

# The blunt rule

A repo item is inexcusable dead code when it fails two or more of these checks:

1. **Owner:** someone accountable owns it.
2. **Entrypoint:** a live runtime/build/test/docs path uses it.
3. **Proof:** telemetry, dependency graph, or CI proves it is used.
4. **Tests:** current tests cover the reason it exists.
5. **Docs:** docs explain why it remains.
6. **Expiry:** it has a removal date or removal condition.
7. **Security:** it is scanned for secrets, vulnerabilities, and licenses.
8. **Regeneration:** generated/binary artifacts can be reproduced.
9. **Recovery:** deletion is safe because Git history, package registry, release artifact, or archive can recover it.
10. **Cost:** keeping it does not slow clone, build, CI, reviews, search, onboarding, upgrades, or security work.

When the answer is “we do not know,” the code is already guilty until proven live.

Below is a **practically exhaustive taxonomy of inexcusable dead-code / repo-rot behavior** I’d look for in a sloppy repo. I’m using “dead code” broadly: source, folders, dependencies, configs, branches, build files, docs, tests, deployment assets, and stale product paths that no longer serve a live purpose.

I treated GitHub/docs/vendor engineering blogs as the strongest sources. Social/forum material from X, LinkedIn, Reddit, Stack Overflow, etc. mostly echoed the same theme: Git/history exists, so keeping obsolete code “just in case” is usually repo pollution. Quora pages were not accessible to my browsing tool, so I’m not relying on them.

## Baseline: what makes this behavior inexcusable

Dead code is not harmless clutter. Research on Java desktop apps describes dead code as unused and/or unreachable code, says prior evidence shows it harms comprehensibility and maintainability, and found that dead methods often survive for a long time and are rarely revived. ([Springer Link][1]) Google and Meta both built automated systems to delete dead code at scale, which is a strong signal that mature engineering orgs treat deletion as an operational discipline, not optional tidying. Google’s Sensenmann sends more than 1,000 deletion changelists per week and had deleted nearly 5% of Google C++ at the time of publication; Meta’s SCARF combines static, runtime, and product analysis to identify and remove dead code. ([Google Testing Blog][2])

The rule of thumb: **if it is not built, shipped, tested, monitored, owned, documented truthfully, or intentionally archived outside the active path, it should not live in the active repo.** Refactoring guidance says to delete unused code and unneeded files; GitHub’s own docs recommend deleting merged or stale branches; GitHub archive docs say archived repos should be read-only and clearly marked as no longer actively maintained. ([Refactoring Guru][3])

GitHub examples show a healthier version of this: old repos can be archived, marked read-only, and pointed at successors. Examples include repos whose README says “Do not use this repository” and points to the replacement, or “old source code… out of date and should not be used.” ([GitHub][4]) Google’s open-source repo management guidance similarly says to update the README to indicate the repo is no longer maintained and then archive it. ([Google Open Source][5])

510. Dead tests plus high claimed coverage.
511. Deprecated endpoints plus no traffic data.
512. Legacy code plus no tests plus no owner.
513. “Temporary” migration scripts committed for years.
514. Old infra code with live credentials.
515. Multiple old implementations plus no product decision.
516. Stale docs plus automated agents using those docs.
517. CI excludes dead folders instead of deleting them.
518. “Do not delete” comments without a ticket, owner, or date.
519. Public stale repos with broad org permissions.
520. Stale branches from former employees.
521. Old vendor integrations plus active secrets.
522. Dead API contracts plus generated clients.
523. Stale flags plus stale experiments plus stale dashboards.
524. Old package versions kept only for dead code.
525. Hidden dynamic usages with no telemetry, tests, or documentation.

## A hardline cleanup standard

A repo is healthy when obsolete things are **deleted, archived intentionally, or justified with ownership and expiry**. The inexcusable version is leaving them in the active path where developers, CI, scanners, agents, and future maintainers must keep paying attention to them.

A good policy is:

**Delete** dead code and unneeded files.
**Archive** whole repos only when they are truly inactive, read-only, and clearly redirected.
**Tag/release** historical states instead of keeping `old/` folders.
**Expire** feature flags at creation time.
**Measure runtime liveness** for endpoints, jobs, CLIs, and dynamic dispatch.
**Prune dependencies** as part of security hygiene.
**Reject commented-out code** in review.
**Treat stale docs/tests/config as dead code** because they preserve obsolete behavior in people’s heads.

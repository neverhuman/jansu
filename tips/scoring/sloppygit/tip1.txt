You’re right to treat this as more than “style.” In Git, fake versioning habits create unreproducible releases, impossible reviews, broken rollbacks, bloated history, and security exposure.

One caveat: nobody can prove a literally complete list of every bad behavior ever mentioned on Reddit, X, LinkedIn, Quora, etc. I treated this as a practical exhaustive blacklist: recurring public-discussion anti-patterns plus the canonical Git/GitHub/SemVer guidance that makes them objectively indefensible. Quora-specific pages were not reliably accessible, so I am not inventing unverifiable Quora claims.

Below is the list I’d call **inexcusable in a professional repo unless explicitly documented, automated, and justified**.

## 1. Manual “version control outside version control”

These are the core bad behaviors you called out: using filenames, folders, comments, zips, or copies as a fake version-control system even though Git already records history. Public discussions repeatedly call out `file_v1/file_v2`, dated folder copies, binary `FINAL_v2` files, and the recommendation to use tags/commits instead. ([Reddit][1])

3. Keeping old versions as `module_old.js`, `module_backup.js`, `module_DO_NOT_USE.js`.
4. Copying entire source trees before making a change.
5. Keeping “current” and “previous” copies of the same code in the repo.
6. Using dates as folder versions: `2024-05-01/`, `2024-05-15-fixed/`, `release_2026_05_06/`.
7. Using deployment folders as source history: `prod_copy/`, `prod_before_patch/`, `qa_v2/`.
8. Committing zipped source snapshots: `source.zip`, `project_2026_05_06.zip`, `backup.tar.gz`.
9. Exporting code from another system, zipping it, and bulk-committing the archive as “the version.”
10. Keeping file-level version numbers independent of the repository version.
11. Adding manual version comments at the top of files instead of relying on commit history.

18. Maintaining customer-specific copies as folders: `clientA/`, `clientB/`, `clientC/`, instead of configuration, feature flags, packages, or branches.
19. Manually copying files between “versions” instead of merging/cherry-picking.
20. Deploying from a copied folder instead of a tagged commit or immutable release artifact.

**Correct replacement:** use commits for history, branches for parallel work, tags for released versions, package versions for distributed code, and release artifacts for built outputs.

## The truly unforgivable top tier

These are the ones I would treat as **hard-stop, no-excuse failures** in almost any professional repository:

1. **Versioned folders/files instead of Git history:** `project_v2`, `final_final`, dated source copies.
2. **No release tags or mutable release tags.**
3. **Reusing the same version number for different code.**
4. **Moving or force-overwriting published tags.**
5. **Committing secrets, then only deleting them without rotation.**
6. **Force-pushing shared/protected branches without coordination.**
7. **Committing directly to main/release branches without review/checks.**
8. **Committing large binaries, datasets, or build artifacts to normal Git history without LFS/artifact storage.**
9. **Committing generated/build output as if it were source, with no documented reason.**
10. **Using environment branches/folders as divergent source versions.**
11. **Shipping releases that cannot be traced to an exact commit, tag, and artifact.**
12. **Manual deployment from copied folders or developer machines.**
13. **No branch protection on important branches.**
14. **No CI/status checks before merge or release.**
15. **No documented versioning/release process in a team repo.**

A good rule of thumb: **Git versions commits; package managers version packages; tags identify releases; artifact stores hold builds; secret managers hold secrets.** Any workflow that replaces those with filenames, folders, screenshots, zips, Slack messages, or memory is the bad behavior.

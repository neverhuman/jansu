Below is a **practical exhaustive taxonomy** of “versioning bad behavior” in Git. By “inexcusable,” I mean: **in a shared/professional repository, after Git is already available, and without a documented exception.** Some patterns are acceptable only when deliberately designed, for example `/api/v2` as a real compatibility boundary, a `release/2.x` branch for maintained old releases, or committed generated files for a documented distribution reason.

The core rule:

> **Never create a second fake version-control system inside Git.**
> Code history belongs in commits. Release identity belongs in tags/releases. Component versions belong in manifests. Large artifacts belong in artifact storage, Git LFS, or DVC. Database versions belong in migrations.

Public discussions repeatedly show the same anti-patterns: manual `v1`, `v2`, `final`, `REAL_FINAL` filenames; separate folders for each software version; careless Git habits like blind `git add -A`; and large files/data committed into normal Git history. Stack Overflow answers also point beginners away from filename versioning and toward Git commits/tags. ([Reddit][1])

## A. Inexcusable Git/versioning anti-patterns

### 1. Versioning by filename, folder, or copy

These are the classic “we are pretending Git does not exist” mistakes.

1. `file_v2.py`, `file_v3.py`, `file_final.py`, `file_final_FINAL.py`.
2. `README_old.md`, `README_new.md`, `README_really_new.md`.
3. `app_copy.py`, `app_backup.py`, `app_before_refactor.py`.
4. `src_v1/`, `src_v2/`, `src_v3/`.
5. `project-v1/`, `project-v2/`, `project-latest/` inside the same repo.
6. `old/`, `archive/`, `backup/`, `do_not_delete/` folders containing previous code.
7. Date folders used as version history: `2024-01-01/`, `2024-02-15-final/`.
8. “Current” folders: `current/`, `latest/`, `prod-current/`.
9. Keeping an entire previous repo copy inside the repo.
10. Committing `.zip`, `.tar.gz`, `.rar`, or `.7z` archives of earlier repo states.
11. Keeping both `component.js` and `component_new.js` instead of changing the original file and relying on history.
12. Renaming files every release solely to encode version, for example `invoice_v1.ts`, `invoice_v2.ts`.
13. Using filenames as workflow state: `approved_report.md`, `reviewed_report.md`, `client_sent_report.md`.
14. Keeping “backup before merge” files committed.
15. Keeping unresolved conflict leftovers as “versions,” for example `file.mine`, `file.theirs`, `file.orig`.
16. Duplicating generated bundles as `bundle.1.js`, `bundle.2.js`, `bundle.final.js` in source.
17. Keeping separate copies for each customer unless those are truly separate products.
18. Creating `v2` folders for code that should be a Git tag, branch, package version, or API version.
19. Keeping “just in case” deleted files in a `graveyard/` folder.
20. Treating GitHub/Bitbucket/GitLab as Dropbox with manually named copies.

**Correct replacement:** one canonical file/folder, normal commits, meaningful branches while work is active, and tags/releases for stable snapshots.

### 2. Misusing branches

Branches are for **active lines of development**, not for every historical snapshot. Git branches are intentionally lightweight and support branching/merging often, while Git workflows commonly use feature branches, release branches, and hotfix branches with review and testing. ([Git][2])

21. Creating a branch for every version ever released when no future maintenance will happen.
22. Using `v1`, `v2`, `v3` branches where immutable tags are the right object.
23. Leaving hundreds of dead release branches instead of tagging releases and pruning branches.
24. `release-final`, `release-final-2`, `release-real-final`.
25. `prod`, `production`, and `main` all drifting with unclear meaning.
26. Using a branch named `latest`.
27. Using `develop`, `staging`, `qa`, `prod`, and `release` without documented promotion rules.
28. Directly committing to `main`/`master` in a team repo without review.
29. Directly committing to production branches.
30. Using long-lived feature branches that diverge for weeks/months and become unmergeable.
31. Using personal branches as permanent release records.
32. Creating customer-specific branches that permanently fork the product without a support policy.
33. Cherry-picking randomly between branches without tracking what has been backported.
34. Fixing a supported release branch but forgetting to fix `main`.
35. Fixing `main` but forgetting supported release branches.
36. Releasing from an arbitrary developer branch.
37. Releasing from a dirty local working tree.
38. Releasing code that has not passed the same checks as `main`.
39. Treating branches as access control instead of using permissions/protected branches.
40. Force-pushing shared branches without an explicit emergency procedure.

**Correct replacement:** feature branches for work in progress, protected `main`, release branches only for actively maintained release lines, hotfix branches for urgent fixes, and immutable tags for release points.

**Correct replacement:** immutable, protected, preferably annotated/signed tags such as `v1.2.3` or `api/v1.2.3`, created by CI from a clean commit, with release notes and artifacts tied to that exact commit.

## B. Best-known practices for managing versions in Git

### 1. Use the right object for the job

Use this mapping as policy:

| Thing being versioned          | Best mechanism                                 |
| ------------------------------ | ---------------------------------------------- |
| Source code evolution          | Git commits                                    |
| Active work                    | Feature branches                               |
| Supported maintenance line     | `release/<major>.x` branch                     |
| Immutable release point        | Annotated/signed Git tag                       |
| Published release notes/assets | GitHub/GitLab release                          |
| Package/library version        | Manifest file plus Git tag                     |
| Docker/container image         | Registry tag plus digest plus OCI labels       |
| Database schema                | Ordered immutable migrations                   |
| Large binary artifacts         | Artifact registry or Git LFS                   |
| Datasets/models                | DVC, Git LFS, artifact/model registry          |
| Config schema                  | Versioned config schema and migration notes    |
| API contract                   | OpenAPI/spec version plus compatibility policy |

### 2. Tag every release immutably

For official releases:

* Tag the exact commit being released.
* Prefer annotated tags for releases.
* Sign tags when provenance matters.
* Protect release tags.
* Never move `v1.2.3` after publishing.
* If a release is bad, publish `v1.2.4`; do not rewrite `v1.2.3`.
* Use release notes attached to the tag.
* Attach artifacts built by CI from that tag.

GitHub documents signed tags, and GitLab documents protected tags to control who can create/update/delete release tags. ([GitHub Docs][13])

### 3. Choose and document your versioning scheme

For most libraries, SDKs, APIs, and packages, use SemVer:

```text
MAJOR.MINOR.PATCH
1.4.2
```

Meaning:

* `PATCH`: compatible bug fix.
* `MINOR`: backward-compatible feature/addition.
* `MAJOR`: breaking/incompatible change.

For products where calendar identity matters more than API compatibility, use documented CalVer, for example `2026.05.0`. Do not mix schemes casually.

### 4. Keep one source of truth for the version

Pick one canonical version location per component:

* Node/package: `package.json`.
* Python package: `pyproject.toml`.
* Rust: `Cargo.toml`.
* Java/Maven: `pom.xml`.
* Gradle: `gradle.properties` or build file.
* Go: usually Git tags/modules rather than a manually edited version field.
* Generic service: `VERSION` or build metadata generated from Git tag.

Everything else should derive from that source or from the release tag. Do not hardcode the same version in five places.

### 5. Use release automation

Good automation does at least this:

1. Checks branch protection and CI status.
2. Determines changed components.
3. Determines version bump.
4. Updates manifest/version files.
5. Updates changelog.
6. Creates tag.
7. Builds artifacts from a clean checkout.
8. Publishes package/image/release.
9. Records provenance: Git SHA, tag, build ID, artifact digest.

Tools such as semantic-release can automate SemVer-based version determination, changelog generation, tagging, and publishing from commit conventions. ([GitHub][14])

### 6. Use Conventional Commits or another strict commit convention

A practical convention:

```text
feat(api): add customer search endpoint
fix(auth): handle expired refresh tokens
docs(sdk): document retry behavior
refactor(worker): split queue handler
feat!: remove legacy v1 endpoint
```

Then map:

* `fix` → patch.
* `feat` → minor.
* `!` or `BREAKING CHANGE:` → major.

This works especially well with automated changelogs and releases. ([Conventional Commits][15])

### 7. Maintain a human changelog

A good changelog is not just `git log`. It should group notable changes by version and date, with sections such as:

```text
## [2.1.0] - 2026-05-06

### Added
- New bulk import endpoint.

### Changed
- Improved retry behavior for transient failures.

### Deprecated
- Legacy v1 export endpoint.

### Fixed
- Fixed token refresh race condition.

### Security
- Patched vulnerable dependency.
```

Keep a Changelog explicitly recommends human-readable, chronologically ordered notable changes, with versions, dates, and categories; it also warns against dumping raw commit logs or hiding breaking changes/deprecations. ([keepachangelog.com][16])

### 8. Protect `main`, release branches, and tags

Minimum professional settings:

* Require pull requests.
* Require at least one review.
* Require CI checks.
* Prevent direct pushes to `main`.
* Restrict who can create release tags.
* Restrict who can delete/move release tags.
* Require signed commits/tags where appropriate.
* Disable force-pushes on protected branches.

GitHub branch protection rules support requiring reviews and status checks before merge. ([GitHub Docs][17])

### 9. Use branches intentionally

A clean branch model:

```text
main
feature/<ticket-or-topic>
bugfix/<ticket-or-topic>
release/1.x
hotfix/<ticket-or-topic>
```

Rules:

* `main` is always releasable.
* Feature work happens in short-lived branches.
* Releases are tagged from `main` or a release branch.
* `release/1.x` exists only if version 1 is still maintained.
* Hotfixes are merged to `main` first, then backported to supported branches.
* Historical versions are tags, not branches.

### 10. For monorepos, choose fixed or independent versioning deliberately

**Fixed versioning** works when components are shipped together:

```text
repo tag: v3.8.0
all packages: 3.8.0
```

**Independent versioning** works when components ship separately:

```text
api/v2.4.1
web/v7.3.0
sdk-js/v1.9.2
worker/v0.12.0
```

For independent monorepos, use tools like Changesets, Nx Release, Lerna, Rush, Turborepo workflows, or custom CI to detect changed packages and update dependent package versions.

### 11. Version packages through their ecosystem

Examples:

```text
Node:   package.json version + npm publish + Git tag
Python: pyproject.toml version + wheel/sdist + Git tag
Rust:   Cargo.toml version + cargo publish + Git tag
Java:   pom.xml/Gradle version + Maven repository + Git tag
Go:     module path + SemVer Git tags
```

For npm specifically, name and version identify package releases, and published changes should come with version changes. ([npm Docs][18])

### 12. Version containers separately but traceably

Recommended image tags:

```text
my-service:1.4.2
my-service:1.4
my-service:1
my-service:git-a1b2c3d
```

Also record:

```text
org.opencontainers.image.source
org.opencontainers.image.version
org.opencontainers.image.revision
org.opencontainers.image.created
```

Deploy by immutable digest where reproducibility matters:

```text
my-service@sha256:...
```

Use `latest` only as a convenience pointer, never as the only release identity.

### 13. Version databases with immutable migrations

Good migration naming:

```text
V001__create_users.sql
V002__add_email_to_users.sql
V003__create_orders.sql
V004__add_order_status.sql
```

Rules:

* Never edit applied migrations.
* Create a new migration to change state.
* Keep migrations in Git with the app.
* Test migrations from the previous released version.
* Make destructive changes backward-compatible when rolling deployments require it.
* Use migration checksums/history tables.

### 14. Use Git LFS, DVC, artifact stores, and registries for non-source assets

Use normal Git for source and small text metadata. Use specialized storage for big or generated things:

| Asset               | Better practice                                   |
| ------------------- | ------------------------------------------------- |
| Large images/videos | Git LFS or object storage                         |
| Release binaries    | GitHub/GitLab release assets or artifact registry |
| Docker images       | Container registry                                |
| Datasets            | DVC/object storage                                |
| ML models           | DVC/model registry/artifact store                 |
| Database backups    | Backup system/object storage, not Git             |
| Build outputs       | CI artifacts/package registry                     |

Commit pointer/metadata files when appropriate, for example `.gitattributes` for LFS or `.dvc` files for DVC.

### 15. Make every deployed version traceable

Every running service should be able to answer:

```text
version: 1.4.2
git_sha: a1b2c3d4
build_time: 2026-05-06T14:32:00Z
image_digest: sha256:...
```

Expose this through logs, health endpoints, admin UI, Kubernetes labels, or deployment metadata.

### 16. Use a release checklist

A strong release checklist:

```text
[ ] main/release branch is green
[ ] changelog updated
[ ] version bump is correct
[ ] migration reviewed
[ ] breaking changes documented
[ ] tag created by CI
[ ] artifacts built from clean checkout
[ ] package/image published
[ ] release notes published
[ ] deployment version recorded
[ ] rollback/roll-forward path known
```

### 17. Handle bad releases by rolling forward, not rewriting history

Bad:

```text
git tag -d v1.2.3
git tag v1.2.3 <new-commit>
git push --force --tags
```

Good:

```text
v1.2.3  # bad release, documented
v1.2.4  # hotfix release
```

Then mark `v1.2.3` as deprecated/yanked where the package ecosystem supports it, and explain the fix in the changelog.

## C. “Bad → good” examples

| Bad behavior                      | Good replacement                            |
| --------------------------------- | ------------------------------------------- |
| `src_v2/`                         | Same `src/` folder; tag `v2.0.0`            |
| `file_final.py`                   | Commit the final state; tag/release it      |
| `project_backup.zip`              | Git remote + tags/releases                  |
| `release-final-2` branch          | `v1.2.1` tag or `release/1.x` branch        |
| `schema_v3.sql`                   | Immutable migration `V003__description.sql` |
| `model_final.pkl`                 | DVC/LFS/model registry version              |
| Docker `latest` only              | `1.2.3`, Git SHA tag, digest                |
| Reusing `v1.2.3`                  | Publish `v1.2.4`                            |
| One version string in five files  | One source of truth; generate the rest      |
| Copy-pasted shared library        | Package, submodule, subtree, or monorepo    |
| Raw commit log as changelog       | Curated changelog grouped by version        |
| `data_v7_final/`                  | Stable path plus DVC-tracked revisions      |
| Branch dependency `main`          | Version range, tag, or immutable SHA        |
| Manual release from laptop        | CI release from clean tagged commit         |
| `config-prod-v2.yml` with secrets | Versioned config schema + secrets manager   |

## D. A strict policy template

```text
Versioning policy

1. Git history
   - Source history is represented only by commits.
   - Manual versioned filenames/folders are prohibited.

2. Branches
   - main is protected and must remain releasable.
   - Work happens on feature/* or bugfix/* branches.
   - release/<major>.x branches exist only for supported maintenance lines.

3. Tags
   - Every release must have an annotated tag.
   - Tags are immutable after publication.
   - Tags are protected.
   - Component tags in monorepos use <component>/vMAJOR.MINOR.PATCH.

4. Versions
   - Components follow SemVer unless documented otherwise.
   - Each component has one version source of truth.
   - Breaking changes require a major version bump.

5. Changelog
   - Every release has human-readable notes.
   - Breaking changes, removals, deprecations, migrations, and security fixes are explicit.

6. Artifacts
   - Binaries, datasets, models, and images are stored in the appropriate registry/storage.
   - Artifacts must record Git SHA, version, build time, and digest/checksum where applicable.

7. Database
   - Schema changes use immutable migrations.
   - Applied migrations are never edited.

8. Security
   - Secrets are never committed.
   - If a secret is committed, it is revoked/rotated and history cleanup is coordinated.

9. Releases
   - Releases are created by CI from a clean commit.
   - Bad releases are superseded by new versions, not overwritten.
```

The shortest enforceable version is:

> **No `_v2`, no `final`, no copied release folders, no mutable release tags, no untracked manual release state. Every released thing must trace back to one Git commit, one immutable tag, one version policy, and one reproducible artifact.**

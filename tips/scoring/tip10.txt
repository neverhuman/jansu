I understand the mission as: **make agent-assisted code changes rejectable, localizable, provable, repairable, and reviewable without letting “looks fine” become merge policy**. Jankurai is already much stronger than a normal lint/audit tool: it has owner maps, test maps, generated-zone policy, proof lanes, repair queues, score artifacts, UX evidence, language bad-behavior catalogs, release evidence, and a hard-cap scoring model. The missing step is to make the score mean: **all important evidence actually ran, on this commit, in strict mode, after all artifacts were generated, with external/repo-control verification, and with no stale or self-generated proof.**

I inspected the uploaded tarball statically. I also tried to compile-test it, but this environment cannot resolve crates.io and the offline cache did not contain required crates, so I could not execute the Rust test suite here. The offline check failed with `no matching package named anyhow found`. Everything below is based on code, docs, workflows, config, and current public best-practice references.

## Highest-priority findings

### 1. The final audit score is generated too early

The workflow creates `agent/repo-score.json` at the beginning of the `audit` job, then runs proofbind, proofmark, rust witness, UX QA, security, vibe coverage, language bad-behavior tests, public evidence, optimization, and exception expiry **after** the score has already been written. Evidence: `.github/workflows/jankurai.yml:32-38` writes the score and ratchet output; `.github/workflows/jankurai.yml:41-113` runs most evidence-producing lanes after that; `.github/workflows/jankurai.yml:114-145` uploads all artifacts.

That means the uploaded score can be a **pre-evidence score**. The report may not include the security evidence artifact, UX report, proofmark receipt, public evidence bundle, or exception-expiry outcome from the same run.

**Fix:** split CI into two stages:

1. Generate all evidence first: security, SAST, proofbind, proofmark, witness, UX QA, migration, vibe validate/coverage, release evidence, exception expiry.
2. Run one final `jankurai audit` last, ingesting every artifact.
3. Upload that final score as the only authoritative score.

Add a hard cap:

`HLT-038-FINAL-AUDIT-NOT-LAST`
Max score: 70
Trigger: `agent/repo-score.json` is created before required evidence artifacts, or any required artifact has `generated_at` newer than the score report.

### 2. The CI ratchet baseline is self-generated in the same run

The workflow generates a score, copies it to `target/jankurai/baseline-score.json`, then immediately ratchets against that same file. Evidence: `.github/workflows/jankurai.yml:32-38`.

That defeats the purpose of a ratchet. A ratchet must compare against the last accepted baseline from protected `main`, a signed score ledger, or a previous successful CI artifact. The code also silently falls back to the current score if the baseline JSON parses but lacks a usable `score` field: `unwrap_or(report.score as i64)` in `crates/jankurai/src/main.rs:2286-2292`.

**Fix:** reject baselines that are generated in the same run, have the same `input_fingerprint` as the current report, are parse-invalid, lack `score`, or are not from a trusted source. Add:

`HLT-039-FALSE-RATCHET-BASELINE`
Max score: 65
Trigger: ratchet baseline is produced during the same workflow run, missing required metadata, parse-invalid, or not traceable to protected-branch history.

### 3. The security lane is non-strict in CI

`tools/security-lane.sh` defaults `JANKURAI_SECURITY_STRICT` to `0`, so missing tools are skipped/advisory unless strict mode is explicitly enabled. Evidence: `tools/security-lane.sh:4`, `tools/security-lane.sh:41-50`, `tools/security-lane.sh:73-99`.

The CI job runs:

`jankurai security run . --out target/jankurai/security/evidence.json`

with no `--strict`. Evidence: `.github/workflows/jankurai.yml:86-87`.

The security policy only requires `gitleaks`; `cargo audit` and `npm audit` are advisory. Evidence: `agent/security-policy.toml:3-16`.

For a “best available standard,” CI security evidence must fail closed. GitHub’s dependency review action is designed to scan pull requests for dependency changes and raise errors for introduced vulnerabilities or invalid licenses, which is exactly the kind of PR-time gate Jankurai should ingest rather than merely mention. ([GitHub][1])

**Fix:** make `--strict` mandatory for CI/release modes. Require every configured security command to run, emit machine-readable results, and fail on configured severity thresholds.

Add:

`HLT-040-SECURITY-NONSTRICT-CI`
Max score: 70
Trigger: CI security lane runs with `wrapper_strict=false`.

`HLT-041-SECURITY-TOOL-SKIPPED-OR-FAILED`
Max score: 60
Trigger: any required security tool is skipped, missing, failed, or not represented in the evidence artifact.

`HLT-042-SECURITY-ARTIFACT-STALE`
Max score: 70
Trigger: security evidence `git_head` differs from score `git.head`, or artifact timestamp/run ID does not match the final audit run.

### 4. Security scoring is too marker-based

`has_secret_or_dependency_scans` returns true when the security text contains **any** one of `tools/security-lane.sh`, `gitleaks`, `dependency-review`, `syft`, `grype`, `cargo audit`, or `npm audit`. Evidence: `crates/jankurai/src/audit/helpers.rs:561-574`.

The security dimension awards points for text markers like `gitleaks`, `audit`, `syft`, `sbom`, `zizmor`, and `cargo audit`, but the score is not hard-gated on current security evidence proving those commands ran successfully. Evidence: `crates/jankurai/src/audit/analyzers/security.rs:23-68`.

You already parse a security evidence artifact with `wrapper_strict`, `commands_ran`, `commands_skipped`, `commands_failed`, `generated_at`, and `git_head`. Evidence: `crates/jankurai/src/audit/security_artifact.rs:30-71`. The missing part is making those fields authoritative.

**Fix:** score security from evidence, not text. “Tool configured” should be low maturity. “Tool ran in CI on this commit, strict mode, uploaded artifact, verified schema, no skipped commands” should be high maturity.

Add report-level fields:

```json
"evidence_maturity": {
  "security": "artifact_verified",
  "sast": "missing",
  "sbom": "configured",
  "repo_controls": "missing"
},
"score_confidence": "medium",
"skipped_required_tools": 0,
"stale_artifacts": 0
```

### 5. GitHub Actions are not pinned to full commit SHAs

The workflow uses mutable references such as `actions/checkout@v6`, `dtolnay/rust-toolchain@stable`, `actions/setup-node@v6`, and `actions/upload-artifact@v7`. Evidence: `.github/workflows/jankurai.yml:12-16`, `.github/workflows/jankurai.yml:114`, `.github/workflows/jankurai.yml:150-163`.

The composite action also uses `dtolnay/rust-toolchain@stable`. Evidence: `action.yml:20-25`.

GitHub’s secure-use guidance says pinning an action to a full-length commit SHA is the only way to use an action as an immutable release; tags can move or be deleted. ([GitHub Docs][2])

Your CI detector only flags `@main`, `@master`, and `@latest`, not version tags or `@stable`. Evidence: `crates/jankurai/src/audit/language_rules/ci.rs:66-78`.

**Fix:** for HL3/release mode, treat any third-party `uses:` value not pinned to a full SHA as a high finding. Keep lower modes advisory to avoid surprising adopters.

Add:

`HLT-043-WORKFLOW-ACTION-NOT-SHA-PINNED`
Max score: 70
Trigger: external GitHub Action or reusable workflow is not pinned to a full-length commit SHA.

### 6. Workflow permissions are not explicit

The main workflow has no top-level `permissions:` block. Evidence: `.github/workflows/jankurai.yml:1-8`.

GitHub Actions supports a top-level or job-level `permissions` key for `GITHUB_TOKEN`; when any permissions are specified, unspecified permissions are set to `none`, and `permissions: {}` disables all token permissions. ([GitHub Docs][3]) GitHub also warns that actions can access `github.token` and recommends least-privilege credentials. ([GitHub Docs][4])

**Fix:** set default read-only/none permissions, then grant narrow job-specific writes only where needed:

```yaml
permissions:
  contents: read

jobs:
  audit:
    permissions:
      contents: read
      security-events: write   # only if uploading SARIF
      attestations: write      # only if generating attestations
      id-token: write          # only if using OIDC/attestation/cloud auth
```

Add:

`HLT-044-GITHUB-TOKEN-PERMISSIONS-GAP`
Max score: 75
Trigger: workflow lacks explicit least-privilege permissions.

### 7. SARIF is generated but not uploaded to GitHub code scanning

The workflow writes `target/jankurai/jankurai.sarif` and uploads it as an artifact. Evidence: `.github/workflows/jankurai.yml:38`, `.github/workflows/jankurai.yml:114-145`.

I did not see a `github/codeql-action/upload-sarif` step. Without upload, GitHub code scanning cannot surface findings in the Security tab or act as a PR check. GitHub code scanning supports CodeQL and third-party analysis, displays alerts in the repository security view, and can report alerts on pull requests when configured as a PR check. ([GitHub Docs][5]) ([GitHub Docs][6])

**Fix:** upload Jankurai SARIF and any SAST SARIF to GitHub code scanning in CI. Require `security-events: write` only on that job.

Add:

`HLT-045-SARIF-GENERATED-NOT-UPLOADED`
Max score: 82
Trigger: SARIF artifact exists but no SARIF upload step exists in CI.

### 8. No independent SAST/code scanning lane

Jankurai has many custom detectors, but I did not find a CodeQL, Semgrep, or equivalent SAST lane in the workflow. Custom scanners are useful, but world-class audit posture needs an independent SAST/code-scanning layer.

**Fix:** add a `sast` lane with CodeQL and/or Semgrep SARIF. For this repo:

* CodeQL for JavaScript/TypeScript and Python where applicable.
* Semgrep or equivalent for TS/Python/Docker/YAML patterns.
* Rust-specific: clippy security/correctness profile, cargo-geiger or unsafe-review evidence where applicable, cargo-audit/deny/vet for dependencies.
* Upload SARIF and ingest summary into Jankurai score.

Add:

`HLT-046-SAST-EVIDENCE-GAP`
Max score: 80
Trigger: product-code repo lacks current SAST/code-scanning evidence.

### 9. No OpenSSF Scorecard / external posture calibration

Jankurai is self-auditing. That is valuable, but for a world-class score, it should be externally calibrated. OpenSSF Scorecard assesses projects through automated checks across source, build, dependencies, testing, and maintenance; its checks include Branch Protection, Dangerous Workflow, Code Review, Pinned Dependencies, Token Permissions, Packaging, Signed Releases, SAST, Fuzzing, Dependency Update Tool, Security Policy, and Vulnerabilities. ([undefined][7])

**Fix:** add Scorecard as an external signal. Ingest JSON/SARIF, not just logs. Use it to validate repo controls that file scanning cannot prove.

`HLT-047-EXTERNAL-SECURITY-POSTURE-UNVERIFIED`
Max score: 82
Trigger: no Scorecard or equivalent external repo-security posture evidence.

### 10. Repository settings need API-backed evidence

A file audit cannot prove:

* Branch protection/rulesets.
* Required status checks.
* Required CODEOWNERS review.
* Admin bypass settings.
* Direct-push restrictions.
* Secret scanning and push protection.
* Dependabot alerts/settings.

The repo has CODEOWNERS entries. Evidence: `.github/CODEOWNERS` exists, and README points to private vulnerability reporting. But file presence is not the same as enforcement.

**Fix:** add a `jankurai repo-controls verify` command that uses `gh api` or GitHub REST/GraphQL to write:

`target/jankurai/repo-controls/evidence.json`

The artifact should include protected branches/rulesets, required checks, required reviews, CODEOWNERS enforcement, bypass actors, Actions settings, Dependabot/security settings, and private vulnerability reporting status.

Max score: 82

### 11. Badge claims are not fully replayable from the tarball

The tarball contains `agent/jankurai-badge.json` with score `100`, decision `pass`, and `source_report: "agent/repo-score.json"`. Evidence: `agent/jankurai-badge.json:1-21`.

But `agent/repo-score.json` is absent in the tarball, and `.gitignore` explicitly ignores `agent/repo-score.json` and `agent/repo-score.md`. Evidence: `.gitignore:19-22`.

That creates a replayability gap: the public badge points to a source report not present in the source tree. This may be intentional if CI artifacts are the source of truth, but then the badge should point to a score-history ledger entry or CI artifact identity, not an ignored local file.

**Fix:** make badge generation verify its source:

* If source report is ignored, badge must reference a signed ledger row or CI artifact URL/run ID.
* Badge should include `report_fingerprint`, `input_fingerprint`, `git_head`, `dirty_worktree`, `evidence_maturity`, and `self_audit`.
* CI should run `jankurai badge verify`.

Add:

`HLT-049-BADGE-SOURCE-MISSING-OR-STALE`
Max score: 75
Trigger: badge source report is missing, stale, advisory-mode, dirty, or not fingerprint-linked.

### 12. Dirty worktree can still pass

The report records `dirty_worktree`. Evidence: `crates/jankurai/src/audit/mod.rs:163-174`.

But pass/fail only uses score and high/critical findings. Evidence: `crates/jankurai/src/audit/mod.rs:346-365`.

The score history shows `dirty_worktree=true` with pass and 100/100 entries. Evidence: `agent/score-history.csv:34-36`.

For local advisory this is fine. For a published badge, release score, or protected-branch score, a dirty worktree must block.

Max score: 80, release block

### 13. Self-audit is bypassed by default for Jankurai itself

The runtime surface classifier excludes `crates/jankurai/` unless `--self-audit` is set. Evidence: `crates/jankurai/src/audit/helpers.rs:734-760`.

It also excludes `packages/ux-qa/` unless `--self-audit` is set. Evidence: `crates/jankurai/src/audit/helpers.rs:769`.

The CLI has `--self-audit`, but it is false by default. Evidence: `crates/jankurai/src/main.rs:260-294`, `crates/jankurai/src/main.rs:2060-2067`.

There is a `just self-audit` target, but the main CI workflow does not run or upload it. Evidence: `Justfile:45-46`, `.github/workflows/jankurai.yml:32-145`.

This is understandable for adopter repos, but for **Jankurai auditing Jankurai**, the public score should be a self-audit score. Otherwise the tool’s biggest Rust and TypeScript surfaces are mostly outside product scoring.

**Fix:** generate two scores:

* `agent/repo-score.json`: adopter-mode score.
* `target/jankurai/self-audit.json`: audit-the-auditor score.

For this repo’s badge, use the stricter self-audit score.

Add:

`HLT-051-SELF-AUDIT-BYPASS-FOR-AUDITOR-REPO`
Max score: 80
Trigger: a repo containing the auditor implementation publishes a score without `--self-audit`.

### 14. Large-file/code-shape policy is not strong enough in self-audit mode

The rubric says mega files should split before 500 LOC and preferably under 300 LOC; mega functions should stay under 80 LOC by default. Evidence: `docs/audit-rubric.md:24-37` describes code shape, and the “Known Vibe-Coding Insults” section defines mega-file/mega-function repair expectations.

The tarball contains very large Rust files:

* `crates/jankurai/src/main.rs`: ~2318 LOC.
* `crates/jankurai/src/audit/scan.rs`: ~1740 LOC.
* `crates/jankurai/src/commands/rust.rs`: ~1627 LOC.
* `crates/jankurai/src/audit/mod.rs`: ~1560 LOC.
* `crates/jankurai/src/commands/proof.rs`: ~1481 LOC.

This is exactly the locality problem Jankurai is designed to fight: agents patch the wrong area, reviewers lose ownership boundaries, and detector code becomes hard to reason about.

**Fix:** in `--self-audit` and HL3 mode, make shape caps apply to the auditor itself. Split:

* CLI argument parsing from command execution.
* report construction from findings.
* scanner families into rule-specific modules.
* language detectors into per-rule modules or generated catalogs.
* long tests into fixture tables plus focused assertions.

Add:

`HLT-052-MEGA-AUDITOR-SURFACE`
Max score: 85 initially, then 78 after migration window
Trigger: auditor-owned runtime files exceed configured LOC limits without decomposition exception.

### 15. AppleDouble sidecar files are present in the uploaded package

The uploaded tarball contains **973 AppleDouble `._*` files**, including files under `.github`, `.agents`, `.cursor`, and root metadata. `.gitignore` ignores `.DS_Store` but not `._*`. Evidence: `.gitignore:1-28`.

This matters because release/source packages should not contain platform metadata, hidden sidecars, editor swap files, or accidental binary/resource forks. It can also pollute scanners and confuse ownership/test maps.

**Fix:**

* Add `._*` to `.gitignore`.
* Add package hygiene scanner for `._*`, `.DS_Store`, `Thumbs.db`, `.swp`, `.bak`, `*.orig`, `.env`, `.npmrc`, `.pypirc`, `.netrc`, key material, crash logs, screenshots, and local caches.

* Add `jankurai package audit` that inspects `cargo package --list`, `npm pack --dry-run --json`, Docker build context, and release tarballs.

Add:

`HLT-053-PACKAGE-HYGIENE-GAP`
Max score: 78
Trigger: source/release package contains OS sidecars, editor artifacts, ignored build directories, secrets, or unreviewed generated outputs.

### 21. Evidence maturity should cap the maximum possible score

Right now a marker-detected lane and an artifact-verified lane can look too similar. Introduce score ceilings:

| Evidence maturity   | Meaning                                                 |  Suggested max score |
| ------------------- | ------------------------------------------------------- | -------------------: |
| `none`              | no config/evidence                                      | 60–75 depending risk |
| `configured`        | config or command text exists                           |                   82 |
| `ci_detected`       | CI command exists                                       |                   88 |
| `artifact_uploaded` | artifact uploaded                                       |                   92 |
| `artifact_verified` | schema-valid, current commit, strict, no skipped tools  |                   97 |
| `attested_external` | signed/attested artifact plus repo-control/API evidence |                  100 |

This prevents a 100/100 score from being reached by textual presence alone.

## Supply-chain and release gaps

### 25. SBOM is generated only advisory and not uploaded

OWASP SCVS treats SBOM, build environment, package management, component analysis, and pedigree/provenance as separate supply-chain control families. ([OWASP SCVS][9])

**Fix:** for released artifacts:

* Generate checksums.
* Generate SBOM.
* Generate provenance attestation.
* Sign/attest with GitHub artifact attestations or Sigstore/cosign.

`HLT-061-PROVENANCE-ATTESTATION-GAP`

### 27. Container/Docker attestation coverage should be explicit

If this standard is meant to cover Docker, add Docker-specific release gates. `HLT-062-CONTAINER-PROVENANCE-SCAN-GAP`

## Language-specific audit coverage to add

### Rust

Current Rust bad-behavior coverage is useful, but world-class Rust auditing should add:

1. **Mandatory fmt/clippy/test coverage.** See above.
2. **Unsafe inventory:** every `unsafe` block/function gets owner, reason, invariant, safety docs, tests, and optional Miri/fuzz proof.
3. **Panic policy:** no `unwrap`, `expect`, `panic`, indexing, integer overflow, or `todo!` in product/runtime except typed boundary or tests.
4. **Async/concurrency policy:** detect unbounded tasks, unbounded channels, detached tasks, missing cancellation, missing timeouts, blocking in async.
5. **Error shape:** require typed errors across boundaries, not `anyhow` leaking into API/domain surfaces.
6. **Serde/deserialization:** deny untagged enums for untrusted input unless reviewed; require schema/version tests.
7. **Path/filesystem safety:** canonicalization, symlink race avoidance, temp file safety, no path traversal sinks.
8. **Command execution safety:** no shell strings; use argv arrays; allowlist binaries; no user-controlled args without schema.
9. **Crypto policy:** no weak algorithms, custom crypto, insecure randomness, or token comparison without constant-time where applicable.
10. **Resource exhaustion:** input size limits, recursion limits, regex safety, parser budget, backpressure.

Smart rollout: make these **detector-backed advisory** first. Promote to hard only for `crates/domain`, `crates/application`, `crates/api`, security tools, and release tooling.

### TypeScript / Vite / React

Current TypeScript rules catch some bad behavior, but add:

1. Require root/workspace `typecheck`.
2. Require `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`; flag `skipLibCheck` as advisory unless justified. The UX package has strict options but also `skipLibCheck: true`. Evidence: `packages/ux-qa/tsconfig.json:1-20`.
3. ESLint/Biome with security rules.
4. No `dangerouslySetInnerHTML` without sanitizer and tests.
5. No unsafe `innerHTML`, `eval`, dynamic script injection.
6. No broad `any` at API boundaries.
7. Generated client enforcement: no handwritten DTO/fetch wrappers for contract surfaces.
8. Runtime schema validation for untrusted API/tool outputs.
9. React accessibility rules: labels, keyboard, focus order, no pointer-only controls.
10. Dependency policy for package publish: exact runtime deps where possible, lockfile verified, `npm pack --dry-run` scanned. `@jankurai/ux-qa` publishes `dist` only, which is good, but dependency `axe-core` uses a caret range. Evidence: `packages/ux-qa/package.json:15-27`.

### Python

Jankurai’s Python containment philosophy is strong, but if Python exists, add:

1. `ruff check`, `ruff format --check`.
2. `mypy` or `pyright`.
3. `bandit` or Semgrep Python security.
4. `pip-audit`/`uv pip audit`/`osv-scanner`.
5. Lockfile required: `uv.lock`, `requirements.lock`, or equivalent.
6. No direct production DB ownership unless specifically allowed under `python/ai-service`.
7. No pickle/yaml unsafe loads.
8. No `subprocess(..., shell=True)` with dynamic input.
9. HTTP calls require timeouts and TLS verification.
10. PII/redaction policy for prompts, logs, vector stores, transcripts, and eval data.

### SQL / PostgreSQL

Existing SQL rules should expand significantly:

1. Migration checksum ledger: forbid editing applied migrations.
2. Migration replay lane on fresh DB.
3. Expand/contract migration policy.
4. `lock_timeout` / `statement_timeout` for risky migrations.
5. Concurrent index creation where applicable.
6. Backfill batching and idempotency.
7. Rollback/down plan or explicit irreversible approval.
8. RLS evidence for tenant/owner tables.
9. Constraint evidence for durable invariants.
10. No `SECURITY DEFINER` without fixed `search_path`.
11. No broad grants to `public`.
12. No seed secrets/PII.
13. No destructive DDL without rehearsal artifact.
14. SQL parser-backed detection instead of only line-oriented detection.

### Docker

Existing Docker bad-behavior rules are a good base. Add:

1. Base image digest pinning.
2. Non-root runtime user.
3. Minimal runtime image.
4. `HEALTHCHECK` where service-like.
5. No secrets in `ARG`/`ENV`.
6. BuildKit secret mounts for build secrets.
7. `.dockerignore` required.
8. No `ADD` remote URLs.
9. No `curl | sh`.
10. Trivy/Grype/Docker Scout scan.
11. SBOM + provenance attestations.
12. Read-only root filesystem/capability policy for compose/k8s if present.

### Git / Git tools

Existing Git/Gittools rules should add:

1. Signed commits/tags policy for release mode.
2. Protected tags or tag immutability evidence.
3. No force-push capable release automation.
4. No `git config --global` mutations in scripts unless isolated.
5. No `git submodule update` without pinned commit and allowed URL policy.
6. No hidden hooks installed from unreviewed paths.
7. No bypassing hooks in release/CI scripts.

### CI

## Smart rollout plan that should not break adopters

### Phase 0: fix clear self-contained issues immediately

These are low-risk:

* Add `._*` to `.gitignore`.
* Remove AppleDouble files from packages/tarballs.
* Add final audit as the last CI step.
* Stop generating ratchet baseline from the same run.
* Upload SBOM if generated.
* Run `vibe validate`.
* Add top-level `permissions: contents: read`.
* Add `timeout-minutes` and artifact `retention-days`.
* Add `jankurai badge verify`.

### Phase 1: evidence maturity without hard blocking

Add evidence maturity fields and warnings:

* `security.wrapper_strict=false`
* skipped security commands
* missing SARIF upload
* missing Scorecard
* non-SHA action refs
* missing repo-controls API artifact
* stale badge/source report
* dirty worktree public score

Do not cap scores yet except for self-audit/public badge mode.

### Phase 2: make release/HL3 stricter than advisory mode

Add profile-specific enforcement:

| Mode              | Behavior                                                     |
| ----------------- | ------------------------------------------------------------ |
| `observe`         | no fail, emits gaps                                          |
| `advisory`        | no fail, no public badge allowed                             |
| `ratchet`         | fail on regressions and high/critical                        |
| `release` / `HL3` | strict evidence, no stale/skipped/non-attested public claims |

### Phase 3: promote the strongest gaps to hard caps

Hard-cap only high-confidence, low-false-positive issues first:

* Final audit not last.
* False ratchet baseline.
* Non-strict security CI.
* Skipped required security tool.
* Missing badge source.
* Dirty public score.
* Workflow non-SHA action refs.
* Missing explicit token permissions.
* SARIF generated but not uploaded.
* Spec/implementation drift.

### Phase 4: deepen semantic proof

Then add heavier obligations:

* Authz matrix.
* Input-boundary taint proof.
* Rust unsafe inventory.
* SQL migration replay/RLS.
* Docker provenance.
* AI/model/prompt/eval drift.
* Human review API receipts.

## Bottom line

Jankurai is already excellent at defining what “non-vibe” should mean. The biggest missing best practice is making the score **evidence-terminal**: the score must be generated last, from strict current artifacts, with no self-baselining, no skipped tools, no marker-only credit, no dirty public claims, no self-audit bypass, and no unverified repo controls.

The path to “best available standard” is:

1. **Final score last.**
2. **Strict security evidence.**
3. **Real ratchet baseline.**
4. **SHA-pinned and least-privilege CI.**
5. **SAST/SARIF/code scanning.**
6. **Scorecard + repo controls API evidence.**
7. **SBOM + provenance + attestation.**
8. **Self-audit for Jankurai itself.**
9. **Spec/code/schema parity.**
10. **Proof obligation coverage instead of marker presence.**

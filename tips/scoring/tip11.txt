I unpacked `/mnt/data/jankurai.tar(1).gz` and treated it as the source of truth. I inspected the audit scorer, caps, rule registry, scanners, schemas, proofbind/proofmark crates, security wrapper, CI workflow, composite action, policy/config files, docs, and language detector packs. # Executive assessment

Jankurai is already doing something unusually valuable: it is not just “linting,” it is trying to make codebases agent-safe by forcing ownership, proof routing, caps, evidence artifacts, repair queues, generated-boundary discipline, anti-placeholder rules, and language-specific bad-behavior packs. That is the right direction for “kill vibe coding.”

The main gap is not lack of ideas. The main gap is that the current scoring path still over-credits **presence of controls** instead of verifying **fresh, current-commit, policy-bound evidence**. A world-class version should score every control at one of four levels:

| Level        | Meaning                                                                                   | Scoring treatment            |
| ------------ | ----------------------------------------------------------------------------------------- | ---------------------------- |
| `declared`   | Repo mentions a control or command.                                                       | Small advisory credit only.  |
| `configured` | Machine-readable config exists and validates.                                             | Moderate credit.             |
| `executed`   | Lane ran on the audited commit and emitted artifacts.                                     | Strong credit if successful. |
| `verified`   | Artifacts are fresh, hashed, schema-valid, commit-bound, command-bound, and score-gating. | Full credit.                 |

Right now, many dimensions are closer to `declared/configured`; the next jump is to make `executed/verified` the scoring standard.

NIST SSDF 1.1 frames secure development around reducing vulnerabilities, mitigating impact, and addressing root causes; NIST has also published SSDF 1.2 as an initial public draft focused on improved secure and reliable development/delivery practices. Jankurai should map its HLT rules to SSDF-style practices so its output can be both agent-native and standards-legible. ([NIST][1])

# What Jankurai is trying to do, as I understand it

The project is trying to build a **codebase governance engine for AI-assisted development**:

1. Keep agents from guessing by giving them ownership maps, test maps, proof lanes, concise instructions, and local context.
2. Keep product code from drifting into “vibe code” through TODOs, fallback soup, weak names, generated-code mutation, hidden Python product truth, wrong-layer DB access, and unproved UX/security behavior.
3. Convert code quality into a **scored, capped, machine-readable audit report** with findings and an `agent_fix_queue`.
4. Replace “trust me” review with receipts, artifacts, proof lanes, evidence hashes, repair queues, and CI gating.
5. Make Rust/TypeScript/Postgres/generated contracts the preferred durable surface, with Python boxed into rare ML/data exceptions.

That mission is strong. The improvements below are about making the scorer harder to game, safer to adopt, and closer to “world-class merge standard.”

# Highest-priority current audit gaps

## P0. Proof receipts are not score-gating

In `crates/jankurai/src/audit/mod.rs`, `run_audit_timed_with_options` computes dimensions, raw score, caps, final score, findings, agent fix queue, decision, conformance summary, and git summary before loading `proof_receipts`.

The key sequence is:

```text
crates/jankurai/src/audit/mod.rs:132-144  dimensions, raw_score, caps, final_score
crates/jankurai/src/audit/mod.rs:149-160  findings and decision
crates/jankurai/src/audit/mod.rs:165      proof_receipts loaded
crates/jankurai/src/audit/mod.rs:206      proof_receipts attached to report
```

That means proof receipts can appear in the final JSON report without actually affecting the score, caps, findings, or pass/fail decision.

### Fix

Load and validate proof receipts **before** dimensions/caps/final decision. Add a `ProofEvidenceSummary` that participates in `caps_applied`, `build_findings`, and `report_decision`.

Required receipt validations:

| Field                                             | Required scoring behavior                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| `exit_code`                                       | Must be `0` for a positive proof.                                              |
| `git_head`                                        | Must equal audited `git.head`.                                                 |
| `dirty_worktree`                                  | Must be false, or explicitly policy-accepted with residual risk.               |
| `command_digest`                                  | Must match the planned lane command.                                           |
| `plan_digest`                                     | Must match current proof plan.                                                 |
| `artifact_digests`                                | Every claimed artifact must exist and match SHA-256.                           |
| `log_sha256`                                      | Log path must exist and match hash.                                            |
| `rules_covered`                                   | Must cover the rule IDs required by the changed surface.                       |
| `changed_paths`                                   | Must cover the changed files being claimed. Empty should not mean “all paths.” |
| `generated_at/started_at/finished_at`             | Must be inside CI run window and not stale.                                    |
| `standard_version/auditor_version/schema_version` | Must match or be explicitly compatible.                                        |
| `run_id`                                          | Must match the audit run or trusted upstream run.                              |

### New cap

```text
proof-receipts-not-score-gating -> max_score 50
stale-or-unbound-proof-receipt -> max_score 65
proof-receipt-git-head-mismatch -> max_score 55
proof-receipt-artifact-digest-missing -> max_score 70
proof-receipt-command-digest-missing -> max_score 72
```

This is the biggest gap because it changes the meaning of “proof” from “reported evidence” to “decision evidence.”

## P0. Ratchet mode can self-baseline in CI

The workflow currently generates a baseline from the same checkout and then runs ratchet mode against that fresh baseline:

```text
.github/workflows/jankurai.yml:32-36  Generate CI ratchet baseline
.github/workflows/jankurai.yml:37-38  Run jankurai audit with that baseline
```

That makes the ratchet less meaningful. Ratchet should compare a PR/head to an accepted prior baseline, not to itself.

`apply_mode_and_baseline` also only reads `score` from the baseline JSON:

```text
crates/jankurai/src/main.rs:2286-2296
```

It does not verify baseline commit, schema version, standard version, auditor version, input fingerprint, policy fingerprint, caps, hard findings, artifact digest, or whether the baseline came from the protected base branch.

### Fix

A ratchet baseline should be accepted only when:

```text
baseline.git.head == protected base commit or trusted release artifact
baseline.policy_fingerprint matches or is explicitly migrated
baseline.standard_version/auditor_version/schema_version are compatible
baseline.input_fingerprint is signed or trusted
baseline.report_fingerprint verifies
baseline.caps_applied and hard findings are compared, not only score
```

### New cap

```text
ci-self-baselining-ratchet-gap -> max_score 50
ratchet-baseline-untrusted -> max_score 60
ratchet-baseline-version-mismatch -> max_score 72
ratchet-score-only-comparison -> max_score 76
```

Score-only ratchets miss the most important regressions: a score can stay flat while a new critical cap appears.

## P0. Proofbind treats empty `changed_paths` and empty `rules_covered` as broad proof

In `crates/jankurai-proofbind/src/receipts.rs`, `receipt_satisfies` accepts a receipt when:

```text
receipt.changed_paths.is_empty() || changed path matches
receipt.rules_covered.is_empty() || rule intersects
```

Specifically:

```text
crates/jankurai-proofbind/src/receipts.rs:84-99
```

This means an empty `changed_paths` or empty `rules_covered` can satisfy too much. For proof systems, “empty” should usually mean “unknown,” not “all.”

### Fix

Change semantics:

```text
empty changed_paths = invalid for changed-surface proof
empty rules_covered = invalid when surface.required_rules is non-empty
```

Allow broad receipts only when they explicitly claim:

```json
"scope": "full-repository",
"covers_all_paths": true,
"covers_all_rules": true,
"artifact_digests": [...]
```

### New cap

```text
proofbind-empty-changed-paths-broad-proof -> max_score 65
proofbind-empty-rules-covered-broad-proof -> max_score 68
```

## P0. Proofmark lets unavailable mutation evidence pass

`crates/jankurai-proofmark/src/report.rs:68` treats mutation as OK when status is either `pass` or `unavailable`:

```rust
let mutation_ok = mutation.status == "pass" || mutation.status == "unavailable";
```

It records residual risk, but the obligation can still pass when coverage and negative proof pass.

Also, malformed mutation JSON is parsed as `{}`:

```text
crates/jankurai-proofmark/src/report.rs:239-249
```

Since `{}` yields survived=0 and timeout=0, malformed mutation evidence can become `pass`.

### Fix

Change mutation states:

| State         | Meaning                                                 | Required behavior                |
| ------------- | ------------------------------------------------------- | -------------------------------- |
| `pass`        | Valid mutation evidence, no survived/timed-out mutants. | Counts.                          |
| `review`      | Valid evidence with survived/timed-out mutants.         | Blocks required mode.            |
| `unavailable` | No mutation evidence supplied.                          | Review/advisory unless low-risk. |
| `invalid`     | Malformed or unreadable evidence.                       | High finding / hard cap.         |

For boundary-sensitive rules (`HLT-021` to `HLT-024`, authz, input, migration, agent tool supply), unavailable mutation should not pass in required mode.

### New cap

```text
malformed-mutation-evidence-counted-as-pass -> max_score 55
boundary-proof-without-mutation-evidence -> max_score 72
changed-line-coverage-unavailable-for-required-proof -> max_score 70
```

# The core scoring architecture improvement

## Add a first-class evidence verdict model

Add a scoring object like:

```rust
pub enum EvidenceLevel {
    Declared,
    Configured,
    Executed,
    Verified,
}

pub struct EvidenceVerdict {
    pub id: String,
    pub lane: String,
    pub level: EvidenceLevel,
    pub status: String, // pass, review, fail, stale, invalid, unavailable
    pub rule_ids: Vec<String>,
    pub paths: Vec<String>,
    pub git_head: Option<String>,
    pub dirty_worktree: Option<bool>,
    pub command: Option<String>,
    pub command_digest: Option<String>,
    pub artifacts: Vec<ArtifactDigest>,
    pub log_sha256: Option<String>,
    pub residual_risk: Vec<String>,
}
```

Then every scoring dimension should be able to ask:

```text
Does required evidence exist?
Was it executed?
Was it verified?
Does it cover this path/rule?
Is it fresh for this commit?
```

## Change scoring order

Current order:

```text
scan -> dimensions -> caps -> final score -> findings -> decision -> proof receipts
```

Target order:

```text
inventory
load configs
load/validate evidence artifacts
verify proof receipts
compute evidence verdicts
compute dimensions
compute caps from static + evidence verdicts
build findings
compute score
compute decision
render report
```

## Add cap confidence and rollout mode

Every cap should have:

```text
confidence: high | medium | low
mode_default: observe | advisory | ratchet | release
false_positive_risk: low | medium | high
applicability: repo profile predicates
```

This avoids causing issues. High-confidence deterministic checks can hard-cap. Pattern-only checks should usually start advisory.

# CI and GitHub audit gaps

## 1. Missing explicit `permissions`

The workflow has no top-level or job-level `permissions:` block. That means `GITHUB_TOKEN` behavior depends on repository/org defaults. World-class CI should explicitly request least privilege.

Suggested default:

```yaml
permissions:
  contents: read
```

Then add per-job grants only when needed:

```yaml
security-events: write   # SARIF upload
id-token: write          # attestations/OIDC
attestations: write      # artifact attestation
artifact-metadata: write # GitHub attest action
```

GitHub’s SARIF upload docs show `security-events: write`, `contents: read`, and sometimes `actions: read` for private repos. ([GitHub Docs][2])

### New cap

```text
github-token-permissions-unspecified -> max_score 78
workflow-job-overbroad-permissions -> max_score 72
```

## 2. Mutable GitHub Action references

The workflow uses references like:

```text
actions/checkout@v6
actions/setup-node@v6
actions/upload-artifact@v7
dtolnay/rust-toolchain@stable
```

The composite action uses:

```text
dtolnay/rust-toolchain@stable
```

GitHub’s secure-use guidance says pinning an action to a full-length commit SHA is the only way to use it as an immutable release; GitHub also recommends CODEOWNERS for workflow changes, OIDC instead of long-lived cloud secrets, Dependabot for action updates, and dependency review for workflow dependency changes. ([GitHub Docs][3])

### Smart rollout

Do not immediately hard-fail all tag refs for every adopting repo. Use modes:

| Mode     | Behavior                                                                                    |
| -------- | ------------------------------------------------------------------------------------------- |
| observe  | Report mutable refs only.                                                                   |
| advisory | Medium finding.                                                                             |
| ratchet  | High finding for third-party actions; local first-party reusable actions can be advisory.   |
| release  | Hard cap unless full SHA pinned or organization policy allows trusted publisher exceptions. |

### New cap

```text
third-party-action-not-sha-pinned -> max_score 75
release-workflow-action-not-sha-pinned -> max_score 65
mutable-toolchain-channel-in-release -> max_score 72
```

## 3. SARIF is generated but not uploaded to code scanning

`crates/jankurai/src/report/sarif.rs` emits SARIF 2.1.0, and workflow uploads `target/jankurai/jankurai.sarif` as an artifact. I did not see `github/codeql-action/upload-sarif`.

GitHub supports uploading third-party SARIF into code scanning, and GitHub uses `partialFingerprints` to prevent duplicate alerts. The upload action can calculate them when source code is present, but best practice is to emit stable fingerprints yourself when possible. ([GitHub Docs][2])

### Fix

Add:

```yaml
- name: Upload Jankurai SARIF
  uses: github/codeql-action/upload-sarif@<full-sha>
  with:
    sarif_file: target/jankurai/jankurai.sarif
    category: jankurai
```

Add SARIF fields:

```json
"partialFingerprints": {
  "primaryLocationLineHash": "...",
  "jankuraiFinding": "..."
}
```

### New cap

```text
sarif-generated-but-not-uploaded -> max_score 80
sarif-missing-partial-fingerprints -> max_score 85
sarif-rule-metadata-incomplete -> max_score 88
```

## 4. No artifact attestation/provenance enforcement

Jankurai has artifact digests, report fingerprints, and public evidence ideas, but GitHub release/public artifacts should be attested. GitHub artifact attestations create signed provenance claims that include workflow, repository, organization, environment, commit SHA, triggering event, and OIDC information; `actions/attest` requires `id-token: write`, `attestations: write`, and `artifact-metadata: write`. ([GitHub Docs][4])

SLSA v1.2 Build L1 requires provenance, L2 requires signed provenance from a hosted build platform, and L3 requires a hardened build platform. ([SLSA][5])

```text
attestation-not-verified-before-release -> max_score 70
```

# The biggest conceptual upgrade

Jankurai should become an **evidence verifier**, not just a **repository scanner**.

The best version of this system says:

```text
This repo claims it is safe for agent-assisted work.
Here are the exact controls that apply.
Here is what was declared.
Here is what was configured.
Here is what ran.
Here is what was verified.
Here is what caps the score.
Here is the smallest safe repair queue.
Here is the evidence digest that makes this report reproducible.
```

That is the standard that will actually kill vibe coding: not more lint noise, but fewer places for unproved claims to hide.

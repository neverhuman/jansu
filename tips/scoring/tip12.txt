Below is the report I would give the maintainers after reviewing the uploaded repository tree.

I reviewed this as an **audit-of-the-auditor**: the scoring model, rules, schemas, CI workflow, proof receipts, witness logic, Rust implementation, TypeScript/Vite package, Python allowance, Docker/SQL rules, security lane, agent policies, generated-zone policies, docs, and release posture.

# Executive summary

Jankurai is already aiming at the right thing: **kill vibe coding by making code changes evidence-bound, policy-bound, owner-bound, and repairable.** The existing rubric, hard caps, generated-zone model, proof lanes, repair queue, language bad-behavior rules, and anti-agent-boundary concepts are strong.

The biggest missing layer is **assurance of the assurer**.

Right now, the repository has many good audit ideas, but the score can still look stronger than the evidence because:

1. **The CI ratchet baseline is generated from the candidate run.** That makes the regression gate much easier to game.
2. **Fresh proof/security/UX evidence is generated after the audit score in the main workflow.** The score can therefore miss the evidence it is supposed to evaluate.
3. **Security is not strict in the main CI lane.**
4. **Proof receipts are treated too much like declarations, not commit-bound attestations.**
5. **The report lacks deep coverage metadata: skipped files, parser failures, truncation, unsupported languages, generated/vendor exclusions, tool versions, detector confidence, and standards mapping.**
6. **The audit engine itself violates some of its own “shape” ideals with very large core files, without a visible exception mechanism.**
7. **The repo has AppleDouble `._*` sidecar files from the uploaded archive, and `.gitignore` does not ignore them.** That is a real archive/release hygiene gap and could break TypeScript globs if committed.
8. **The tool needs a calibration corpus and detector accuracy reporting.** World-class audit tools prove not only that rules exist, but that rules catch known-bad code and avoid punishing known-good code.
9. **Release/security supply-chain controls need to move from “documented/advisory” to “strictly evidenced” for top scores.**
10. **The custom rubric needs an external control map** to NIST SSDF, OWASP ASVS, OWASP Code Review, SLSA, OpenSSF Scorecard, CWE, and language-specific guidance. NIST SSDF is designed to help reduce software vulnerabilities across the SDLC, OWASP ASVS provides verifiable application security requirements, and OWASP’s code review guidance covers vulnerabilities that automated tools often miss. ([NIST Computer Security Resource Center][1])

The repo is on a good path. The next step is to make every score point traceable to **fresh, independently verifiable, standards-mapped, commit-bound evidence**.

# What Jankurai is trying to become

My read is that Jankurai is not just a linter. It is trying to be a **local, agent-aware, evidence-first engineering quality standard**.

The core philosophy appears to be:

* Stop AI-generated “looks plausible” code from entering real systems.
* Force code to have ownership, contracts, tests, proof, security checks, and clear repair paths.
* Penalize vague TODOs, fallback soup, dead code, unsafe defaults, contract drift, generated-zone edits, direct DB misuse, prompt-injection surfaces, secret leakage, and false-green tests.
* Give humans and agents a shared scorecard for whether a repo is actually production-worthy.
* Work across Rust, TypeScript/Vite, SQL, Docker, Python exceptions, CI, Git, release, and generated contracts.

That is the right north star.

The missing work is mostly not “add 500 more grep rules.” The missing work is:

```text
Make the audit itself hard to lie to.
Make the score explain exactly what it did and did not check.
Make strict evidence happen before scoring.
Make proof receipts fresh and tamper-evident.
Make standards coverage explicit.
Make detectors calibrated.
Make release and CI supply chain verifiable.
```

# P0 audit/scoring gaps

## 1. The CI ratchet baseline is generated from the candidate commit

In `.github/workflows/jankurai.yml`, the workflow first generates:

```sh
cargo run -p jankurai -- . --json agent/repo-score.json --md agent/repo-score.md
cp agent/repo-score.json target/jankurai/baseline-score.json
```

Then it runs ratchet mode against that copied baseline:

```sh
cargo run -p jankurai -- audit . \
  --mode ratchet \
  --baseline target/jankurai/baseline-score.json
```

That means the candidate is effectively compared against itself.

For a world-class audit gate, this should be a **release-blocking flaw**. Ratchets only work when the baseline is a trusted prior state: protected `main`, a signed artifact, an immutable release artifact, or a separately approved baseline file.

Recommended hard cap:

```text
audit.ratchet_baseline_from_candidate
severity: critical
cap: 45
blocks_release: true
condition:
  The ratchet baseline is generated from the same candidate tree being judged.
```

Correct behavior:

```text
PR candidate score >= protected-main accepted baseline score
```

Not:

```text
PR candidate score >= PR candidate score
```

Safer implementation options:

```sh
# Option A: Use committed baseline from protected main
git fetch origin main
git show origin/main:agent/repo-score.json > target/jankurai/baseline-score.json

# Option B: Download prior successful protected-main artifact
# Verify artifact provenance, commit SHA, branch, and signature.

# Option C: Release baseline
# Use immutable release artifact + attestation.
```

Also add a schema-level rule:

```json
{
  "baseline": {
    "source": "protected-main|signed-release|attested-artifact",
    "git_head": "...",
    "tree_hash": "...",
    "created_by": "...",
    "verified": true,
    "same_as_candidate": false
  }
}
```

## 2. The main workflow scores before generating security/proof/UX evidence

The main CI workflow currently runs the audit early, then later runs proof/security/UX evidence steps. That ordering weakens the score.

A score should be produced **after** the evidence it evaluates exists.

Current problematic order:

```text
audit score
proofbind
proofmark
rust witness
UX QA
security lane
vibe coverage
merge witness
```

Better order:

```text
checkout/setup
format/lint/test/build
security strict
dependency/supply-chain checks
proofbind/proofmark/witness
UX QA against real product routes
vibe coverage
final audit score
merge witness
upload artifacts
```

Recommended hard cap:

```text
audit.evidence_generated_after_score
severity: critical
cap: 60
blocks_release: true
condition:
  The final score is produced before required evidence artifacts are generated.
```

This matters because the audit loader reads existing evidence files such as security and UX artifacts. If those are created after scoring, the score either sees nothing or sees stale local artifacts.

## 3. Security is advisory in CI where it should be strict

The workflow runs:

```sh
cargo run -p jankurai -- security run . --out target/jankurai/security
```

It does not pass `--strict`.

Your docs and matrix already point toward strict release security, but top-level CI should be clearer:

```text
local developer loop: advisory allowed
PR on normal paths: targeted strict checks
PR touching high-risk paths: strict required
protected main: strict required
release: strict + SBOM + provenance + signatures + vuln threshold
```

Recommended hard cap:

```text
ci.nonstrict_security_on_protected_branch
severity: high
cap: 70
blocks_release: true
condition:
  Protected branch or release CI runs the security lane without strict mode.
```

The security lane should also stop treating only `gitleaks` as a required tool. For world-class coverage, protected branch/release strict mode should require, at minimum:

```text
gitleaks
cargo audit / RustSec
cargo deny
npm audit or better package-audit equivalent
GitHub dependency review on PRs
zizmor
actionlint
Syft SBOM
Grype or Trivy vulnerability scan
Semgrep or CodeQL
OpenSSF Scorecard
release signature / attestation verification
```

RustSec is the maintained advisory database for Rust crates, and `cargo-deny` can check advisories against that data. GitHub’s dependency review action is specifically designed to inspect dependency changes and catch vulnerable versions introduced in pull requests. ([RustSec][2])

## 4. CI does not run a full one-command quality gate

The `Justfile` default/check path is too weak for a repo claiming top audit quality. It runs audit/version/paper-related commands, but not the full quality gate.

A best-standard gate should include:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo test --doc --workspace --locked
npm ci
npm --workspace @jankurai/ux-qa run build
npm --workspace @jankurai/ux-qa run test
jankurai security run . --strict --out target/jankurai/security
jankurai audit . --mode ratchet --baseline target/jankurai/baseline-score.json
jankurai witness .
```

Recommended hard cap:

```text
ci.no_single_world_class_verification_command
severity: high
cap: 82
condition:
  There is no canonical command that runs formatting, linting, tests, security, proof, audit, and witness.
```

Recommended new command:

```make
verify-world-class:
    cargo fmt --all -- --check
    cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
    cargo test --workspace --all-targets --locked
    cargo test --doc --workspace --locked
    npm ci
    npm --workspace @jankurai/ux-qa run build
    npm --workspace @jankurai/ux-qa run test
    cargo run -p jankurai -- security run . --strict --out target/jankurai/security
    cargo run -p jankurai -- conformance run --out target/jankurai/conformance
    cargo run -p jankurai -- audit . \
      --mode ratchet \
      --baseline target/jankurai/baseline-score.json \
      --json target/jankurai/repo-score.json \
      --md target/jankurai/repo-score.md
    cargo run -p jankurai -- witness . \
      --score target/jankurai/repo-score.json \
      --baseline target/jankurai/baseline-score.json \
      --json target/jankurai/merge-witness.json \
      --md target/jankurai/merge-witness.md
```

## 5. GitHub Actions are not pinned to immutable SHAs

The workflow and composite action use version tags like:

```yaml
actions/checkout@v6
dtolnay/rust-toolchain@stable
actions/setup-node@v6
actions/upload-artifact@v7
```

Tags can move. For high-assurance CI, third-party actions should be pinned to full-length commit SHAs, with a tool-managed update process. GitHub’s own guidance says pinning to a full-length commit SHA is the only way to use an action as an immutable release, and OpenSSF Scorecard includes checks for pinned dependencies and token permissions. ([GitHub Docs][3])

Recommended hard cap:

```text
ci.unpinned_third_party_actions
severity: high
cap: 75
condition:
  Third-party GitHub Actions are referenced by tag or branch instead of full commit SHA.
```

Safer pattern:

```yaml
- uses: actions/checkout@<full-length-commit-sha>
- uses: dtolnay/rust-toolchain@<full-length-commit-sha>
- uses: actions/setup-node@<full-length-commit-sha>
```

Also add a bot/process for digest updates:

```text
updatebot proposes SHA updates
CI verifies source repository/tag correspondence
human reviewer approves
```

## 6. Workflow permissions are not strict enough by default

The generated CI template has some job-level `permissions: contents: read`, but the main workflow should enforce top-level least privilege and job-specific escalation.

GitHub recommends controlling the `GITHUB_TOKEN` permissions, and the token is repo-scoped. OpenSSF Scorecard also checks whether workflows use read-only token permissions. ([GitHub Docs][4])

Recommended hard cap:

```text
ci.missing_top_level_readonly_permissions
severity: high
cap: 80
condition:
  Workflow lacks top-level read-only GITHUB_TOKEN permissions.
```

Recommended baseline:

```yaml
permissions:
  contents: read
```

Then only escalate in specific jobs that need it:

```yaml
permissions:
  contents: read
  id-token: write # only for artifact attestations/provenance
```

## 7. Proof receipts are under-bound

The proof receipt schema has the right idea, but strict/release mode should require more fields.

Currently, a receipt can be useful even if it has little more than:

```json
{
  "lane": "...",
  "command": "...",
  "exit_code": 0,
  "elapsed_ms": 123,
  "artifacts": []
}
```

For best-standard evidence, proof receipts should be bound to:

```json
{
  "git_head": "...",
  "tree_hash": "...",
  "dirty_worktree": false,
  "ci_run_id": "...",
  "actor": "...",
  "started_at": "...",
  "finished_at": "...",
  "command": "...",
  "command_digest": "...",
  "exit_code": 0,
  "stdout_hash": "...",
  "stderr_hash": "...",
  "log_hash": "...",
  "artifact_digests": [],
  "rules_covered": [],
  "changed_paths": [],
  "tool_versions": {},
  "environment": {
    "os": "...",
    "arch": "...",
    "network": "disabled|restricted|allowed",
    "container_image_digest": "..."
  },
  "signature": "...",
  "attestation": "..."
}
```

Recommended hard cap:

```text
evidence.stale_or_unbound_proof_receipts
severity: high
cap: 78
blocks_release: true
condition:
  Proof receipts are not bound to candidate git head, tree hash, command digest, logs, artifacts, and CI identity.
```

For release artifacts, SLSA provenance and GitHub artifact attestations are directly relevant because they are designed to provide provenance and integrity guarantees for built artifacts. npm also supports provenance statements for packages, establishing where a package was built and who published it. ([SLSA][5])

## 8. Merge witness accepts receipts too generously

The witness logic currently accepts successful receipts too easily. A receipt with `exit_code == 0` can satisfy obligations without enough freshness and scope evidence.

High-assurance witness logic should require:

```text
receipt.git_head == current candidate git head
receipt.tree_hash == current tree hash
receipt.dirty_worktree == false
receipt.changed_paths covers affected files
receipt.rules_covered covers required rule family
receipt.command_digest matches approved command
receipt.artifact_digests verified for every artifact
receipt.tool_versions captured
receipt.created during this CI run or an approved prior run
```

Recommended hard caps:

```text
evidence.receipt_without_changed_paths
severity: high
cap: 80

evidence.receipt_without_rules_covered
severity: high
cap: 80

evidence.receipt_head_mismatch
severity: critical
cap: 50
blocks_release: true

evidence.receipt_dirty_worktree
severity: critical
cap: 55
blocks_release: true
```

The witness should be strict by default for protected branches and releases, with advisory leniency only in local development mode.

## 9. Malformed or missing baseline should fail closed

In audit/witness flows, baseline parsing appears to fall back to the current score in some cases. That is dangerous because a malformed baseline can self-pass.

Recommended behavior:

```text
advisory mode:
  malformed baseline => warning

ratchet mode:
  malformed baseline => fail

release mode:
  missing/malformed/unverified baseline => fail closed
```

Recommended hard cap:

```text
audit.malformed_baseline_self_pass
severity: critical
cap: 70
blocks_release: true
condition:
  Ratchet or witness mode silently treats an unreadable baseline as the current score.
```

## 13. Distinguish declared proof, observed proof, and attested proof

Reports should never treat all evidence equally.

Use an explicit evidence ladder:

```text
declared:
  config/docs claim something

observed-static:
  static detector saw code/config

observed-dynamic:
  command ran and produced artifact

attested:
  command/artifact is signed, provenance-bound, and verified

manual-reviewed:
  named human reviewed with checklist and timestamp
```

Suggested scoring:

```text
declared evidence can support at most medium confidence
observed-static can support medium/high depending on detector confidence
observed-dynamic can support high if fresh and reproducible
attested can support release-grade confidence
manual-reviewed can support logic/security exceptions if bounded and signed
```

Recommended hard cap:

```text
audit.declared_evidence_used_as_release_proof
severity: high
cap: 78
condition:
  Release-grade controls are satisfied by config/docs declarations without fresh observed or attested evidence.
```

# Smart rollout plan

To avoid causing issues, do not turn every new rule into a release blocker immediately. Add levels.

## Level model

```text
HL1 — advisory only
HL2 — score deduction
HL3 — cap for protected branches
HL4 — release blocker
HL5 — security-critical blocker
```

Example rollout:

```text
Week 1:
  Add report fields, warnings, detector fixtures.
  No hard failures except ratchet/evidence-order fixes.

Week 2:
  Enforce strict security on main.
  Add baseline provenance and receipt freshness warnings.

Week 3:
  Turn stale proof, candidate baseline, and unpinned action checks into caps.

Week 4:
  Release mode requires SBOM, provenance, signatures, strict security.

Later:
  Add deeper language-specific checks gradually with calibration corpus.
```

## Noise-control principles

Use these rules to avoid hurting developers:

```text
Do not fail on a new detector until it has fixtures.
Do not hard-cap without an escape hatch.
Every exception needs owner/reason/expiry.
Every finding needs a safe remediation.
Prefer path-sensitive strictness.
Prefer changed-code strictness before whole-repo strictness.
Separate local/advisory mode from protected/release mode.
Track false positives publicly.
```

# Concrete CI redesign

A better workflow shape:

```yaml
name: jankurai

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  audit:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@<full-length-sha>
        with:
          fetch-depth: 0
          persist-credentials: false

      - uses: dtolnay/rust-toolchain@<full-length-sha>
        with:
          toolchain: stable
          components: rustfmt, clippy

      - uses: actions/setup-node@<full-length-sha>
        with:
          node-version-file: .nvmrc
          cache: npm

      - name: Load protected baseline
        run: |
          mkdir -p target/jankurai
          git fetch origin main
          git show origin/main:agent/repo-score.json > target/jankurai/baseline-score.json

      - name: Rust quality
        run: |
          cargo fmt --all -- --check
          cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
          cargo test --workspace --all-targets --locked
          cargo test --doc --workspace --locked

      - name: TypeScript quality
        run: |
          npm ci
          npm --workspace @jankurai/ux-qa run build
          npm --workspace @jankurai/ux-qa run test

      - name: Strict security
        run: |
          cargo run -p jankurai -- security run . \
            --strict \
            --out target/jankurai/security

      - name: Proof lanes
        run: |
          cargo run -p proofbind -- verify --root . --out target/jankurai/proofbind.json
          cargo run -p proofmark -- rust --root . --out target/jankurai/proofmark-rust.json
          cargo run -p jankurai -- rust witness build \
            --root . \
            --out target/jankurai/rust-witness.json

      - name: UX QA
        run: |
          npm --workspace @jankurai/ux-qa run build
          # Start real app or documented fixture mode.
          # Then write target/jankurai/ux-qa.json.

      - name: Final audit score
        run: |
          cargo run -p jankurai -- audit . \
            --mode ratchet \
            --baseline target/jankurai/baseline-score.json \
            --json target/jankurai/repo-score.json \
            --md target/jankurai/repo-score.md

      - name: Merge witness
        run: |
          cargo run -p jankurai -- witness . \
            --score target/jankurai/repo-score.json \
            --baseline target/jankurai/baseline-score.json \
            --json target/jankurai/merge-witness.json \
            --md target/jankurai/merge-witness.md
```

# Immediate fixes I would make first

## Fix 1: Ratchet baseline

Stop generating the baseline from the candidate tree.

Use:

```sh
git fetch origin main
git show origin/main:agent/repo-score.json > target/jankurai/baseline-score.json
```

Then verify:

```text
baseline.git.head != candidate.git.head
baseline.source == protected-main or signed artifact
baseline schema valid
baseline score parse succeeds
```

## Fix 2: Move final audit after evidence

Generate security, proof, UX, and coverage artifacts first. Then run final audit.

## Fix 3: Make strict security required on main/release

Change protected-branch workflow to:

```sh
jankurai security run . --strict --out target/jankurai/security
```

Then strengthen `required_tools`.

## Fix 4: Add top-level workflow permissions and action pinning

Add:

```yaml
permissions:
  contents: read
```

Pin external actions to full SHAs.

## Fix 5: Add coverage and confidence metadata

Do this before adding many more detectors. It will reduce confusion and false confidence.

## Fix 6: Add detector fixtures

Every new rule should ship with:

```text
known-bad fixture
known-good fixture
expected finding JSON
false-positive regression fixture if needed
```

## Fix 7: Fix archive hygiene

Add:

```gitignore
._*
.AppleDouble
```

Add an audit rule to flag AppleDouble sidecars.

## Fix 8: Tighten proof receipts

For strict/release, require git head, tree hash, dirty flag, command digest, log hash, artifact digests, changed paths, rules covered, and CI run identity.

# The “best available standard” target

For Jankurai to credibly claim world-class audit/scoring, I would define the target as:

```text
A repo can only score 95+ when:

1. The audit ran after all required evidence was generated.
2. The ratchet baseline came from protected prior state, not candidate state.
3. All critical evidence is bound to git head, tree hash, command, logs, artifacts, and CI identity.
4. Strict security ran on protected branch.
5. CI actions are pinned and least-privilege.
6. Release artifacts have SBOM, vulnerability scan, provenance, and signatures.
7. The report lists scanned, skipped, truncated, generated, vendor, unreadable, and parser-failed files.
8. Rules map to external standards.
9. Detectors have known-good/known-bad fixtures.
10. High-risk changes require stronger proof and review.
11. Suppressions have owner, reason, expiry, and compensating control.
12. Audit artifacts are scanned/redacted before upload.
13. Agent instructions cannot override trusted policy.
14. The auditor itself obeys its own shape/security rules or declares expiring exceptions.
```

That is the line between a good custom linter and a serious engineering assurance system.

Jankurai already has many of the right concepts. The highest-value next move is to make the system **fresh-evidence-first, non-self-ratcheting, strict-on-protected-branches, standards-mapped, and calibration-backed**.

## Executive assessment

You are building more than a lint tool. The repo is trying to create an **evidence-carrying merge discipline**: owner maps, test maps, generated-zone rules, proof lanes, HLT audit rules, security evidence, UX receipts, score history, merge witnesses, and repair queues. That is exactly the right direction for “kill vibe coding”: stop accepting plausible-looking code and require reproducible evidence.

The strongest parts are the **standard-first framing**, stable HLT rule IDs, explicit owner/test maps, generated-zone manifests, conformance fixtures, proofbind/proofmark concepts, UX artifact receipts, security-lane envelope, and broad bad-behavior catalogs across Rust, SQL, TypeScript, Docker, Python, CI, Git, Git tooling, and release scripts.

The biggest gap is that the current implementation can still produce or display a high score while important evidence is missing, weak, self-referential, advisory-only, or not actually executed. The top priority should be **score integrity**: a score must never be better than the weakest required proof for the changed surface.

I could not run the Rust tests in this container because Cargo attempted to reach `index.crates.io` and DNS/network access failed. So the report below is a static code/policy/workflow review plus current best-practice comparison. That failure is itself a useful signal: the repo is not currently hermetic/offline-verifiable from the archive alone.

# Highest-priority gaps to fix first

## P0. The CI ratchet baseline is self-generated in the same run

In `.github/workflows/jankurai.yml:32-38`, CI first runs:

```bash
jankurai . --json agent/repo-score.json --md agent/repo-score.md
cp agent/repo-score.json target/jankurai/baseline-score.json
```

Then it runs ratchet mode against that freshly generated baseline. That defeats the purpose of ratcheting: the baseline is the current result, so regressions against the accepted historical baseline are not detected.

This is the single most important scoring issue I found.

**Fix:**

Use an accepted baseline that is committed, protected, or downloaded from a trusted prior artifact. Do not generate the ratchet baseline inside the same job.

Recommended model:

```yaml
- name: Verify committed ratchet baseline exists
  run: test -f agent/baselines/main.repo-score.json

- name: jankurai audit
  run: >
    jankurai audit .
    --mode ratchet
    --baseline agent/baselines/main.repo-score.json
    --json target/jankurai/repo-score.json
    --md target/jankurai/repo-score.md
    --sarif target/jankurai/jankurai.sarif
```

Also: the README says to commit `agent/repo-score.json` as the accepted baseline, but `.gitignore:19-21` ignores `agent/repo-score.json` and `agent/repo-score.md`. That is contradictory. Either use `agent/baselines/main.repo-score.json` as the committed baseline, or unignore the chosen baseline path.

## P0. The public score badge is not backed by the submitted source report

`README.md:1-2` displays `Jankurai score: 100/100`. `agent/jankurai-badge.json:6-20` claims:

```json
"source_report": "agent/repo-score.json",
"score": 100,
"decision": "pass",
"findings": 0
```

But in the submitted archive, `agent/repo-score.json` is absent, `agent/repo-score.md` is absent, and `agent/jankurai-badge.svg` is absent. The badge JSON points to a source report that is not present.

That is a trust gap: a world-class audit system should not allow a public “100/100 pass” claim unless the exact source report exists and its fingerprint matches.

**Fix:**

Add a hard gate:

```text
HLT-public-claim-integrity:
  If README, badge JSON, badge SVG, release notes, public evidence, or docs claim a score:
    - source report must exist
    - source report fingerprint must match badge fingerprint
    - badge SVG must exist

```

The command should be something like:

```bash
jankurai badge verify \
  --badge-json agent/jankurai-badge.json \
  --source agent/repo-score.json \
  --readme README.md \
  --strict
```

## P0. GitHub Actions are not supply-chain hardened

The workflow uses tag-based actions:

```yaml
actions/checkout@v6
dtolnay/rust-toolchain@stable
actions/setup-node@v6
actions/upload-artifact@v7
```

GitHub’s secure-use guidance recommends pinning third-party actions to a full-length commit SHA; full SHA pinning is the only immutable way to pin an action release. ([GitHub Docs][2])

The workflow also has no top-level `permissions:` block. GitHub says it is good security practice to grant the `GITHUB_TOKEN` only the minimum required permissions, commonly read-only contents by default. ([GitHub Docs][2])

**Fix:**

At minimum:

```yaml
permissions:
  contents: read

jobs:
  audit:
    permissions:
      contents: read
      security-events: write # only if uploading SARIF
```

Then pin actions by SHA, or introduce a policy exception file requiring owner, expiry, and review for tag-pinned actions.

Add a CI detector that blocks:

```text
- no top-level permissions
- write-all permissions
- unpinned third-party action refs
- mutable runner labels in release jobs
- pull_request_target + checkout of PR head
- untrusted scripts with secrets
- upload-artifact paths that include secrets, .env, npmrc, cargo credentials, SSH keys
```

OpenSSF Scorecard includes checks for pinned dependencies, token permissions, packaging, and signed releases, so this should become a native evidence lane rather than only a custom heuristic. ([undefined][3])

# Scoring and audit architecture gaps

## 1. Language bad-behavior findings are not fully integrated into scoring caps

`agent/audit-policy.toml:18-45` has caps for older rule families, but the newer HLT-028 through HLT-037 families are not consistently represented as cap buckets. The detector can emit findings for HLT-029 through HLT-037, but the score cap model does not appear to guarantee that serious language/CI/release issues cap the score appropriately.

**Fix:**

Every stable HLT rule should have:

```text
rule_id
severity floor
cap bucket
cap value
detector coverage
proof lane
required artifact
docs URL
safe/risky/ambiguous fixtures
exception policy
```

For example:

```toml
[caps]
rust_bad_behavior_high = 72
sql_bad_behavior_high = 70
typescript_bad_behavior_high = 72
docker_bad_behavior_high = 68
python_bad_behavior_high = 70
ci_bad_behavior_high = 65
git_bad_behavior_high = 75
gittools_bad_behavior_high = 74
release_bad_behavior_high = 60
boundary_evidence_gap = 76
```

A release integrity finding should never allow a 90+ score. A CI token/action hardening finding should usually cap below the merge threshold.

## 2. Too many findings report only the first hit

In `crates/jankurai/src/audit/mod.rs`, many categories use only the first hit:

scan::todo_hits(ctx)[0]
scan::fallback_hits(ctx)[0]

Do not spam the Markdown report, but the JSON/SARIF should preserve all evidence.

## 3. “Hardness” and confidence should be explicit in scoring

The current system has severity, category, check ID, confidence, hardness fields in schemas, but scoring should more explicitly distinguish:

```text
deterministic hard blocker
high-confidence static finding
medium-confidence heuristic
missing evidence
advisory best-practice gap
tool unavailable
tool failed
tool skipped
```

A missing required tool should be different from “tool ran and found no issues.” A heuristic substring match should not carry the same semantics as a parser-confirmed unsafe sink.

**Fix:**

Every finding should include:

```json
{
  "evidence_kind": "parser|tool|receipt|heuristic|missing-artifact|policy",
  "confidence": "high|medium|low",
  "detector_version": "...",
  "detector_mode": "required|advisory|observe",
  "tool_status": "ran|failed|skipped|missing|not_applicable",
  "suppression_status": "none|approved|expired|invalid"
}
```

Then scoring should treat `missing required evidence` as a first-class risk.

## 4. Release-mode proof receipts can bypass full evidence integrity

`release_proof_findings` in `crates/jankurai/src/audit/mod.rs:1221-1243` validates full evidence only when `--proof-evidence` is provided. If `--proof-receipts` is supplied and receipts are non-empty, it returns `Ok(vec![])`.

That means raw receipts can satisfy release proof without the stronger evidence-index checks later implemented in `release_proof_evidence_findings`.

**Fix:**

For release mode, require the evidence index. Raw receipt mode should be advisory only.

```text
release mode:
  require evidence-index
  require plan digest
  require command digests
  require log digests
  require artifact digests
  require manifest fingerprints
  require git_head == current HEAD or explicitly accepted
  require changed path coverage
```

## 5. Changed-path detection can false-green on git diff failure

`changed_paths_from_git` returns `Ok(vec![])` if `git diff base...HEAD` fails:

```rust
if !output.status.success() {
    return Ok(vec![]);
}
```

That is dangerous. If `origin/main` is missing or a ref is wrong, changed-path mode silently becomes empty/full-ish depending on caller behavior.

**Fix:**

Return an error with stderr:

```rust
if !output.status.success() {
    bail!("git diff {}...HEAD failed: {}", base, stderr);
}
```

In CI, failed changed-path resolution should be blocking.

## 6. Report timestamps and run IDs are weak

`started_at()` emits Unix seconds as a string, and `run_id()` is based on that same second. Multiple audits in one second can collide, and schemas cannot reliably enforce date-time formats because the custom schema validator does not support `format`.

**Fix:**

Use:

```text
generated_at: RFC3339 UTC
started_at: RFC3339 UTC
run_id: UUIDv7 or sha256(repo, head, timestamp_nanos, pid/random)
```

Also add a monotonic run sequence only for local history display, not identity.

---

## 7. Public conformance levels are too coarse

`conformance_summary` returns HL3 when the decision passes, otherwise HL2 review/block. That makes conformance look like a score alias rather than a maturity model.

**Fix:**

Define measurable levels:

```text
HL0: inventory only
HL1: owner/test/generated-zone maps present
HL2: advisory audit + required maps + no critical public-claim gaps
HL3: CI-required audit + required proof lanes + strict security + no high blockers
HL4: ratchet with accepted baseline + SARIF + SBOM + dependency policy + release evidence
HL5: signed releases + SLSA/provenance + reproducible build + branch protection + external verification
```

The report should compute which level is actually satisfied and which requirements are missing.

# Supply-chain and release gaps

## 1. No SLSA/npm provenance release lane

The repo has release bad-behavior detectors and public evidence concepts, but no release workflow that actually produces signed provenance, npm provenance, checksums, and attestations.

For GitHub Actions releases, SLSA recommends using hosted build platforms that generate signed provenance; for GitHub Actions specifically, it points to the language-agnostic GitHub provenance generator/builder as a way to qualify for SLSA 3. ([SLSA][4]) The SLSA GitHub generator project describes itself as tooling to generate and verify SLSA Build Level 3 provenance for native GitHub projects. ([GitHub][5])

For npm, provenance statements publicly establish where a package was built and who published it. ([npm Docs][6])

**Fix:**

Add a release workflow with:

```text
cargo test/clippy/fmt
cargo package --list
cargo publish --dry-run
npm ci
npm pack --dry-run
npm publish --provenance --dry-run or controlled release
SBOM generation
checksums
cosign/signing or GitHub artifact attestations
SLSA provenance
tag verification
changelog/version consistency
rollback instructions
```

Then make `HLT-037-RELEASE-BAD-BEHAVIOR` require those artifacts for release mode.

## 2. No dependency license/source policy

`Cargo.lock` has duplicate versions for several crates, including `bitflags`, `hashbrown`, `thiserror`, `windows-sys`, `winnow`, and `wit-bindgen`. Duplicates are not automatically bad, but they should be reviewed because they increase attack surface and patch drift.

**Fix:**

Add `deny.toml` and require:

```bash
cargo deny check advisories bans licenses sources
```

Policy should include:

```text
- allowed licenses
- denied licenses
- denied duplicate versions above threshold
- allowed registries/sources
- yanked crate policy
- unmaintained advisory policy
- build-script review policy for high-risk crates
```

## 3. npm audit is not enough unless lockfile integrity is enforced

This repo has `package-lock.json`, and CI uses `npm ci`, which is good. npm’s audit command relies on package lock/shrinkwrap by default, and without a lock the results can vary. ([npm Docs][7])

**Fix:**

Audit should explicitly require:

```text
- package-lock.json present for npm projects
- npm ci used, not npm install, in CI
- lockfile version expected
- package-lock integrity fields present
- no workspace package uses unpublished broad ranges unless intentional
- npm audit required in strict lane
- npm provenance required for publish
```

`packages/ux-qa/package.json:25-26` uses:

```json
"axe-core": "^4.11.4"
```

That is fine for development with a root lockfile, but for a published package you should decide whether runtime dependencies should be exact or whether provenance/lock evidence is enough.

# Rust audit gaps

The Rust detector pack is useful. It catches undocumented unsafe blocks, public unsafe functions missing `# Safety`, unsafe Send/Sync, `transmute`, `assume_init`, `zeroed`, unchecked APIs, `static mut`, `repr(packed)`, lint suppression, dynamic shell, unbounded channels, `block_on` in async, clone overuse, `Arc<Mutex>`, `Rc<RefCell>`, casts, `repr(C)`, `Pin`, atomics, and unwraps.

But world-class Rust quality needs ecosystem-native proof, not just custom scans.

## Required Rust gates to add

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
cargo test --workspace --no-default-features
cargo doc --workspace --all-features --no-deps
cargo audit
cargo deny check
cargo tree -d
cargo package --list
cargo package --allow-dirty --dry-run # only in controlled release context
```

Clippy’s `correctness` lint group is deny-by-default and covers code that is outright wrong or useless, so the custom audit should not substitute for Clippy. ([Rust Documentation][9])

For libraries, `#![deny(missing_docs)]` is a useful way to prevent public API documentation drift. ([Rust Documentation][10])

## Unsafe Rust policy should be stricter

Rust’s unsafe features include raw pointer dereference, unsafe function calls, mutable statics, unsafe traits, and union field access. ([Rust Documentation][11]) Your current detector catches many unsafe patterns, but you should require an unsafe ledger:

```text
unsafe block ID
file/line
reason
safety invariant
caller obligations
test/proof evidence
Miri status if applicable
reviewer
expiry if temporary
```

Add gates:

```text
- forbid unsafe_code by default for crates that do not need it
- deny unsafe_op_in_unsafe_fn where possible
- every unsafe block has nearby SAFETY comment
- every public unsafe fn has # Safety docs
- unsafe in dependencies measured by cargo-geiger or equivalent
- FFI/build.rs reviewed separately
```

`cargo-geiger` is designed to list unsafe Rust usage in a crate and its dependencies, so it is a good advisory/release evidence tool. ([GitHub][12])

## Public API compatibility is missing

For published crates, add:

```bash
cargo semver-checks
```

Cargo documents semver compatibility rules for Rust packages, and public API drift should be a release blocker unless the version bump and changelog justify it. ([Rust Documentation][13])

## Repository Rust code size violates the stated standard

`agent/audit-policy.toml:47-52` sets:

```toml
rust_file_hard = 350
function_hard = 70
```

But several production Rust files are far above 350 lines, including:

```text
crates/jankurai/src/main.rs                         2317
crates/jankurai/src/audit/scan.rs                  1739
crates/jankurai/src/commands/rust.rs               1626
crates/jankurai/src/audit/mod.rs                   1559
crates/jankurai/src/commands/proof.rs              1480
crates/jankurai/src/commands/update.rs             1270
```

Either the policy is aspirational, or the tool is not self-enforcing. For trust, the repo should self-audit.

**Fix:**

Create an explicit self-audit exception file:

```text
docs/exceptions/large-rust-files.toml
owner = "tools"
expires = "2026-06-30"
reason = "migration in progress"
target = "split audit/mod.rs into scoring, evidence, report, git, proof modules"
```

Then make large-file exceptions visible in the score.

# TypeScript / Vite / React gaps

The UX QA package has a strong `tsconfig`: `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes` are enabled. That is good. TypeScript’s `noUncheckedIndexedAccess` intentionally adds `undefined` to unknown indexed fields, which is valuable for boundary safety. ([typescriptlang.org][14])

But the TypeScript detector only checks a narrow set: `@ts-nocheck`, `any`/casts at boundaries, `strict`/`strictNullChecks`/`noEmitOnError`, dangerous eval/DOM, raw shell/SQL.

## TypeScript audit coverage to add

Detect and/or require:

```text
tsc --noEmit
noImplicitOverride
noUncheckedIndexedAccess
exactOptionalPropertyTypes
useUnknownInCatchVariables
noPropertyAccessFromIndexSignature
noFallthroughCasesInSwitch
noImplicitReturns
noEmitOnError
skipLibCheck policy
```

`skipLibCheck` is enabled in `packages/ux-qa/tsconfig.json`. That is common, but for a release-quality package, the audit should at least report it as an advisory tradeoff.

## ESLint/type-aware checks are missing

Add required linting:

```text
@typescript-eslint strict type-checked rules
eslint-plugin-react-hooks
eslint-plugin-jsx-a11y for React/UI packages
eslint-plugin-security or Semgrep rules
no-floating-promises
no-misused-promises
no-unsafe-assignment
no-unsafe-member-access
no-explicit-any except approved boundary files
```

React’s official hooks plugin catches rules-of-hooks and exhaustive-deps issues at build time; exhaustive-deps validates hook dependency arrays to avoid stale closures. ([React][15])

## Vite-specific env leakage should be a first-class rule

Vite exposes variables prefixed with `VITE_` to client-side code after bundling; those values should not contain secrets. ([vitejs][16])

Add a detector:

```text
- .env files committed
- .env.*.local not ignored
- VITE_* contains TOKEN, SECRET, PASSWORD, KEY, PRIVATE, CREDENTIAL
- import.meta.env usage without typed env schema
- server-only env accessed from client package
```

Also add a Vite build artifact scanner:

```text
- grep built dist for known secret markers
- verify source maps policy
- verify CSP headers for web apps
- bundle size/performance budget
```

## UX QA is promising but not yet world-class visual QA

`@jankurai/ux-qa` captures screenshots, ARIA snapshots, accessibility summaries, and visual baseline hashes. Good direction. But `visual-baseline.ts` compares screenshot file hashes, not perceptual image diffs. Byte hash equality is deterministic, but too brittle for fonts, antialiasing, OS differences, and browser rendering variance.

**Fix:**

Use three tiers:

```text
deterministic DOM geometry rules => hard blocker
axe accessibility violations => hard blocker
visual hash change => review/block depending policy
pixel/perceptual diff with threshold => review/block
owner-approved baseline update => allowed only with approval receipt
```

Also validate `baselineApprovedAt` as a date-time and require `baselineOwner`/`approvedBy` for baseline changes.

# SQL / Postgres gaps

The SQL detectors catch dynamic SQL, destructive migrations, full-table update/delete, and `SELECT *`. Good baseline. But migration safety is still too comment/line oriented.

`docs/testing.md:24-28` already admits that destructive checks are line-oriented and can be confused by pathological SQL. That limitation should be converted into a scoring rule: serious DB changes require migration analysis evidence, not just static comments.

## SQL migration safety to add

Require for every migration:

```text
unique monotonic migration ID
transaction policy
lock_timeout / statement_timeout where appropriate
rollback/down migration or explicit irreversible approval
expand/contract plan for breaking changes
backfill strategy
index creation strategy, e.g. concurrently where needed
large-table risk annotation
data-loss risk annotation
dry-run against disposable DB
schema diff artifact
RLS/policy diff where applicable
EXPLAIN evidence for changed hot queries
```

Do not let a comment like `-- rollback proof` fully suppress destructive migration risk. It should reduce severity only when backed by a migration receipt.

## SQL parser gap

Line-level detection misses multi-line SQL, procedural SQL, comments/strings, CTEs, and dialect-specific statements.

**Fix:**

Use a SQL parser or dialect-aware linter for Postgres. Add fixtures for:

```sql
DELETE
FROM users
WHERE id = $1;
```

and:

```sql
EXECUTE format('DROP TABLE %I', table_name);
```

and procedural bodies where strings contain destructive SQL.

## Data authorization/RLS gap

The standard mentions authz isolation, but for Postgres the audit should specifically check:

```text
- RLS enabled for tenant/user-owned tables
- deny-by-default policies
- owner/non-owner negative tests
- service-role key not available to client/Vite
- migrations that create tenant tables include RLS policy proof
```

OWASP ASVS is a good baseline for web application technical security controls and secure development requirements, so authn/authz/input/session/API checks should map to ASVS controls rather than only local heuristics. ([OWASP Foundation][18])

# Schema and report contract gaps

## 1. Custom JSON Schema validator supports only a subset

`crates/jankurai/src/validation.rs` supports `$ref`, `const`, `enum`, `pattern`, `type`, `allOf`, `anyOf`, `oneOf`, objects, arrays, numeric constraints, string length, and `additionalProperties`. It does not support many common JSON Schema keywords such as:

```text
format
patternProperties
dependentRequired
if/then/else
contains
minContains
propertyNames
unevaluatedProperties
multipleOf
exclusiveMinimum/exclusiveMaximum
```

That is not automatically wrong, but it means schemas can look stricter than they are. For example, a schema may say a field is a timestamp conceptually, but the validator cannot enforce `format: date-time`.

**Fix:**

Either use a full JSON Schema implementation, or make the supported subset explicit and ban unsupported keywords at authoring time. You already ban unsupported keywords, which is good. Next step: add format support or avoid pretending date strings are validated.

## 2. Many schemas allow extra fields or omit root `additionalProperties: false`

Examples from the schema inventory:

```text
repo-score.schema.json            additionalProperties missing
finding.schema.json               additionalProperties missing
readme-badge.schema.json          additionalProperties missing
score-diff.schema.json            additionalProperties missing
score-trend.schema.json           additionalProperties missing
security-evidence.schema.json     additionalProperties true
proof-plan.schema.json            additionalProperties true
evidence-index.schema.json        additionalProperties true
ux-qa-policy.schema.json          additionalProperties true and no root required
```

Some extension points are valid, but report contracts should be strict by default. Otherwise, agents can add fields that look official but are ignored.

**Fix:**

Adopt:

```text
additionalProperties: false by default
extensions allowed only under "extensions" object
extension keys namespaced, e.g. "com.example.foo"
unknown root fields fail
```

# Security and secret handling gaps

## 1. Gitleaks allowlist lacks owner/expiry/reason granularity

`.gitleaks.toml:6-24` has broad allowlists for paths and regexes such as `token-hash` and `signing-key`. This is understandable for fixtures and docs, but world-class secret scanning needs explainable exceptions.

**Fix:**

Move allowlist metadata to a machine-readable exceptions file:

```toml
[[allowlist]]
path = "examples/perfect-web-api-db/backend/src/auth_session.rs"
reason = "fixture contains non-secret token-hash wording"
owner = "security"
expires = "2026-07-01"
regex = "token-hash"
```

Then generate `.gitleaks.toml` from that file or validate it against it.

## 2. Security wrapper uses shell command strings

`tools/security-lane.sh:55` and `:83` run:

```bash
bash -c "$cmd"
```

Right now commands are static arrays in the script, so this is not an immediate injection bug. But the pattern is dangerous if commands later come from config.

**Fix:**

Move security orchestration to Rust and run commands as argv arrays:

```rust
Command::new("gitleaks").args(["detect", "--source", ".", "--redact", "--no-banner"])
```

Keep the shell wrapper only for manual debugging.

# Detector-quality gaps

The repo intentionally uses many line/substring detectors. That is fine for early coverage, but “best available standard” should graduate high-impact rules to AST/parser-backed checks.

## Add parser-backed detection for high-risk families

Use:

```text
Rust: syn/rustc/cargo metadata
TypeScript/TSX: TypeScript compiler API or tree-sitter
Python: ast module or tree-sitter
SQL: Postgres dialect parser/linter
YAML/GitHub Actions: YAML AST + action semantics
Dockerfile: Dockerfile parser/Hadolint semantics
Shell: shell parser/ShellCheck where relevant
```

Keep substring scans as a broad net, but mark them as heuristic.

## Fixed executable suppression can hide real risks

`scan.rs` has `is_fixed_safe_command_invocation`, which suppresses findings for fixed executables like `git`, `cargo`, `node`, `npm`, etc. That reduces false positives, but “fixed executable” is not always safe:

```text
git -c core.sshCommand=...
node -e ...
npm exec ...
npx ...
cargo install ...
cargo run --example ...
```

**Fix:**

Replace “fixed executable safe” with a command policy matrix:

```text
executable
allowed args
forbidden args
network behavior
write behavior
secret exposure risk
requires approval?
```

Example:

```toml
[[command_policy]]
exe = "git"
allowed = ["status", "diff", "rev-parse", "ls-files"]
forbidden = ["push", "reset", "clean", "config core.sshCommand"]

[[command_policy]]
exe = "node"
forbidden = ["-e", "--eval"]
```

# Safe rollout plan

Do not flip everything to hard-blocking at once. That would create noise and undermine trust. Use a ratcheted maturity rollout.

## Phase 1: Integrity blockers immediately

Make these hard failures now:

```text
- badge/source report mismatch
- ratchet baseline generated in same CI run
- fail_on policy ignored
- changed-from git failure silently empty
- release mode without evidence-index
- lane artifact contract mismatch
```

These are not style preferences; they directly affect audit truth.

## Phase 2: Advisory for ecosystem tools

Add but do not immediately block:

```text
cargo deny
cargo audit strict
npm audit strict
pip-audit when Python deps exist
zizmor
syft SBOM
trivy/grype
cargo tree -d
cargo semver-checks
cargo geiger
```

Publish skipped/missing tools clearly in the report.

## Phase 3: Ratchet to required

Once baseline noise is understood:

```text
- require strict security on main/release
- require fmt/clippy/test workspace
- require dependency policy
- require SBOM/provenance on release
- require SHA-pinned actions
- require explicit GitHub token permissions
```

## Phase 4: Parser-backed detectors

Gradually replace high-impact substring detectors with parser-backed detectors. Keep the heuristic layer as an early-warning net, but do not let low-confidence heuristics dominate score without evidence.

# Bottom line

The project has the right philosophy and a strong skeleton. The main missing piece is **audit self-trust**: the score must be impossible to inflate through stale badges, self-generated baselines, missing artifacts, skipped tools, advisory-only security, ignored policy, or shallow detector summaries.

The first fixes I would make are:

1. Remove the self-generated CI ratchet baseline.
2. Add badge/source-report integrity verification.
3. Make `fail_on` actually drive pass/fail.
4. Replace `just check`/`full` with a real full gate.
5. Run security strict in CI and require SCA/SBOM/workflow scanning evidence.
6. Pin GitHub Actions and set least-privilege permissions.
7. Require evidence-index proof for release mode.
8. Make changed-path git failures hard failures.
9. Add cap buckets for HLT-028 through HLT-037.
10. Add full-hit accounting, not only first-hit findings.

Those changes will most improve the credibility of the score and make Jankurai much harder for vibe-coded work to fool.

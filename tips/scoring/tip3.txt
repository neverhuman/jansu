# Code audit report: missing best-practice coverage and high-priority fixes

I inspected the uploaded repository as a static code/config audit: Rust workspace, CLI scoring engine, audit rule families, GitHub workflow, composite action, policies, schemas, conformance fixtures, TypeScript/Playwright package, Docker/SQL examples, Justfile, security lane, score history, and agent control-plane files. I did **not** execute arbitrary project code. I attempted a Rust build/test path, but the container had no cached crates and no internet access to `index.crates.io`, so compile/test execution was not possible here. The findings below are therefore strongest on audit architecture, CI, scoring, policy, and static rule coverage.

The short version is: **Jankurai is already a strong idea and has many good anti-vibe controls, but the current audit can produce a “pass-looking” repository posture that is not yet defensible as world-class because multiple gates measure the presence of audit artifacts rather than proving strict, current, non-skipped, blocking execution.** NIST’s SSDF frames secure software development as practices that reduce vulnerabilities, mitigate impact, and address root causes; SLSA similarly emphasizes tamper resistance, artifact integrity, and proving that the source relied on is the source actually used. Jankurai should move closer to that standard by making every important score depend on independently verifiable evidence, not on self-reported reports or command strings. ([NIST Computer Security Resource Center][1])

## Highest-priority problems needing attention

### 1. Critical: `jankurai audit` appears not to fail closed

In `crates/jankurai/src/main.rs:2037-2217`, `run_audit_and_write` writes JSON, Markdown, SARIF, JUnit, step summary, repair queue, history, and badge output, then returns `Ok(())`. I did not find a final enforcement step that exits non-zero when `report.decision.passed == false`.

`apply_mode_and_baseline` at `crates/jankurai/src/main.rs:2273-2304` mutates the report decision for advisory/ratchet/release modes, but it also returns `Ok(())` even when the decision becomes failed. That means CI can be green while the generated report says fail.

This is the most important fix. A scoring tool that reports failure but exits zero is a false-green machine.

**Fix:**

After all artifacts are written, but before returning `Ok(())`, fail for every non-advisory mode when the decision is failed. Writing artifacts first is smart because CI can still upload the report with `if: always()`.

```rust
fn enforce_audit_decision(
    report: &jankurai::model::Report,
    mode: AuditMode,
) -> anyhow::Result<()> {
    if matches!(mode, AuditMode::Advisory) {
        return Ok(());
    }

    let Some(decision) = report.decision.as_ref() else {
        anyhow::bail!("audit produced no decision");
    };

    if !decision.passed {
        anyhow::bail!(
            "jankurai audit failed: mode={} score={} minimum={} hard_findings={} soft_findings={} caps={}",
            mode.as_str(),
            report.score,
            decision.minimum_score,
            decision.hard_findings,
            decision.soft_findings,
            report.caps_applied.len()
        );
    }

    Ok(())
}
```

Call it near the end of `run_audit_and_write`, after report files are written and before the final `Ok(())`.

Add conformance tests that assert the CLI process exits non-zero for:

```text
standard mode + score below minimum
standard mode + high finding
ratchet mode + score regression
release mode + missing release proof
```

This should become a new hard rule, for example:

```text
HLT-038-AUDIT-FAILS-CLOSED
Critical if a blocking audit report can exit zero.
```

### 2. Critical: CI ratchet baseline compares the repository against itself

The workflow currently does this:

```yaml
# .github/workflows/jankurai.yml:32-38
- name: Generate CI ratchet baseline
  run: |
    jankurai . --json agent/repo-score.json --md agent/repo-score.md
    cp agent/repo-score.json target/jankurai/baseline-score.json
    cp agent/repo-score.md target/jankurai/baseline-score.md

- name: jankurai audit
  run: jankurai audit . --mode ratchet --baseline target/jankurai/baseline-score.json ...
```

That makes the ratchet compare the current score against a baseline generated from the same current checkout. The ratchet therefore cannot meaningfully block score regressions.

**Fix:**

Use an accepted baseline from the base branch or a protected checked-in baseline, never a current-head report generated immediately before the ratchet.

Good options:

```yaml
- name: Fetch base branch baseline
  run: |
    git fetch origin main --depth=1
    git show origin/main:agent/repo-score.json > target/jankurai/baseline-score.json

- name: jankurai audit
  run: >
    jankurai audit .
    --mode ratchet
    --baseline target/jankurai/baseline-score.json
    --json target/jankurai/repo-score.json
    --md target/jankurai/repo-score.md
    --sarif target/jankurai/jankurai.sarif
    --github-step-summary target/jankurai/summary.md
    --repair-queue-jsonl target/jankurai/repair-queue.jsonl
```

Even better: store the accepted baseline separately as `agent/baseline-score.json`, protect it with CODEOWNERS, and require a “baseline update” label plus human approval.

Add a detector:

```text
HLT-039-CI-SELF-BASELINE
Critical if a workflow creates a baseline from the same checkout and then runs ratchet against it.
```

### 3. Critical: the security lane is non-strict in CI, and skipped tools can still look acceptable

The workflow runs:

```yaml
# .github/workflows/jankurai.yml:86-87
- name: Security lane
  run: jankurai security run . --out target/jankurai/security/evidence.json
```

No `--strict`.

The shell lane defaults to non-strict:

```bash
# tools/security-lane.sh:4
strict="${JANKURAI_SECURITY_STRICT:-0}"
```

Missing required tools are skipped outside strict mode:

```bash
# tools/security-lane.sh:41-51
if ! command -v "$tool" >/dev/null 2>&1; then
  echo "skip: $tool not installed; advisory outside strict mode"
  emit_step "$tool" "$tool" "$cmd" "skipped" "1" ""
  if [ "$strict" = "1" ]; then
    exit 1
  fi
  return 0
fi
```

The Rust wrapper only bails when the script exit code is non-zero:

```rust
// crates/jankurai/src/commands/security.rs:240-242
if exit_code != 0 {
    anyhow::bail!("security lane exited with status {exit_code}");
}
```

The audit then attaches a summary of the evidence artifact at `crates/jankurai/src/audit/mod.rs:218-220`, but I did not see scoring logic that turns `wrapper_strict=false`, skipped required commands, failed commands, stale evidence, or missing tool versions into hard findings. `crates/jankurai/src/audit/security_artifact.rs:30-71` summarizes these fields but does not enforce them.

**Fix:**

In CI:

```yaml
- name: Security lane
  run: jankurai security run . --strict --out target/jankurai/security/evidence.json
```

Then make audit scoring fail when any of these are true:

```text
security_evidence.artifact is missing
wrapper_strict == false in protected CI
commands_skipped > 0 for required tools
commands_failed > 0
git_head != current checkout SHA
generated_at is stale
required tool has no version/provenance
evidence schema validation fails
```

The current lane also has a policy drift problem: `agent/security-policy.toml` lists `gitleaks`, `cargo audit`, and `npm audit`, but `tools/security-lane.sh` also runs `syft` and `zizmor` as advisory tools. Put the same tool list in one policy source and generate the script or validate the script against the policy.

Add:

```text
HLT-040-EVIDENCE-STRICTNESS-GAP
Critical if a required evidence lane is absent, stale, skipped, non-strict, or not tied to the current commit.
```

### 4. Critical: GitHub Actions permissions and action pinning are below world-class standard

The actual workflow has no top-level or job-level `permissions:` block in `.github/workflows/jankurai.yml`. The README example does include `permissions: contents: read` at `README.md:162-164`, but the real workflow does not.

The workflow uses tag/channel refs:

```yaml
actions/checkout@v6
dtolnay/rust-toolchain@stable
actions/setup-node@v6
actions/upload-artifact@v7
```

The current CI language rule detector flags `@main`, `@master`, and `@latest`, but it does not flag major-version tags like `@v6` or channel refs like `@stable`. GitHub’s Actions security guidance says pinning to a full-length commit SHA is the only way to use an action as an immutable release, and GitHub also recommends limiting `GITHUB_TOKEN` permissions to the minimum required. ([GitHub Docs][2])

**Fix:**

Add explicit permissions:

```yaml
permissions:
  contents: read
```

For jobs that upload SARIF or attestations, add only the minimum required scopes:

```yaml
permissions:
  contents: read
  security-events: write
```

For provenance/release publishing jobs, add only when needed:

```yaml
permissions:
  contents: read
  id-token: write
  attestations: write
```

Add a hard detector:

```text
HLT-041-ACTION-SHA-PINNING-GAP
High/critical if third-party actions are not pinned to full commit SHAs.

HLT-042-CI-LEAST-PRIVILEGE-GAP
High if a workflow lacks explicit minimal permissions.
Critical if write-all, broad write scopes, or untrusted pull_request_target patterns are present.
```

Also enable CodeQL for both source languages and GitHub Actions workflows. GitHub now supports workflow security analysis through CodeQL, including detection for missing permissions and script injection issues. ([GitHub Docs][3])

### 5. High: `--policy` and `--fail-on` CLI behavior is incomplete

`AuditArgs` defines:

```rust
// crates/jankurai/src/main.rs:290-298
baseline: Option<String>,
policy: Option<String>,
self_audit: bool,
fail_under: Option<i32>,
fail_on: Vec<String>,
```

But `run_audit_and_write` does not appear to use `args.policy`. The audit policy is loaded from `agent/audit-policy.toml` inside `crates/jankurai/src/audit/mod.rs:307-343`.

Also, `--fail-on` only updates `report.policy.fail_on` in `crates/jankurai/src/main.rs:2085-2089`; it does not appear to recompute hard findings or the decision. `report_decision` currently hard-codes high/critical as hard severities at `crates/jankurai/src/audit/mod.rs:346-352`.

**Fix:**

Make policy path an actual input to `run_audit_timed_with_options`, or remove the CLI arg until implemented. Then compute hard findings from `policy.fail_on`, not hard-coded severities.

Expected behavior:

```text
--fail-on critical,high          default hard gate
--fail-on critical,high,medium   medium becomes blocking
--fail-on none                   only minimum score gates, if intentionally allowed
```

Add tests proving that `--fail-on medium` changes the process exit code.

### 6. High: the “one command” local validation is not enough

`Justfile:19-22` defines:

```just
check:
    cargo run -p jankurai -- versions
    cargo run -p jankurai -- . --json agent/repo-score.json --md agent/repo-score.md ...
    latexmk ...
```

This does not run:

```text
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --locked
cargo deny check
cargo audit
npm ci
npm audit
npm run build/test
TypeScript noEmit
Playwright/UX QA
security strict
conformance
Docker lint/scan
SQL migration analysis
```

For an anti-vibe coding system, “one command validates the repo” has to mean the same thing locally and in CI. Right now, `just check` is closer to “generate report and paper” than “prove merge readiness.”

**Fix:**

Split commands:

```just
fast:
    cargo fmt --all --check
    cargo check --workspace --locked
    npm ci
    npm --workspace @jankurai/ux-qa run build

test:
    cargo test --workspace --locked
    npm --workspace @jankurai/ux-qa run test

security:
    cargo deny check
    cargo audit
    npm audit --audit-level=high
    cargo run -p jankurai -- security run . --strict --out target/jankurai/security/evidence.json

audit:
    cargo run -p jankurai -- audit . --mode standard --json target/jankurai/repo-score.json --md target/jankurai/repo-score.md

check: fast test security audit conformance
```

Keep a separate `paper` target so paper build failures do not hide code validation failures.

# Scoring and audit architecture gaps

## A. Score should be secondary to hard gates

A 72/100 with a critical finding should not feel “mostly okay.” A world-class scoring system should have two layers:

```text
Gate result: pass/fail
Score: diagnostic/ratchet signal
```

Recommended decision model:

```json
{
  "passed": false,
  "blocking_reasons": [
    "critical finding",
    "ratchet regression",
    "required evidence missing",
    "required security tool skipped"
  ],
  "score": 88
}
```

The current cap model is useful, but critical failures should force an explicit blocking decision regardless of score. Keep score for trend and repair prioritization, but never allow a nice score to soften a hard gate.

## B. Evidence needs a trust level

Add an evidence trust ladder:

```text
E0: claimed in docs
E1: config file exists
E2: command string present in CI
E3: artifact exists and schema-valid
E4: artifact is from current commit, strict mode, no skipped required tools
E5: artifact is attested/signed and tied to CI run identity
```

Most Jankurai scoring should require at least E4 for blocking controls. Release controls should require E5.

## C. Report/badge tampering is not controlled enough

The README badge says `Jankurai score: 100/100` at `README.md:2`. `agent/jankurai-badge.json` points to `agent/repo-score.json`, but the archive did not contain `agent/repo-score.json`; it did contain score history and badge JSON. More importantly, a tracked badge or report can be modified unless CI regenerates it from the current tree and verifies it.

Add:

```text
HLT-050-REPORT-TAMPERING-GAP
Critical if tracked score/badge/history can be edited without regeneration proof.
```

Fix pattern:

```bash
jankurai audit . --json target/jankurai/repo-score.json --md target/jankurai/repo-score.md
jankurai badge verify --source target/jankurai/repo-score.json --readme README.md --tracked agent/jankurai-badge.json
git diff --exit-code -- README.md agent/jankurai-badge.json
```

Do not treat checked-in reports as the source of truth. Treat the CI-generated report as the source of truth.

## D. Inventory coverage can hide important files

`crates/jankurai/src/audit/fs.rs:50-55` uses `ignore::WalkBuilder` with `.git_ignore(true)`, `.git_exclude(true)`, and `.git_global(true)`. That is usually convenient, but for a security/audit tool it can miss code hidden by `.gitignore`. The scanner also captures only the first 120,000 characters by default (`crates/jankurai/src/audit/fs_policy.rs:6`).

Add an inventory manifest to every report:

```json
{
  "files_total": 973,
  "files_scanned": 900,
  "files_skipped_by_gitignore": 30,
  "files_skipped_by_policy": 12,
  "files_truncated": 4,
  "truncated_paths": [...]
}
```

Add a hard finding when a high-risk file is ignored/truncated:

```text
ignored Dockerfile, workflow, SQL migration, Rust source, TypeScript source, Python source
large file truncated before sink pattern
policy excludes product path
```

## E. Pattern detectors need companion semantic tools

The current detectors are useful but mostly line/string based. That is fine for high-confidence smell detection, but not enough for a world-class gate. Add companion tools:

```text
Rust: clippy, miri, cargo-deny, cargo-audit, cargo-nextest
TypeScript: tsc, ESLint typed rules, dependency-cruiser, npm audit
Python: ruff, mypy/pyright, bandit, pip-audit
Docker: hadolint, trivy/grype, syft
SQL: SQLFluff, migration analyzer, pgTAP/testcontainers
CI: actionlint, zizmor, CodeQL Actions queries, OpenSSF Scorecard
```

OpenSSF Scorecard is designed to assess open-source projects for security risks through automated checks, so it should be one of the external calibration signals for Jankurai’s own scoring. ([undefined][4])

Use actual full commit SHAs in real workflows.

```text
EXPLAIN plan regression checks
pgTAP or testcontainers integration tests
SQLFluff lint
```

OWASP’s SQL injection guidance explicitly calls out dynamic queries with string concatenation and user-supplied input; Jankurai should require parameterized query evidence at every application boundary, not just scan `.sql` files. ([OWASP Cheat Sheet Series][10])

Add:

```text
HLT-049-POSTGRES-RLS-GAP
Critical if multi-tenant tables lack RLS/tenant isolation proof.

sql.security-definer.search-path
Critical if SECURITY DEFINER function lacks SET search_path.

sql.grants.public-write
Critical if PUBLIC or app role gets broad write/admin privileges.
```

# Smart rollout plan that avoids breaking the project unnecessarily

## Phase 0: fix correctness of the auditor itself

Do these immediately:

```text
Make non-advisory audit exit non-zero on failed decision
Stop self-baselining in CI
Make security lane strict in CI
Add explicit workflow permissions
Fix or remove unused --policy
Make --fail-on affect decision
Generate audit outputs under target/ in CI
Verify badge/report regeneration separately
```

These are not “new strict opinions”; they are correctness fixes.

## Phase 1: add high-confidence gates

Add blocking gates only where false positives are low:

```text
cargo fmt --check
cargo clippy -D warnings
cargo test --workspace --locked
npm ci
npm workspace build/test
gitleaks strict
dependency review
cargo-deny
cargo audit
npm audit high/critical
actionlint/zizmor
CodeQL
```

## Phase 2: add advisory detectors with conformance fixtures

Add new detectors first as advisory:

```text
Docker hardening
Postgres RLS
Vite secret exposure
Python path traversal/requests timeout
Rust subprocess timeout
Agent policy integrity
Report tamper
Inventory coverage
```

Each detector needs fixtures before it becomes blocking.

## Phase 3: ratchet to blocking

Promote only high-confidence advisory findings to hard findings after:

```text
false-positive review
exception mechanism exists
owner mapping exists
conformance fixture exists
repair guidance exists
CI artifact exists
```

This keeps the audit strong without creating noisy gates that teams will work around.

# Final verdict

Jankurai is pointed in the right direction, and the existing rule families are a strong foundation. But the current “100/100” posture should be treated as **aspirational** until the audit itself fails closed, the ratchet uses a real baseline, the security lane is strict, and evidence quality becomes part of scoring.

The biggest conceptual change is:

```text
Do not score “configured.”
Score “proved, current, strict, non-skipped, blocking, and tied to this commit.”
```

Once that principle is implemented across Rust, TypeScript/Vite, Python, Docker, SQL, CI, Git, release, and agent tooling, Jankurai will be much closer to the “kill vibe coding + excellent code” standard you are aiming for.

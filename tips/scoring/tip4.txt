## Executive verdict

Jankurai is pointed in the right direction. The repo already has a strong anti-vibe-coding thesis: owner maps, proof lanes, generated-zone policy, security lanes, score history, repair queues, rule IDs, schemas, conformance fixtures, Rust/TS/SQL/Docker/Python/CI/Git language detectors, and agent-readable docs. That is much better than a normal “lint + tests” setup.

The main gap is that the current audit still often proves **that a repo says the right words**, not that the repo actually executed the right proof. To reach a world-class standard, Jankurai should become much more receipt-driven, parser-driven, supply-chain-aware, and diff-aware. The highest-priority fix is to stop any path where a run can self-generate its own baseline, self-declare tool coverage, or pass because a keyword appears in a script or doc.

For the target standard, I would anchor the audit catalog to four external frames: NIST SSDF for secure-development lifecycle coverage, OWASP ASVS 5.0.0 for web/app-security requirements, SLSA for build provenance and artifact integrity, and OpenSSF Scorecard-style supply-chain posture checks. NIST SP 800-218 is the Secure Software Development Framework baseline, OWASP lists ASVS 5.0.0 as the latest stable ASVS version, SLSA defines controls/provenance to reduce tampering risk, and OpenSSF Scorecard provides automated security posture checks for open-source repositories. ([NIST Computer Security Resource Center][1])

I could not execute the full test suite in this environment because `cargo test` attempted to fetch crates and DNS resolution for `index.crates.io` failed. The report below is based on static inspection of the archive, source tree, workflow, audit engine, schemas, docs, policies, and scripts.

# 1. The biggest audit gaps to fix first

## P0-1. CI ratchet currently self-baselines the same commit

This is the most important issue I found.

In `.github/workflows/jankurai.yml`, the workflow generates a baseline from the current checkout and then immediately runs ratchet mode against that generated baseline:

```yaml
32  - name: Generate CI ratchet baseline
33    run: |
34      jankurai . --json agent/repo-score.json --md agent/repo-score.md
35      cp agent/repo-score.json target/jankurai/baseline-score.json
...
37  - name: jankurai audit
38    run: jankurai audit . --mode ratchet --baseline target/jankurai/baseline-score.json ...
```

That undermines the purpose of a ratchet. The README correctly says “Ratchet mode is impossible without an accepted baseline” and that the baseline should be committed after acceptance, but the workflow contradicts this.

**Fix:** In CI, compare against one of these, never against a freshly generated score from the same commit:

1. committed `agent/repo-score.json` from the base branch;
2. last successful main-branch artifact;
3. release baseline artifact signed/attested at release time.

Add an audit rule:

```text
HLT-CI-SELF-BASELINE
critical
Fail when a workflow creates a score/baseline artifact and then uses that same artifact as ratchet baseline in the same job.
```

Safe rollout: make this critical immediately for this repo, because it is narrow and deterministic.

## P0-2. Policy fields are parsed but not enforced

`agent/audit-policy.toml` defines:

```toml
fail_on = ["critical", "high"]
advisory_on = ["medium", "low"]
```

`load_policy` parses `fail_on` and `advisory_on` in `crates/jankurai/src/audit/mod.rs:307-343`, but `report_decision` ignores them and hard-codes “high or critical” as failing in `crates/jankurai/src/audit/mod.rs:346-364`.

That makes policy look more configurable than it is.

**Fix:** Make the decision engine honor `policy.fail_on`. Then add schema validation that allowed severities are only `critical | high | medium | low | info`.

Suggested logic:

```rust
let fail_set = policy.fail_on.iter().collect::<HashSet<_>>();
let blocking_findings = findings
    .iter()
    .filter(|f| fail_set.contains(&f.severity))
    .count();

passed = score >= policy.minimum_score && blocking_findings == 0;
```

Add a conformance fixture proving that `fail_on = ["critical"]` allows high findings but fails critical findings.

---

## P0-3. The audit over-trusts “presence of text” as proof

Several analyzers award score for text markers, scripts, or docs rather than executed proof receipts. Examples:

* `has_security_lane` checks for strings such as `gitleaks`, `dependency-review-action`, `syft`, `cargo deny`, `cargo audit`, and `npm audit`.
* `has_jankurai_audit_ci_lane` checks command-surface text for `jankurai audit` and `repo-score`.
* UX, proof, observability, release, and tool adoption also use many “path or text exists” signals.

This is understandable for an adoption scanner, but it is not enough for a world-class gate. The audit should distinguish:

```text
declared     = a doc/config says the lane exists
configured   = a script/workflow invokes the lane
executed     = CI/local run executed it
verified     = exit code, artifact digest, schema, freshness, and changed-file scope verified
trusted      = artifact came from trusted CI context with immutable source/ref
```

**Fix:** Add an `evidence_level` field to every dimension and finding:

```json
{
  "evidence_level": "declared|configured|executed|verified|trusted",
  "freshness": "current_commit|base_branch|stale|unknown",
  "source": "ci|local|committed|generated|claimed",
  "command_digest": "sha256:...",
  "artifact_digests": [...]
}
```

Then scoring should cap high-assurance dimensions unless the evidence level is at least `verified`.

## P0-4. The dedicated test analyzer is empty

`crates/jankurai/src/audit/analyzers/test.rs` is a zero-line file, and `all_dimensions` in `crates/jankurai/src/audit/analyzers/mod.rs:18-32` does not include a test-quality analyzer.

There are test-related checks elsewhere, but there is no first-class “test quality” dimension. That is a major gap if the mission is to kill vibe coding, because vibe-coded repos often have tests that are shallow, skipped, snapshot-only, non-deterministic, or unrelated to the change.

**Fix:** Add a real `test` dimension. It should score:

* changed-code-to-test mapping;
* negative tests for authz/input/data-boundary changes;
* mutation testing for critical logic;
* property tests for parsers, routing, policy, scoring, and schema code;
* fuzzing for parsers and format readers;
* coverage trend, but not coverage alone;
* flaky-test quarantine policy;
* skipped/focused test bans;
* proof receipt freshness.

A good rule family:

```text
HLT-TEST-UNPROVEN-CHANGE
high
Changed product/security/data/control-plane file has no mapped executed proof receipt.
```

## P0-5. Security lane is mostly advisory and tool availability is weakly enforced

`tools/security-lane.sh` requires only `gitleaks`; `cargo audit`, `npm audit`, `syft`, and `zizmor` are advisory unless `JANKURAI_SECURITY_STRICT=1`. In the GitHub workflow, the run is:

```yaml
86  - name: Security lane
87    run: jankurai security run . --out target/jankurai/security/evidence.json
```

No `--strict`.

So the normal CI security lane can skip core security tools and still pass. The security wrapper records steps, which is good, but the default gate is not strong enough.

**Fix:**

* In main/release CI: run `jankurai security run . --strict`.
* In PR/adoption mode: allow advisory mode, but emit hard findings when a configured required tool is missing.
* Expand `agent/security-policy.toml` so required tools are per ecosystem and per risk tier.

Recommended minimum required tools for this repo:

```toml
required_tools = [
  "gitleaks",
  "cargo audit",
  "cargo deny",
  "cargo vet",
  "npm audit",
  "syft",
  "zizmor"
]
```

`cargo-vet` is specifically designed to help ensure Rust third-party dependencies have been audited by trusted entities, so it fits the project’s “proof, not vibes” thesis very well. ([Mozilla GitHub Pages][2])

## P0-6. GitHub Actions hardening is incomplete

The workflow lacks top-level/job-level `permissions`, uses mutable action references such as `actions/checkout@v6`, `actions/setup-node@v6`, and `actions/upload-artifact@v7`, and has no visible `timeout-minutes` or `concurrency`.

GitHub’s own docs say it is good security practice to set the default `GITHUB_TOKEN` permission to read-only contents and then increase per job only as needed. ([GitHub Docs][3])

**Fix:**

```yaml
permissions:
  contents: read

concurrency:
  group: jankurai-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  audit:
    timeout-minutes: 30
    permissions:
      contents: read
      security-events: write # only if uploading SARIF
```

Then add detector coverage for:

* any `uses:` not pinned to full commit SHA;
* missing top-level `permissions`;
* `permissions: write-all`;
* `pull_request_target` with checkout of untrusted head;
* `curl | bash`;
* untrusted artifacts consumed across jobs;
* cache poisoning risks;
* broad secrets exposure;
* non-ephemeral self-hosted runners for untrusted PRs.

Current `ci_hardening_hits` only catches `@master` and some nonblocking security lines (`crates/jankurai/src/audit/scan.rs:1541-1586`). It misses most of the above.

## P0-7. Supply-chain provenance is not yet release-grade

The repo has SBOM/provenance language and some release checks, but the workflow does not produce cryptographically signed build provenance for release artifacts.

SLSA provenance describes where, when, and how software was produced, and GitHub artifact attestations can create signed provenance/integrity claims for built artifacts. ([SLSA][4])

**Fix:** Add release-gate requirements:

* build artifacts have SHA256 digests;
* SBOM is generated for binaries/packages/images;
* artifact attestation is generated in CI;
* release tags are signed/protected;
* release artifacts are immutable;
* consumers can verify provenance;
* published package version matches Git tag, Cargo version, npm package version, docs, and standard manifest.

GitHub’s artifact attestation docs show the needed permission shape: `id-token: write`, `contents: read`, and `attestations: write` for provenance generation. ([GitHub Docs][5])

## P0-8. Exception/allow comments do not enforce expiry

The documented allow format is:

```text
jankurai:allow <detector-id> reason=... expires=YYYY-MM-DD
```

`nearby_allow` checks that an `expires=YYYY-MM-DD` pattern exists, but not whether the date is expired. That means an exception can live forever as long as it has a date-shaped string.

**Fix:**

Require:

```text
reason=
owner=
ticket=
expires=
scope=
```

Then fail on:

* expired exceptions;
* expiry more than 90 days out for high-risk rules;
* missing owner;
* missing issue/ticket link;
* exception that does not name the exact detector/rule;
* exception that is too far from the risky construct.

Safe rollout: advisory for 30 days, then hard-fail expired high/critical exceptions.

---

## P0-9. The input fingerprint omits some file content

`input_fingerprint` hashes path plus `prose::fingerprint_text(file)` when text exists (`crates/jankurai/src/audit/mod.rs:469-479`). Binary, unreadable, or skipped-large files may become path-only in the audit fingerprint.

For a scoring/report artifact, this is too weak. A changed binary, lockfile, generated artifact, image, wasm, model file, tarball, or compressed artifact can matter.

**Fix:** Fingerprint all files included in inventory using byte hash when feasible:

```text
path
size
mode
sha256(bytes)
text_capture_sha256 if captured
file_kind
skipped_reason
```

If a file is excluded or too large, record `skipped_reason` and include size/mtime/path in the report so it is not invisible.

## P0-10. Finding caps hide total issue volume

`pattern_hits` returns at most 20 hits (`crates/jankurai/src/audit/scan.rs:376-400`), many findings use the first hit only, and language modules often cap samples.

Sample caps are fine for readability, but the report also needs total counts. Otherwise a repo with 21 issues can look similar to a repo with 200 issues.

**Fix:** Every finding family should carry:

```json
{
  "sample_count": 20,
  "total_count": 183,
  "truncated": true,
  "affected_files_count": 41
}
```

Score should use total counts, not only emitted samples.

# 2. Audit-engine improvements needed for world-class scoring

## 2.1 Separate “maturity score” from “defect score”

Right now score combines repo maturity, tool adoption, docs, controls, and findings. That makes it possible for a repo to offset serious gaps with lots of good scaffolding.

Use separate outputs:

```text
coverage_score      Do you have the right lanes/configs/manifests?
evidence_score      Did those lanes run and leave verified receipts?
finding_score       What actual problems were found?
supply_chain_score  Are dependencies/builds/releases trustworthy?
agent_safety_score  Can AI agents safely edit this repo?
overall_decision    pass/fail/advisory based on hard gates and minimums
```

Hard blockers should not be offset by other points. A critical secret, destructive migration, self-baseline ratchet, or unpinned release publish should fail regardless of a high aggregate score.

---

## 2.2 Add “not applicable” support

Some repos do not have Docker, SQL, Python, release artifacts, or frontend code. The current dimensions can reward absence or presence in ways that are hard to interpret.

Add explicit applicability:

```json
{
  "dimension": "docker",
  "applicable": false,
  "reason": "no Dockerfile/container manifest found",
  "score": null
}
```

This prevents false confidence and avoids penalizing repos for irrelevant controls.

---

## 2.3 Add confidence and parser type to every finding

Every finding should say whether it came from:

```text
regex
line heuristic
AST/parser
manifest parser
lockfile parser
executed tool receipt
human-declared policy
```

Then assign confidence:

```text
high     parser/receipt-backed and narrow
medium   text heuristic with local context
low      broad grep signal
```

Low-confidence findings should usually be advisory unless a proof lane confirms them.

---

## 2.4 Make rule metadata map to external standards

Extend `RuleSpec` beyond internal HLT IDs:

```rust
pub struct RuleSpec {
    pub id: &'static str,
    pub cwe: &'static [&'static str],
    pub owasp_asvs: &'static [&'static str],
    pub nist_ssdf: &'static [&'static str],
    pub slsa: &'static [&'static str],
    pub openssf_scorecard: &'static [&'static str],
    pub evidence_level_required: EvidenceLevel,
    pub parser_required: bool,
}
```

This makes Jankurai easier to sell as a serious audit standard and easier to compare against existing security requirements.

---

## 2.5 Do not claim conformance too early

The report sets:

```rust
claimed_conformance_level: "HL3"
```

in `crates/jankurai/src/audit/mod.rs:183`.

That is risky because “claimed” can sound like a certified level even if observed conformance is lower.

**Fix:** Use:

```json
"claimed_conformance_level": null,
"observed_conformance_level": "HLx",
"claim_source": "none|policy|certification|signed_attestation"
```

Only set claimed conformance from a signed/verified certification artifact.

# 3. Missing Rust audit coverage

The Rust coverage is already decent for unsafe and bad behavior, but world-class Rust audit should add these.

## 3.1 Required CI commands

Add hard or release-gate proof for:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features --locked
cargo doc --workspace --all-features --no-deps
cargo test --doc --workspace
```

For this repo specifically, `Justfile check` runs versions, audit, and paper build, but it does not run full workspace tests, clippy, fmt, or UX tests (`Justfile:19-22`). CI only runs one Rust test target for language bad behavior (`.github/workflows/jankurai.yml:90-94`). That is not enough.

## 3.2 MSRV and toolchain pinning

Add audit checks for:

* `rust-toolchain.toml` present;
* MSRV declared;
* CI tests MSRV and stable;
* release build uses pinned toolchain;
* dependency versions are locked for release.

## 3.3 Dependency policy

Add required checks:

* `cargo audit` for RustSec advisories;
* `cargo deny` for advisories, duplicate crates, licenses, bans, and allowed registries;
* `cargo vet` for third-party audit evidence;
* duplicate dependency version policy;
* abandoned/unmaintained crate policy;
* yanked crate detection;
* git dependency restriction;
* crates.io source policy.

## 3.4 Unsafe policy

The current unsafe detector is good, but add stronger governance:

* crate-level `#![forbid(unsafe_code)]` by default;
* if unsafe is allowed, require `unsafe_op_in_unsafe_fn = deny`;
* require `SAFETY:` comments tied to actual invariants, not generic statements;
* require Miri for unsafe-heavy crates;
* require Loom or equivalent model tests for concurrency primitives;
* require fuzz/property tests around unsafe parsers/FFI/binary formats;
* require `cargo geiger`-style inventory as advisory.

## 3.5 Panic and error handling

Add detectors for non-test product code:

* `unwrap()` and `expect()` without bounded invariant;
* `panic!`, `todo!`, `unimplemented!`, `unreachable!`;
* `assert!` on user-controlled input;
* library code returning `anyhow::Result` where typed errors would be better;
* swallowed errors;
* `unwrap_or_default()` on parse/config/security-sensitive paths.

The repo already flags some fallback language, but the audit should distinguish harmless convenience from security/data-loss masking.

## 3.6 Async/concurrency

Add parser-backed checks for:

* blocking filesystem/network calls inside async contexts;
* `std::sync::Mutex` held across `.await`;
* unbounded channels;
* spawned tasks without join/error handling;
* missing cancellation/shutdown path;
* global mutable state;
* atomics without ordering rationale;
* background threads that outlive command execution.

## 3.7 Public API and semver

For crates intended for users:

* run `cargo semver-checks`;
* require changelog entry for public API changes;
* require docs for public API;
* deny broken intra-doc links;
* check package metadata and license files;
* verify published crate contents do not include secrets/test artifacts.

# 7. Missing SQL/database audit coverage

Current SQL checks catch destructive migrations and some bad behavior, but the implementation is too line/keyword based.

## 7.1 Destructive migration proof is too easy to bypass

`migration_safety_evidence_present` returns true if the SQL file contains any marker such as `rollback`, `backfill`, `lock timeout`, `advisory lock`, or `expand-contract` (`crates/jankurai/src/audit/scan.rs:978-997`).

That means a comment like `-- rollback TBD` can suppress a real destructive migration finding.

**Fix:** Require structured migration metadata per statement:

```sql
-- jankurai:migration
-- id: 20260506_drop_old_column
-- risk: destructive
-- rollback: db/migrations/rollback/...
-- lock_timeout: 5s
-- backfill: docs/migrations/...
-- proof: target/jankurai/db/...
-- owner: @db-owner
-- expires: 2026-06-01
```

Then parse and validate each destructive statement.

## 7.2 Use SQL parser or dialect-aware scanner

Line regex is not enough. Add dialect-aware parsing for PostgreSQL:

* `DROP TABLE`;
* `DROP COLUMN`;
* `TRUNCATE`;
* `DELETE` without `WHERE`;
* `UPDATE` without `WHERE`;
* `ALTER TYPE`;
* `ALTER TABLE ... SET NOT NULL`;
* index creation without `CONCURRENTLY`;
* constraints without `NOT VALID` on large tables;
* long locks;
* implicit table rewrites.

## 7.3 Require migration execution proof

For DB changes, require receipts from an ephemeral database:

```text
migration up
migration down or rollback proof
schema diff
constraint validation
query plan for risky paths
lock-timeout proof
application compatibility proof
```

## 7.4 RLS, tenancy, and authz

Add checks for:

* tenant tables have `tenant_id` or documented exemption;
* RLS enabled and forced where expected;
* policies exist for select/insert/update/delete;
* negative tests prove cross-tenant access fails;
* app code cannot bypass tenant filters;
* admin/service roles are isolated.

Current `authz_isolation_hits` treats the repo as safer if any test anywhere contains words like “wrong user”, “forbidden”, or “rls” (`crates/jankurai/src/audit/scan.rs:510-555`). That is too broad. Tests must map to the changed route/table/owner.

## 7.5 Query safety

Add parser/AST checks for:

* SQL string interpolation in Rust/TS/Python;
* parameterized query APIs;
* ORM raw query escape hatches;
* connection string secret handling;
* transaction boundaries;
* N+1 query patterns;
* missing indexes on foreign keys and tenant filters;
* SELECT * in product paths;
* pagination limits;
* user-controlled ORDER BY or column names without allowlist.

# 8. Missing Git/GitHub/CI audit coverage

## 8.1 Workflow action pinning

Current CI hardening only detects `@master` (`crates/jankurai/src/audit/scan.rs:1570-1578`). That misses `@main`, `@stable`, semver tags, and branch tags.

**Fix:** Add severity tiers:

```text
critical: action ref is branch-like: @main, @master, @stable, @latest
high:     action ref is semver tag, not SHA
medium:   official action tag allowed in adoption mode only
pass:     full-length commit SHA with optional comment naming version
```

## 8.2 Token permissions

Add rules for:

* missing top-level `permissions`;
* `permissions: write-all`;
* unnecessary `contents: write`;
* unnecessary `pull-requests: write`;
* `id-token: write` outside attestation/deploy jobs;
* secrets available on PR jobs;

# 12. Missing generated-code audit coverage

Generated-zone support is one of Jankurai’s strengths, but it needs proof stronger than headers.

Current generated identity accepts first-eight-line markers like “generated”, “do not edit”, or “auto-generated” (`crates/jankurai/src/audit/scan.rs:1194-1258`). The manifest metadata check only verifies non-empty `path`, `source`, and `command` (`crates/jankurai/src/audit/scan.rs:1260-1306`).

**Add required proof:**

* generator command exists and is allowlisted;
* generator command executed in CI;
* generated output matches source after regeneration;
* generator version pinned;
* generated file contains source hash;
* generated file contains generator ID/version;
* no manual edits in generated zone;
* generated code touching auth/input/crypto/DB/filesystem requires security lane.

Suggested generated-file header:

```text
// @generated by openapi-client-gen 1.2.3
// source: contracts/api/openapi.yaml
// source-sha256: ...
// command: npm run generate:client
// do-not-edit: true
```

The current future-hostile marker scan catches many terms, but it is broad and can false-positive. Add more semantic checks:

# 22. Safe rollout plan

To avoid breaking teams with noisy rules:

## Phase 1: make the current score honest

Do these first:

1. Fix CI self-baseline.
2. Enforce `fail_on`.
3. Add `evidence_level`.
4. Report total counts behind capped samples.
5. Enforce expired exceptions.
6. Add changed-fast surfaces.
7. Validate every artifact digest.
8. Make strict security lane required on main/release.

## Phase 2: add advisory parser-backed checks

Add as advisory:

* GitHub workflow parser checks;
* Dockerfile/Compose parser checks;
* TS config/Vite config checks;
* Python manifest checks;
* SQL migration metadata parser;
* Rust fmt/clippy/test receipt checks.

## Phase 3: ratchet

Convert from advisory to ratchet only after:

* false positives are measured;
* conformance fixtures exist;
* docs explain remediation;
* findings include safe fix guidance;
* exceptions are scoped and expiring.

## Phase 4: hard gates

Hard-fail only high-confidence issues:

* secrets;
* self-baseline;
* expired high-risk exception;
* destructive migration without structured proof;
* untrusted release artifact;
* security lane disabled/skipped;
* generated security-sensitive drift;
* broad CI token permissions;
* untrusted `pull_request_target`;
* Docker socket/privileged container in CI.

# 24. Bottom line

Jankurai already has the right philosophy: make AI-assisted code auditable, local, owned, routed, and proven. The next level is to make every score answer this question:

> Did the repo merely say it was safe, or did it leave fresh, verified, scoped, tamper-resistant evidence that the changed code was safe?

The biggest missing best practice is not another grep rule. It is **evidence integrity**: baseline integrity, proof receipt integrity, CI integrity, dependency integrity, generated-code integrity, and release artifact integrity. Once those are fixed, the Rust/TypeScript/Python/Docker/SQL-specific coverage can become much more trustworthy without creating noisy, brittle gates.

I read this as more than “a codebase.” It is an **audit/control-plane for killing vibe coding**: a local/CI standard that tries to make AI-assisted changes mergeable only when ownership, tests, proof evidence, security, generated-zone discipline, UX proof, and stack-specific bad-behavior checks are present.

My core conclusion: **the direction is very strong, but the current system can still give confidence too early.** The biggest missing piece is not “more regex rules.” It is **evidence quality**: every green score should prove that the right tools ran, against the right surfaces, from the right baseline, with strict schemas, fresh artifacts, explicit exceptions, and reproducible CI. Right now several controls are advisory, smoke-only, config-present-only, or mismatched between docs and implementation.

One important limitation: I could not fully compile/run the Rust test suite because dependency fetching from crates.io failed in this environment. However, static inspection found a likely compile blocker: `crates/jankurai/src/audit/mod.rs` declares `pub mod prose;`, and `audit/helpers.rs` imports `crate::audit::prose`, but I did not find `crates/jankurai/src/audit/prose.rs` or `crates/jankurai/src/audit/prose/mod.rs` in the archive.

# Executive summary

## What is already good

You already have many of the right ideas:

* A clear “anti-vibe coding” thesis.
* A Rust CLI with repo scoring, SARIF-style findings, repair queues, ownership/test maps, generated-zone detection, and ratchet mode.
* A 37-rule HLT catalog covering core engineering risks and language packs.
* Separate proof tools: `proofbind` and `proofmark`.
* UX QA tooling with screenshots, ARIA snapshots, axe integration, visual baselines, and UI-state expectations.
* Security lane wrappers for tools such as gitleaks, cargo-audit, npm audit, Syft, and zizmor.
* Docs that correctly distinguish local smoke checks from human/product review.
* Conformance fixtures for important failure cases.

That is a serious foundation.

## The biggest gaps

The most important gaps I would fix first are:

1. **The uploaded repo appears to reference a missing Rust module**: `audit::prose`.
2. **CI ratchet mode creates the baseline from the current candidate run**, which defeats the point of ratcheting.
3. **GitHub Actions permissions are not explicitly least-privilege**, and actions are tag-pinned rather than SHA-pinned.
4. **Proofbind/proofmark are advisory in repo config**, so important missing proof evidence can still pass.
5. **Docs, policy, and scoring weights drift from implementation.**
6. **Security docs promise more than policy enforces.**
7. **Security tool outputs are not normalized into real severity decisions.**
8. **UX CI validates a static smoke page, not the product surfaces.**
9. **The audit rules are mostly text/regex based, but some categories need AST, schema, or artifact-aware checks.**
10. **Reports sample only the first few findings without exposing full counts/truncation clearly enough.**
11. **Exceptions/allow comments are too weak for a serious engineering control.**
12. **Schemas are too permissive in places where strict contracts matter.**
13. **The README `100/100` badge is risky because the audit can be green while compile, baseline, proof, security, and doc-policy parity issues remain.**

## 1. Fix the missing Rust module before trusting any score

Static inspection found:


## 2. Fix CI ratchet baseline generation

In `.github/workflows/jankurai.yml`, the audit job creates a baseline from the current run and then ratchets against it. That is a critical gap.

Current pattern:

```bash
cargo run -p jankurai -- . --json agent/repo-score.json
cp agent/repo-score.json target/jankurai/baseline-score.json
cargo run -p jankurai -- audit . --mode ratchet --baseline target/jankurai/baseline-score.json ...
```

This makes the baseline equal to the candidate, so regressions can be hidden. Your README correctly says the ratchet baseline should come from an accepted baseline, not the current candidate. The CI implementation should match that.

**Fix:**

Use a committed or previously published accepted baseline, for example:

```bash
cargo run -p jankurai -- audit . \
  --mode ratchet \
  --baseline agent/accepted-baseline.json \
  --json target/jankurai/repo-score.json
```

Then publish the candidate score as an artifact, but do not replace the accepted baseline automatically.

**Better policy:**

* `agent/accepted-baseline.json` is updated only by a deliberate governance PR.
* Candidate PRs may improve the baseline.
* Candidate PRs may not silently lower it.
* Baseline changes require CODEOWNER review.
* The report should include:

  * `accepted_baseline_score`
  * `candidate_score`
  * `delta`
  * `baseline_source`
  * `baseline_sha256`
  * `baseline_commit`
  * `is_baseline_from_current_run: false`

## 3. Add explicit least-privilege GitHub Actions permissions

The workflow does not declare top-level `permissions:`. That should be fixed.

GitHub’s own guidance recommends pinning third-party actions to a full-length commit SHA for immutable releases, and OpenSSF Scorecard includes checks for token permissions and pinned dependencies. GitHub artifact attestations also provide provenance/integrity guarantees for build outputs. ([GitHub Docs][1])

At the top of every workflow:

```yaml
permissions:
  contents: read
```

Then elevate only where needed, for example:

```yaml
permissions:
  contents: read
  security-events: write   # only for SARIF upload jobs
  id-token: write          # only for attestation/signing jobs
  attestations: write      # only for artifact attestations
```

For checkout:

```yaml
- uses: actions/checkout@<full_commit_sha>
  with:
    persist-credentials: false
```

For artifacts, consider:

```yaml
- uses: actions/upload-artifact@<full_commit_sha>
  with:
    name: jankurai-audit
    path: target/jankurai/
    retention-days: 14
```

```toml
# local dev
```

Then promote high-confidence proof categories to required.

## 6. Make the security policy match the security matrix

`docs/security-tool-matrix.md` is stronger than `agent/security-policy.toml`. The docs mention required CI tools such as gitleaks, cargo audit, npm audit, and zizmor, and recommended/release tools such as Semgrep, CodeQL, cargo-deny, Syft, Grype/Trivy, OpenSSF Scorecard, SLSA/Cosign. The actual policy makes far fewer things required.

This creates a false sense of compliance.

Security tooling should be tiered:

| Tier             | Tooling                                                                 | Gate behavior                                |
| ---------------- | ----------------------------------------------------------------------- | -------------------------------------------- |
| Local minimum    | gitleaks, format, unit tests                                            | fail on secrets / compile breaks             |
| PR required      | gitleaks, cargo-audit, npm audit, zizmor, CodeQL or Semgrep, cargo-deny | fail on high/critical or policy violations   |
| Release required | SBOM, Grype/Trivy, Scorecard, artifact attestations, signed release     | fail if missing provenance or critical vulns |
| Advisory         | experimental tools                                                      | report only                                  |

zizmor is specifically a static analysis tool for GitHub Actions, gitleaks is for secret detection, Syft generates SBOMs, and Grype scans SBOMs/container images/filesystems for vulnerabilities. CodeQL is GitHub’s code scanning engine. ([GitHub][2])

# P1: scoring and audit model gaps

## 9. Score should reward evidence maturity, not config presence

A world-class audit needs evidence levels.

Right now several areas look like they can score because files or configs exist. That is not enough.

Use tiers:

| Evidence level | Meaning                                                        | Score credit          |
| -------------- | -------------------------------------------------------------- | --------------------- |
| L0             | no control                                                     | 0                     |
| L1             | config exists                                                  | small                 |
| L2             | local command configured                                       | low                   |
| L3             | CI command ran                                                 | medium                |
| L4             | artifact exists and validates against schema                   | high                  |
| L5             | artifact is fresh, tied to current commit, and policy-enforced | full                  |
| L6             | negative/adversarial proof also passes                         | bonus / release-grade |

Example: a `proof-plan.json` file should not earn full proof credit unless:

* it validates against strict schema
* it maps to changed surfaces
* commands ran successfully
* artifacts exist
* artifacts hash correctly
* generated report references the same commit
* exceptions are approved and unexpired

## 10. Add artifact freshness checks

Every evidence artifact should carry:

## 12. Report all counts, not just first examples

Many detectors take the first hit or cap findings to a small sample. That is good for readability, but dangerous if the report hides scale.

Every finding group should include:

```json

  "rule_id": "HLT-031-TS-ANY-BOUNDARY",
  "severity": "high",
  "sample_findings": [...],
  "total_findings": 47,
```

## 13. Add exception governance

Current inline allow logic accepts comments like:

```text
jankurai:allow <detector-id> reason=... expires=YYYY-MM-DD
```

That is a good start, but world-class audits need stronger exception metadata.

Require:

```text
jankurai:allow HLT-031-TS-ANY-BOUNDARY
reason="validated by schema at api/user.ts:44"
risk="runtime type escape"
expires="2026-08-01"
owner="@platform-security"
issue="SEC-1234"
approved_by="@staff-engineer"
compensating_control="zod schema UserResponse.safeParse"
```

The audit should fail if:

* expiry is missing
* expiry is in the past
* owner is missing
* issue is missing for high/critical
* approval is missing for high/critical
* compensating control is missing
* allow appears too far from the risky line
* allow references an unknown detector ID
* allow is used in generated code without generated-zone metadata

Also add a central exception registry so inline exceptions can be reviewed and aged out.

# P1: Rust audit coverage gaps

The Rust language pack is good as a first pass, but world-class Rust auditing needs deeper coverage around unsafe, concurrency, error handling, FFI, dependency governance, and testing.

The Rustonomicon is the official deep guide to unsafe Rust, and Miri is designed to detect undefined behavior in Rust binaries and test suites. cargo-deny and cargo-vet cover dependency policy/audit use cases that regex cannot. ([Rust Documentation][5])

## 21. Unsafe Rust should require proof, not just comments

Current checks include:

* undocumented unsafe blocks
* public unsafe fn missing `# Safety`
* unsafe Send/Sync impl
* transmute
* assume_init/zeroed
* unchecked indexing
* raw parts
* static mut
* repr(packed)

Add required proof metadata for every unsafe site:

```rust
// SAFETY:
// invariant: ptr is non-null, aligned, initialized, and valid for len
// proof: tests/unsafe_buffer.rs::rejects_invalid_len
// miri: cargo +nightly miri test -p crate unsafe_buffer
// fuzz: cargo fuzz run parse_buffer
unsafe { ... }
```

The audit should require:

* `SAFETY:` section
* stated invariant
* link to test
* Miri proof for unsafe-heavy crates
* fuzz target for parsers/FFI/binary formats
* review owner for unsafe code
* no broad `allow(unsafe_code)` without justification

# P1: SQL / PostgreSQL audit coverage gaps

## 31. Add tenant/RLS checks

* tenant column

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY documents_tenant_isolation
```

# P1: proofbind / proofmark gaps

## 46. Move from line-based proof to symbol/surface-based proof

`proofmark` currently works from changed lines. That is useful, but it misses semantic changes.

Better model:

```json
{
  "changed_surfaces": [
    {
      "language": "rust",
      "kind": "public_fn",
      "symbol": "audit::run",
      "file": "crates/jankurai/src/audit/mod.rs",
      "lines": [120, 220],
      "risk_tags": ["policy_decision", "file_io"],
      "required_proofs": ["unit", "negative", "snapshot"]
    }
  ]
}
```

Use AST-aware discovery:

* Rust: `syn` or rustdoc JSON
* TypeScript: TypeScript compiler API
* SQL: SQL parser or migration analyzer
* Python: `ast`
* Docker/YAML: structured parser

Line-based proof can remain as a fallback.

---

## 47. Mutation unavailable should not be equivalent to pass in release mode

`proofmark` treats mutation status `unavailable` as acceptable if coverage and negative proofs pass. That is fine in advisory mode. It should not be release-grade.

Policy:

| Mode    | Mutation unavailable                |
| ------- | ----------------------------------- |
| local   | advisory warning                    |
| PR      | review warning for business logic   |
| release | fail for required mutation surfaces |

Surfaces requiring mutation or equivalent negative proof:

* score calculation
* policy decision
* authz
* input validation
* SQL migration safety
* generated-zone mutation
* security normalization
* proof routing
* release gates

---

## 48. Add proof command allowlist

Proof evidence should not be able to claim arbitrary commands.

Bad:

```json
{
  "proof_command": "echo pass"
}
```

Good:

```json
{
  "proof_command_id": "cargo-test-workspace",
  "resolved_command": "cargo test --workspace --locked",
  "allowlisted": true
}
```

Maintain:

```toml
[proof_commands.cargo_test_workspace]
command = "cargo test --workspace --locked"
required_for = ["rust", "policy", "core"]
```

# The standard I would aim for

A world-class Jankurai pass should mean:

> The code compiles from a clean checkout, uses locked dependencies, passes required tests, has ownership and proof evidence for changed surfaces, validates untrusted inputs, blocks known security hazards, enforces generated-code boundaries, checks UX/accessibility on real product routes, produces fresh machine-validated artifacts tied to the current commit, and fails closed unless exceptions are explicit, owned, approved, and unexpired.

That is the difference between “we ran some audits” and “this merge is actually defensible.”

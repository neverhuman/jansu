# Jankurai full audit-design review: missing best practices and scoring gaps

I unpacked the uploaded archive and reviewed the repo at source/design level. I focused on the audit/scoring engine, rule registry, caps, finding builder, CI workflow, security lane, tool adoption config, Rust/TypeScript/Python/Docker/SQL language rules, schemas, tests, docs, and the “vibe coverage” registry. I could not execute a full build or CI run in this environment because `cargo` is not installed here, so this is a static audit-design review, not a passed/failed local CI result.

The repo is trying to do something valuable and unusual: **make AI-assisted merges auditable by killing fake proof, dead/stub code, boundary drift, generated-code mutation, missing ownership, missing proof lanes, and agent overreach.** In other words, this is not just a linter. Jankurai is becoming a repository control plane for “no-vibe” engineering: every merge should have ownership, proof, reproducible evidence, scoped repair guidance, and low ambiguity.

My main conclusion: **the concept is strong, but the current audit/scoring system still has too many ways to earn a high score from marker presence, self-generated evidence, advisory-only lanes, incomplete enumeration, and local-only repo files.** To become “best available standard,” Jankurai needs to distinguish **claim, marker, command, CI receipt, external platform evidence, and cryptographic provenance** as different evidence levels.

## 1. Highest-priority issues I would fix first

### P0 — The uploaded archive appears to contain a build-breaking missing module

In the uploaded archive, `crates/jankurai/src/audit/mod.rs` declares:

```rust
pub mod prose;
```

and at least 24 audit paths call `prose::...`, including `prose::allows_word_scan`, `prose::is_trusted_policy_path`, and `prose::fingerprint_text`. But I did not find `crates/jankurai/src/audit/prose.rs` or `crates/jankurai/src/audit/prose/mod.rs` in the tarball.

That is not an audit-coverage issue; it is a **release-blocking integrity issue**. A world-class audit tool must not ship an archive that is missing a module used by the audit engine.

**Recommended audit rule:** add a hard cap:

```text
source-tree-does-not-compile-or-module-missing
max_score = 40
severity = critical
rule = HLT-038-SOURCE-TREE-INTEGRITY
```

**Low-risk fix:** add CI gates for:

```bash
cargo check --workspace --all-targets --all-features --locked
cargo test --workspace --all-targets --all-features --locked
```

and make the archive/package job verify that the exact released tarball builds from a clean extraction.

### P0 — The ratchet baseline is self-generated in CI

Your docs say ratchet mode must use an accepted baseline, and “no implicit current score can become the baseline.” The uploaded workflow does the opposite:

```yaml
- name: Generate CI ratchet baseline
  run: |
    jankurai . --json agent/repo-score.json --md agent/repo-score.md
    cp agent/repo-score.json target/jankurai/baseline-score.json

- name: jankurai audit
  run: jankurai audit . --mode ratchet --baseline target/jankurai/baseline-score.json ...
```

That makes the candidate checkout create its own ratchet baseline. A bad PR can become its own comparison point. This is the most important scoring gap.

**Best-standard behavior:** ratchet baseline must come from one of:

1. a committed, reviewed `agent/accepted-baseline.json`;
2. the latest successful protected `main` artifact;
3. a signed release artifact;
4. an explicitly approved human baseline with digest and git SHA.

**Audit rule to add:**

```text
self-generated-ratchet-baseline
severity = critical
max_score = 60
evidence = workflow step writes baseline then immediately consumes it
```

**Code fix:** the audit should fail if the baseline artifact has the same `run_id`, same `generated_at`, or same candidate commit as the report being evaluated unless explicitly in advisory/demo mode.

### P0 — Malformed ratchet baselines silently fall back to current score

In `crates/jankurai/src/main.rs`, `apply_mode_and_baseline` parses the baseline score like this:

```rust
let baseline_score = serde_json::from_str::<serde_json::Value>(&text)
    .ok()
    .and_then(|value| value.get("score").and_then(|score| score.as_i64()))
    .unwrap_or(report.score as i64) as i32;
```

If the baseline JSON is malformed or lacks `score`, the current report score becomes the baseline. That is a false-green path.

**Best-standard behavior:** malformed, missing, stale, or unbound baseline is a hard fail in ratchet/release mode.

**Fix:**

```rust
let value: serde_json::Value = serde_json::from_str(&text)
    .with_context(|| format!("parse ratchet baseline `{path}`"))?;

let baseline_score = value
    .get("score")
    .and_then(|score| score.as_i64())
    .ok_or_else(|| anyhow::anyhow!("baseline `{path}` has no integer `score`"))? as i32;
```

Then additionally verify:

```text
baseline.report_fingerprint exists
baseline.input_fingerprint exists
baseline.git.head exists
baseline.standard_version compatible
baseline.schema_version compatible
baseline.generated_at older than candidate
baseline.source = accepted|main-success|release, not candidate
```

### P0 — Security lane is not strict in CI

The workflow runs:

```yaml
jankurai security run . --out target/jankurai/security/evidence.json
```

without `--strict`.

`tools/security-lane.sh` makes missing tools advisory outside strict mode. The policy requires only `gitleaks`; `cargo audit`, `npm audit`, `syft`, and `zizmor` are advisory or script-level advisory. The wrapper records blocking status but does not fail the audit just because a policy-required parsed step is blocking; it mainly fails on the script exit code.

This means the report can contain “security evidence” while important tools were skipped or advisory.

**Best-standard behavior:** security evidence must have an explicit enforcement level:

```text
marker_only       = script/config exists
command_seen      = workflow mentions command
local_ran         = command ran locally
ci_ran            = command ran in CI
ci_blocking       = command failure blocks merge
ci_strict_current = command ran against current commit and failed on policy
```

Only `ci_blocking` or `ci_strict_current` should remove serious caps.

**Fix workflow:**

```yaml
- name: Security lane
  run: jankurai security run . --strict --out target/jankurai/security/evidence.json
```

**Fix policy:** make these required for CI/release posture:

```toml
required_tools = [
  "gitleaks",
  "cargo-audit",
  "cargo-deny",
  "npm-audit",
  "osv-scanner",
  "zizmor",
  "syft",
  "grype-or-trivy",
]
```

GitHub’s dependency review is also specifically designed to catch vulnerable dependency changes in pull requests, and by default the action fails on vulnerable packages; Jankurai should treat that as high-value PR evidence, not merely a local marker. ([GitHub Docs][1])

### P0 — CI does not enforce the repo’s own PR validation checklist

`.github/PULL_REQUEST_TEMPLATE.md` asks contributors to run:

```text
cargo fmt --all
cargo test -p jankurai --test command_surface_smoke
cargo test -p jankurai
just fast
just score
git diff --check
```

But the workflow I reviewed does not enforce the full list. It runs a lot of Jankurai-specific evidence commands, but the only explicit Rust test command in the main audit job is:

```bash
cargo test -p jankurai --test language_bad_behavior
```

A world-class audit cannot substitute audit reports for the underlying build/test/lint/typecheck gates.

**Add a separate required `quality` job:**

```yaml
permissions:
  contents: read

jobs:
  quality:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@<full-length-sha>
        with:
          fetch-depth: 0
      - uses: dtolnay/rust-toolchain@<full-length-sha>
        with:
          toolchain: stable
          components: rustfmt, clippy
      - uses: actions/setup-node@<full-length-sha>
        with:
          node-version: "22"
          cache: npm
      - run: npm ci
      - run: cargo fmt --all --check
      - run: cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
      - run: cargo test --workspace --all-targets --all-features --locked
      - run: npm --workspace @jankurai/ux-qa run build
      - run: npm --workspace @jankurai/ux-qa run test
      - run: git diff --check
```

Then Jankurai should audit whether this baseline quality job exists and is required.

The workflow uses tag refs like:

For a world-class gate, action pinning should be either:

1. full-length SHA pinning, or
2. explicitly accepted trusted first-party action with Dependabot/Renovate update policy and Scorecard evidence.

## 2. The biggest scoring-system gap: evidence levels are too flat

Right now, many parts of the audit treat these as too similar:

```text
file exists
keyword appears
command appears in workflow
tool exists in config
tool ran locally
tool ran in CI
tool failed the build
artifact is bound to this commit
artifact is cryptographically signed
GitHub API proves branch protection / code scanning / secret scanning
```

A world-class scoring system must not treat those as equivalent.

### Add an evidence maturity ladder

Every control should report one of these:

| Evidence level                | Meaning                                              | Should it remove a hard cap? |
| ----------------------------- | ---------------------------------------------------- | ---------------------------: |
| E0 Unknown                    | Audit cannot determine status                        |                           No |
| E1 Marker                     | File/path/keyword/config exists                      |     No for critical controls |
| E2 Command configured         | Workflow or script contains command                  |                   Usually no |
| E3 Local receipt              | Command ran and wrote a valid artifact               |                    Sometimes |
| E4 CI receipt                 | Command ran in CI for current commit                 |        Yes for many controls |
| E5 CI blocking receipt        | Failure blocks merge/release                         |                          Yes |
| E6 External platform evidence | GitHub/API/security setting/provenance verified      |                          Yes |
| E7 Cryptographic provenance   | signed attestations/SBOM/release provenance verified |     Yes for release controls |

Then the report should show:

```json
{
  "control_id": "HLT-016-SUPPLY-CHAIN-DRIFT",
  "status": "pass",
  "evidence_level": "E5_CI_BLOCKING",
  "confidence": "high",
  "artifact": "target/jankurai/security/evidence.json",
  "artifact_sha256": "...",
  "git_head": "...",
  "ci_run_id": "...",
  "blocking": true,
  "freshness": "current_commit"
}
```

### Do not reward unknowns

The report should distinguish:

```text
pass
fail
unknown
not_applicable
advisory_only
marker_only
stale_evidence
suppressed
waived_with_expiry
```

A high-impact control that is `unknown` should not silently add points. It should either be neutral or score-limiting.

## 3. External standards mapping is missing

Jankurai has strong internal HLT rules, but a “best available standard” audit should map each control to external standards. This is not bureaucratic; it prevents Jankurai from becoming self-referential.

The core external baselines I would map to are:

* **NIST SSDF SP 800-218** for secure software development practices. NIST describes SSDF as a core set of high-level secure software development practices to reduce vulnerabilities, mitigate impact, and address root causes. ([NIST Computer Security Resource Center][3])
* **OWASP ASVS 5.0.0** for web/API technical controls. OWASP says ASVS provides a basis for testing web application technical security controls and secure development requirements. ([OWASP Foundation][4])
* **OWASP SAMM** for secure SDLC maturity. SAMM is explicitly designed as an effective and measurable way to analyze and improve the secure development lifecycle across the complete lifecycle. ([OWASP Foundation][5])
* **OWASP API Security Top 10 2023** for API-specific risk coverage, especially BOLA, broken authentication, object property authorization, resource consumption, SSRF, and unsafe API consumption. ([OWASP Foundation][6])
* **SLSA 1.2** for supply-chain provenance and build/source integrity. SLSA defines levels and tracks for incrementally improving supply-chain security, including provenance. ([SLSA][7])
* **NIST SP 800-218A** for AI/agent/model-specific secure development practices if Jankurai is scoring AI-agent and prompt/tooling surfaces. ([NIST Computer Security Resource Center][8])
* **GitHub Code Scanning, Secret Scanning, and Dependency Review** as hosted platform evidence. GitHub documents code scanning as a way to find vulnerabilities and prevent introducing new problems, secret scanning as scanning entire Git history and collaboration surfaces for secrets, and dependency review as PR-level dependency-change security evidence. ([GitHub Docs][9])

### Add this to `RuleSpec`

Current `RuleSpec` has:

```rust
id
name
category
tlr
lane
docs_url
owner_hint
evidence_kind
severity
repairable
repair_eligibility
repair_risk
status
standard_section
cap_key
confidence_policy
```

Add:

```rust
external_refs: &'static [&'static str],
cwe_refs: &'static [&'static str],
asvs_refs: &'static [&'static str],
ssdf_refs: &'static [&'static str],
slsa_refs: &'static [&'static str],
owasp_api_refs: &'static [&'static str],
applies_to: &'static [&'static str],
evidence_min_level: EvidenceLevel,
detector_kind: DetectorKind,
false_positive_risk: RiskLevel,
false_negative_risk: RiskLevel,
fixture_suite: &'static str,
```

Example:

```rust
RuleSpec {
  id: "HLT-016-SUPPLY-CHAIN-DRIFT",
  external_refs: &[
    "NIST-SSDF-PS.2",
    "NIST-SSDF-PS.3",
    "SLSA-v1.2-Build-L1",
    "OpenSSF-Scorecard-Pinned-Dependencies",
    "GitHub-Dependency-Review"
  ],
  evidence_min_level: EvidenceLevel::CiBlocking,
  detector_kind: DetectorKind::CiArtifactAndPlatformApi,
  ...
}
```

## 4. Current audit positives worth preserving

Before listing gaps, it is important to call out what is already strong:

1. **Hard caps** are the right scoring primitive. A repo should not offset critical missing proof with nice docs.
2. **Findings include agent-oriented repair guidance**, not just “bad pattern found.”
3. **Rule registry includes repair eligibility and risk**, which is excellent for safe agent repair.
4. **Owner map, test map, generated-zone manifest, proof lanes, and boundaries** are good anti-vibe primitives.
5. **Security, UX, proofbind, proofmark, vibe coverage, and release evidence artifacts** are moving in the right direction.
6. **Language bad-behavior rules** already cover many high-signal patterns in Rust, TypeScript, Python, SQL, Docker, CI, Git, Git tools, and release scripts.
7. **Schemas and compatibility tests** show awareness that the report is a contract.
8. **The vibe coverage registry honestly marks most rows as partial**. In the archive, `agent/vibe-coverage.toml` maps 260 issues, with 243 marked `partial` and 17 `detector-backed`. That distinction is exactly the kind of honesty that should feed the score.

The next step is to make the scoring engine just as honest as the registry.

## 5. Report schema gaps

The current `Finding` model is useful, but not enough for world-class scoring. It has severity, category, path, problem, agent fix, evidence, check id, hardness, confidence, evidence kind, rerun command, fingerprint, rule ID, TLR, lane, docs URL, owner, line, matched term, and reason.

Missing fields I would add:

```rust
pub struct Finding {
    pub occurrence_count: usize,
    pub occurrences: Vec<FindingOccurrence>,
    pub sampled: bool,
    pub detector_kind: DetectorKind,
    pub evidence_level: EvidenceLevel,
    pub control_status: ControlStatus,
    pub external_refs: Vec<String>,
    pub cwe_refs: Vec<String>,
    pub cvss_vector: Option<String>,
    pub asvs_refs: Vec<String>,
    pub ssdf_refs: Vec<String>,
    pub slsa_refs: Vec<String>,
    pub owasp_api_refs: Vec<String>,
    pub artifact_refs: Vec<EvidenceArtifactRef>,
    pub source_digest: Option<String>,
    pub scan_truncated: bool,
    pub suppression: Option<SuppressionInfo>,
    pub waiver: Option<WaiverInfo>,
    pub expires_at: Option<String>,
    pub owner_required: bool,
    pub human_review_required: bool,
    pub confidence_reason: String,
}
```

And:

```rust
pub struct FindingOccurrence {
    pub path: String,
    pub start_line: usize,
    pub end_line: Option<usize>,
    pub start_col: Option<usize>,
    pub end_col: Option<usize>,
    pub snippet_hash: String,
    pub matched_term: Option<String>,
}
```

### Why this matters

A single exemplar is good for Markdown, but repair and scoring need full scope. The current builder often emits the first hit or caps samples:

* first TODO/stub hit;
* first fallback soup hit;
* first duplicate block;
* first wrong-layer DB hit;
* first prompt injection hit;
* first secret-like hit;
* `take(10)` for owner/test map gaps;
* `take(4)` for soft dimension evidence.

That makes the report concise, but it weakens repair planning and scoring. A best-standard report should show:

```text
finding.problem = "TODO/stub markers in product code"
occurrence_count = 47
sampled = true
sample_size = 10
repair_strategy = "grouped"
```

The Markdown can still show 5 examples; the JSON/SARIF/repair queue should know the full count.

## 6. Input fingerprint and scan truncation gap

`read_text_sample` captures only the first `max_capture_chars` characters of each text file. Default is 120,000 chars. The audit then reasons over captured text. That is fine for speed, but it creates two problems:

1. A secret, TODO, unsafe pattern, destructive SQL, or bad workflow pattern after the capture window can be missed.
2. Input/report fingerprints can become misleading if they are based on sampled text rather than full file digest.

**Best-standard fix:**

Add to `FileInfo`:

```rust
pub sha256: String,
pub text_sha256: Option<String>,
pub captured_chars: usize,
pub total_bytes: u64,
pub truncated: bool,
pub capture_strategy: String,
```

Then:

* use full file SHA for `input_fingerprint`;
* use sampled text for heuristic scans;
* run streaming full-file detectors for secrets, dangerous CI, destructive SQL, and high-risk patterns;
* add a cap if high-risk files are truncated without full streaming scan.

**New cap:**

```text
high-risk-file-truncated-without-streaming-scan
max_score = 80
severity = high
```

## 7. Archive hygiene gap

The uploaded archive includes many macOS AppleDouble/resource-fork files such as `._README.md`, `._Cargo.toml`, etc. `WalkBuilder` uses `.hidden(false)`, and I did not see a default exclusion for `._*` or `__MACOSX`.

This can create noisy scans if users audit an extracted archive rather than a clean git checkout.

**Fix:**

Add default excludes:

```rust
const EXCLUDED_BASENAMES: &[&str] = &[".DS_Store"];
const EXCLUDED_PREFIXES: &[&str] = &["._"];
const EXCLUDED_DIRS: &[&str] = &["__MACOSX", ...];
```

And add an audit finding:

```text
archive-resource-fork-files-present
severity = low
category = hygiene
agent_fix = "remove AppleDouble/resource fork files from the archive or ignore them by default"
```

## 8. Cap/scoring architecture gaps

### 8.1 `CAP_SPECS` and `CAPS` are duplicated

`caps.rs` has both rich `CAP_SPECS` and a separate `CAPS` tuple list. This is a drift risk.

**Fix:** compute scoring from `CAP_SPECS` only:

```rust
pub fn cap_max_score(key: &str) -> Option<i32> {
    CAP_SPECS.iter().find(|c| c.key == key).map(|c| c.max_score)
}
```

Then generate `hard_rules` from `CAP_SPECS`.

### 8.2 Policy config is not fully authoritative

`agent/audit-policy.toml` has cap values, but the hard-coded caps appear to be the source of truth. That can confuse users who think policy changes alter behavior.

**Fix:** support a policy overlay:

```toml
[caps.no-security-lane-on-high-risk-repo]
max_score = 60
mode = "hard"
required_evidence = "ci_blocking"
```

Report the effective policy:

```json
"effective_policy": {
  "source": ["builtin", "agent/audit-policy.toml"],
  "overrides_applied": [...]
}
```

### 8.3 `fail_on` is not fully honored

`load_policy` reads `fail_on`, but `report_decision` hard-codes failure on `high` and `critical`.

**Fix:**

```rust
fn report_decision(score, findings, policy) {
    let fail_on = policy.fail_on;
    let blocking = findings.iter().filter(|f| fail_on.contains(&f.severity));
}
```

### 8.4 Claimed vs observed conformance is too coarse

The report claims HL3 and observes HL3/HL2-ish states. For world-class scoring, conformance should be a matrix:

```text
HL0 = inventory only
HL1 = advisory local evidence
HL2 = CI evidence present
HL3 = CI blocking + ratchet + owner/test maps
HL4 = external platform evidence + strict security + coverage/mutation/fuzz
HL5 = release provenance + signed artifacts + verified SBOM + protected branch/release
```

## 9. Marker-only evidence gaps

Several helper functions rely on marker/path/text evidence. That is acceptable for discovery, but not for high-confidence scoring.

Examples:

* `has_one_command`
* `has_fast_lane`
* `has_security_lane`
* `has_secret_or_dependency_scans`
* `has_rust_property_tests`
* `has_rust_integration_tests`
* `has_web_surface`
* `paths_with`

Specific issue: `has_secret_or_dependency_scans` can be satisfied by one marker like `tools/security-lane.sh` or `gitleaks` text. A world-class security posture should require an expected set of tools and current CI evidence.

**Recommended model:**

```text
detected = marker exists
configured = policy declares expected tool
runnable = command can be executed
ran = receipt exists
blocking = CI gate failed/passed based on policy
verified = artifact is current and bound to commit
```

Do not let `detected` count as `verified`.

## 10. CI/GitHub/repository posture coverage gaps

Jankurai currently audits repo-local files well. A world-class Git audit must also inspect **hosted platform state** through GitHub API or exported evidence. Local files cannot prove branch protection, required checks, signed releases, or secret scanning settings.

### Add GitHub API-backed controls

Audit:

```text
branch protection / rulesets enabled
required status checks include quality, audit, security
required PR review count >= policy
stale review dismissal enabled
CODEOWNERS review required
admin bypass disabled or justified
force pushes disabled
deletions disabled
linear history policy if desired
signed commits/tags required if policy says so
default branch protected
private vulnerability reporting enabled
security policy present
secret scanning enabled
push protection enabled where available
code scanning enabled
dependency graph enabled
Dependabot or Renovate enabled
dependency review required on PRs
```

Secret scanning matters because GitHub scans full Git history and other collaboration surfaces for secrets when enabled; Jankurai’s local scanner cannot fully replace that hosted capability. ([GitHub Docs][10])

### Add workflow hardening controls

Audit:

```text
top-level permissions exists
default permissions contents: read
jobs escalate only when needed
third-party actions pinned to full SHA or accepted exception
no pull_request_target + checkout head
no secrets on untrusted PR path
no direct untrusted expressions in run
timeout-minutes on every job
concurrency cancel-in-progress for PR jobs
cache keys include lockfile hash and safe restore keys
artifact retention is bounded
artifact paths exclude secrets, .env, credentials, SSH keys
workflow changes require CODEOWNERS
release workflows use protected environments
OIDC tokens use audience/subject constraints
```

GitHub documents script injection risk from attacker-controlled workflow contexts such as PR titles and branch names; Jankurai should audit these patterns directly. ([GitHub Docs][11])

### Add OpenSSF Scorecard ingestion

OpenSSF Scorecard should not replace Jankurai, but it should be ingested as external corroborating evidence for:

```text
branch protection
pinned dependencies
token permissions
dangerous workflow patterns
SAST
dependency update tool
fuzzing
maintained status
license
security policy
signed releases
```

## 11. Supply-chain and release provenance gaps

Jankurai has release-readiness and release-bad-behavior checks, and the docs mention SBOM/provenance. But “best available” release scoring needs artifact-level proof.

SLSA 1.2 is the right reference point: it organizes supply-chain security into levels and tracks, and includes provenance/attestation concepts for build and source integrity. ([SLSA][7]) GitHub artifact attestations also provide cryptographically signed provenance and integrity claims tied to workflow, repo, commit SHA, and triggering event. ([GitHub Docs][12])

### Add release evidence requirements

For release mode, require:

```text
signed tag
tag protected / immutable
release built from protected branch or protected workflow
artifact checksums
SBOM generated
SBOM digest included
vulnerability scan of artifact/container
license scan
SLSA provenance generated
provenance verified
artifact signature generated
artifact signature verified
release notes/changelog generated
version source is single authority
rollback instructions
security advisory process
```

### Add new caps

```text
release-without-signed-tag
max_score = 75

release-without-sbom
max_score = 80

release-without-vulnerability-scan
max_score = 80

release-without-provenance
max_score = 70

release-provenance-not-verified
max_score = 75

release-artifact-not-bound-to-source
max_score = 70
```

# The core recommendation

Keep Jankurai’s anti-vibe identity, but make the scoring brutally evidence-aware:

**A marker is not proof. A script is not proof. A local receipt is not CI proof. A CI pass is not platform protection. A release artifact is not trustworthy without provenance. Unknown is not pass. Advisory is not blocking. Candidate-generated baseline is not a ratchet.**

That principle will move Jankurai from “excellent repo hygiene scanner” toward a credible world-class audit standard for Rust/Vite/TypeScript/Python/Docker/SQL code built in Git.

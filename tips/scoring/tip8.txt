# Jankurai audit gap report for the uploaded code snapshot

I understand the goal as: **Jankurai is not just a linter. It is a repo control plane for killing vibe coding by forcing agent/human merges to be localizable, provable, auditable, repairable, and hard to fake.** The README says the public loop is “find vibe artifacts, prove the merge, repair the repo,” and that proof means repository-local evidence receipts, not formal full-program proof (`README.md:14-21`). The audit rubric also says the current audit is strict but **not a general-purpose repo quality score**; it is focused on whether an agent can safely reject, localize, prove, audit, and repair without turning shortcuts into production behavior (`docs/audit-rubric.md:7`).

That framing is good. The biggest missing step is this:

**Jankurai should become evidence-native, not marker-native.**
Right now, several scoring paths can award strong credit when tools, words, docs, or command strings exist. World-class scoring should only award top-band credit when evidence is actually executed, parsed, severity-gated, uploaded, fingerprinted, and, for release, signed or attested.

I could not run `cargo` in this execution environment because the toolchain is not installed, so this is a static source audit of the uploaded archive. However, the static pass found one likely compile blocker and many scoring/control-plane gaps.

---

## Immediate critical issues in the uploaded snapshot

### 1. Uploaded snapshot appears to be missing a Rust module required by compilation

`crates/jankurai/src/audit/mod.rs` declares:

```rust
pub mod prose;
```

at `crates/jankurai/src/audit/mod.rs:15`.

Two files import it:

```rust
use crate::audit::prose;
```

at `crates/jankurai/src/audit/helpers.rs:1`, and:

```rust
use super::prose;
```

at `crates/jankurai/src/audit/scan.rs:3`.

But the uploaded archive does **not** contain `crates/jankurai/src/audit/prose.rs`.

**Why this matters:** a code audit standard should hard-cap any repo that cannot compile. A `100/100` score should be impossible if the uploaded source snapshot is missing a module.

**Add audit rule:**

| Rule                                                           | Severity | Cap | Trigger                                                      |
| -------------------------------------------------------------- | -------: | --: | ------------------------------------------------------------ |
| `build-graph-missing-module` / `HLT-038-BUILD-COMPILE-BLOCKED` | critical |  40 | Rust module declared/imported but missing from source tree   |
| `canonical-build-not-run`                                      |     high |  65 | CI does not prove the package builds from clean checkout     |
| `uploaded-source-incomplete`                                   | critical |  50 | archive/release source differs from compilable repo contents |

**Safe fix:** add `prose.rs` to the repo/archive, or remove the module/imports if the prose detector was superseded. Then add a CI step that runs `cargo check --workspace --all-targets --all-features --locked` before Jankurai can publish a score.

### 2. CI ratchet baseline is self-generated in the same run

The workflow creates the baseline from the current checkout:

```yaml
jankurai . --json agent/repo-score.json --md agent/repo-score.md
cp agent/repo-score.json target/jankurai/baseline-score.json
```

then immediately ratchets against that copied file (`.github/workflows/jankurai.yml:32-38`).

**Why this matters:** this proves “the current code did not regress relative to the current code.” It does not protect against regression.

**Add audit rule:**

| Rule                                                                 | Severity | Cap |
| -------------------------------------------------------------------- | -------: | --: |
| `self-generated-ratchet-baseline` / `HLT-039-EVIDENCE-INTEGRITY-GAP` |     high |  70 |

**Safe fix:** ratchet against one of:

1. committed accepted baseline on `main`;
2. previous successful `main` workflow artifact;
3. signed release baseline;
4. score-history entry with a verified report fingerprint and commit SHA.

The ratchet evidence should include `baseline_source`, `baseline_commit`, `baseline_report_fingerprint`, `current_report_fingerprint`, `allowed_drop`, `score_delta`, and `decision`.

### 3. Security lane is non-strict in CI

CI runs:

```yaml
jankurai security run . --out target/jankurai/security/evidence.json
```

without `--strict` (`.github/workflows/jankurai.yml:86-87`).

`tools/security-lane.sh` makes only `gitleaks` required (`tools/security-lane.sh:104-107`). `cargo audit`, `npm audit`, `syft`, and `zizmor` are advisory (`tools/security-lane.sh:109-115`). In non-strict mode, advisory tools can be missing or fail without blocking (`tools/security-lane.sh:73-100`).

`agent/security-policy.toml` also requires only `gitleaks`; `cargo audit` and `npm audit` are advisory (`agent/security-policy.toml:3-16`).

**Why this matters:** your own security matrix says CI should require `gitleaks`, `cargo audit`, `npm audit`, and `zizmor`, and release should require Syft, Grype/Trivy, Scorecard, and SLSA/Cosign (`docs/security-tool-matrix.md:15-32`). The implementation does not enforce that.

**Add audit rules:**

| Rule                                    |               Severity | Cap |
| --------------------------------------- | ---------------------: | --: |
| `ci-security-lane-not-strict`           |                   high |  65 |
| `required-security-tool-advisory-in-ci` |                   high |  70 |
| `security-policy-tool-matrix-drift`     |                   high |  75 |
| `security-tool-skipped-in-ci`           | critical when required |  60 |

**Safe fix:** in CI, run:

```bash
jankurai security run . --strict --out target/jankurai/security/evidence.json
```

Then update `agent/security-policy.toml` so CI-required tools are truly required:

```toml
required_tools = [
  "gitleaks",
  "cargo audit",
  "npm audit",
  "syft",
  "zizmor"
]
```

Release mode should additionally require `grype` or `trivy`, OpenSSF Scorecard, signing/attestation, and provenance.

### 4. Security output is recorded but not normalized into findings

`SecurityLaneStep` has fields for `finding_count`, `highest_severity`, and `normalized_decision` (`crates/jankurai/src/commands/security.rs:62-82`), but `enrich_step` sets them to `None` (`crates/jankurai/src/commands/security.rs:272-302`).

**Why this matters:** Jankurai records whether a tool ran, but not what it found in a structured, policy-enforced way. A world-class audit needs parsed output, not just command status.

**Add audit rule:**

| Rule                                                                 | Severity | Cap |
| -------------------------------------------------------------------- | -------: | --: |
| `security-tool-output-unparsed` / `HLT-042-SECURITY-TOOL-OUTPUT-GAP` |     high |  80 |

**Safe fix:** require JSON/SARIF output for each tool and normalize into a common schema:

```json
{
  "tool": "cargo-audit",
  "tool_version": "x.y.z",
  "status": "ran",
  "finding_count": 2,
  "highest_severity": "high",
  "normalized_decision": "fail",
  "findings": [
    {
      "id": "RUSTSEC-...",
      "severity": "high",
      "package": "...",
      "fixed_version": "...",
      "direct": false
    }
  ],
  "output_artifact": "target/jankurai/security/cargo-audit.json",
  "output_sha256": "sha256:..."
}
```

### 5. Proof lanes are advisory by default in CI

The workflow runs:

```yaml
jankurai proofbind verify . --changed-from origin/main
jankurai proofmark rust . --obligations target/jankurai/proofbind/obligations.json
```

without required mode (`.github/workflows/jankurai.yml:41-44`).

The CLI defaults to advisory for both:

* `ProofBindVerifyArgs.mode` default is `"advisory"` (`crates/jankurai/src/main.rs:671-679`);
* `ProofMarkRustArgs.mode` default is `"advisory"` (`crates/jankurai/src/main.rs:707-715`).

`agent/tool-adoption.toml` also marks `proofbind` and `proofmark-rust` as advisory (`agent/tool-adoption.toml:11-17`).

**Why this matters:** the repo presents proof as a central concept, but the critical proof lanes are not hard gates.

**Add audit rules:**

| Rule                              | Severity | Cap |
| --------------------------------- | -------: | --: |
| `proofbind-advisory-in-ci`        |     high |  76 |
| `proofmark-advisory-in-ci`        |     high |  76 |
| `proof-required-but-not-blocking` |     high |  70 |

**Safe fix:** make PR CI run:

```bash
jankurai proofbind verify . --changed-from origin/main --mode required
jankurai proofmark rust . \
  --mode required \
  --obligations target/jankurai/proofbind/obligations.json \
  --coverage target/jankurai/coverage/lcov.info \
  --mutation target/jankurai/mutation/mutants.json
```

For local developer loops, advisory is fine. For merge/release, it should be required.

### 6. Missing mutation evidence can still pass ProofMark

In ProofMark:

```rust
let mutation_ok = mutation.status == "pass" || mutation.status == "unavailable";
```

at `crates/jankurai-proofmark/src/report.rs:68`.

That means mutation evidence can be unavailable and still allow an obligation to pass if coverage and negative proof pass (`crates/jankurai-proofmark/src/report.rs:68-74`), even though the residual risk notes that focused mutation evidence was not supplied (`crates/jankurai-proofmark/src/report.rs:89-90`).

**Why this matters:** for critical changes, unavailable mutation evidence should not be a pass. It can be advisory for local mode, but not for release or boundary-sensitive code.

**Add audit rule:**

| Rule                                         | Severity | Cap |
| -------------------------------------------- | -------: | --: |
| `mutation-unavailable-counts-as-pass`        |     high |  82 |
| `boundary-sensitive-change-without-mutation` |     high |  76 |

**Safe fix:** change behavior by mode:

* advisory mode: `unavailable` = review/pass with residual risk;
* required mode: `unavailable` = review/fail for boundary-sensitive obligations;
* release mode: `unavailable` = fail unless exception is owner-approved and unexpired.

### 7. Score history shows `100/100` with dirty worktree

The latest rows in `agent/score-history.jsonl` include `dirty_worktree:true` with `score:100`, `finding_count:0`, and `caps_applied:[]`.

**Why this matters:** dirty worktree means the score may not correspond to committed code. That is acceptable in local advisory mode, but not for CI/release or public badges.

**Add audit rules:**

| Rule                          |    Severity | Cap |
| ----------------------------- | ----------: | --: |
| `dirty-worktree-public-score` | medium/high |  90 |
| `dirty-worktree-release`      |    critical |  70 |
| `badge-from-dirty-worktree`   |        high |  80 |

**Safe fix:** local advisory can record dirty status, but public badges, release evidence, and ratchet baselines should require a clean worktree.

### 8. Canonical `just check` does not run the full quality gate

`Justfile` says `default: check`, but `check` runs only versions, Jankurai score, and LaTeX paper build (`Justfile:19-22`). It does not run:

* `cargo fmt --check`;
* `cargo clippy --workspace --all-targets --all-features -- -D warnings`;
* `cargo test --workspace`;
* `cargo test --doc`;
* npm/TypeScript tests;
* strict security;
* dependency/license checks;
* coverage or mutation.

The PR template asks humans to run several checks (`.github/PULL_REQUEST_TEMPLATE.md:11-16`), but a human checklist is not a merge gate.

**Add audit rules:**

| Rule                                     | Severity | Cap |
| ---------------------------------------- | -------: | --: |
| `canonical-check-does-not-run-build`     |     high |  70 |
| `canonical-check-does-not-run-tests`     |     high |  72 |
| `fmt-clippy-human-only`                  |     high |  78 |
| `human-template-validation-not-ci-gated` |   medium |  84 |

**Safe fix:** add separate lanes:

```make
check-fast:
    cargo check --workspace --all-targets --locked
    npm --workspace @jankurai/ux-qa run build
    cargo run -p jankurai -- audit . --changed-fast --changed-from origin/main ...

check-merge:
    cargo fmt --all -- --check
    cargo clippy --workspace --all-targets --all-features -- -D warnings
    cargo test --workspace --all-features --locked
    cargo test --workspace --doc --locked
    npm ci
    npm --workspace @jankurai/ux-qa run build
    npm --workspace @jankurai/ux-qa run test
    just security-strict
    cargo run -p jankurai -- audit . --mode ratchet --baseline agent/repo-score.json ...

check-release:
    just check-merge
    cargo audit --json ...
    cargo deny check ...
    syft ...
    grype ...
    scorecard ...
    attest/sign/verify ...
```

## Current strengths worth keeping

Before the gaps, the good parts are important:

1. **Clear anti-vibe mission.** README states ownership maps, proof lanes, generated zones, security boundaries, rolling scores, merge witnesses, and repair queues are first-class files (`README.md:14-21`).

2. **Good hard-cap mindset.** `caps.rs` already has many meaningful caps: missing proof lane, secret scanning gap, generated-zone mutation risk, direct DB wrong layer, prompt injection, overbroad agent agency, false-green tests, destructive migrations, authz/data isolation, input boundary, release readiness, and language-specific bad behavior (`crates/jankurai/src/audit/caps.rs`).

3. **Language-rule catalog exists.** Rust, TypeScript, SQL, Docker, Python, CI, Git, Git tooling, and release behavior all have dedicated detector packs under `crates/jankurai/src/audit/language_rules/`.

4. **UX QA is unusually strong.** The UX package checks geometry, target size, clipping, overflow, focus visibility, labels, and accessibility. That is exactly the right direction for killing “looks fine to me” UI vibe coding.

5. **Agent repair queue and receipts are central.** The report model includes dimensions, findings, caps, tool adoption, security evidence, UX evidence, boundary evidence, and repair queues (`crates/jankurai/src/model.rs`).

The gaps below are not “start over” issues. They are “make the score impossible to fake” issues.

# A. Scoring architecture gaps

## A1. Add evidence levels to every scored claim

Right now, scoring often rewards command/text presence. For example, the security analyzer gives credit if command surfaces contain words like `gitleaks`, `audit`, `deny`, `dependency-review`, `syft`, `grype`, `slsa`, `sbom`, `cosign`, `actionlint`, or `zizmor` (`crates/jankurai/src/audit/analyzers/security.rs:20-58`).

That should be replaced or supplemented with an evidence ladder:

| Evidence level       | Meaning                                             |   Score value |
| -------------------- | --------------------------------------------------- | ------------: |
| `absent`             | No control found                                    |             0 |
| `mentioned`          | Appears in docs/text                                |           low |
| `configured`         | Config file exists                                  |    low/medium |
| `scheduled`          | CI step exists                                      |        medium |
| `executed`           | command ran                                         |   medium/high |
| `parsed`             | output parsed into normalized findings              |          high |
| `policy_gated`       | failing findings block merge/release                |     very high |
| `artifact_uploaded`  | evidence artifact retained                          |     very high |
| `signed_or_attested` | artifact provenance/integrity is cryptographic      | release-grade |
| `verified`           | consumer/verifier checked the signature/attestation |      top-band |

**Add field everywhere:**

```json
{
  "evidence_level": "policy_gated",
  "evidence_confidence": "high",
  "applicability": "applicable",
  "artifact_path": "...",
  "artifact_sha256": "...",
  "tool_version": "...",
  "command_sha256": "...",
  "policy_decision": "pass"
}
```

**New cap:** `top-band-score-without-evidence-levels` → max 90.

## A2. Add score ceilings based on evidence quality

A repo should not be able to receive 95–100 if high-assurance evidence is missing.

Suggested ceilings:

| Condition                                    |             Max score |
| -------------------------------------------- | --------------------: |
| Source cannot compile                        |                    40 |
| Missing module/build graph issue             |                    40 |
| Self-generated ratchet baseline              |                    70 |
| CI security lane not strict                  |                    65 |
| Required security tool skipped               |                    60 |
| Security output unparsed                     |                    80 |
| No SAST/code scanning                        |                    82 |
| No dependency review                         |                    82 |
| No workflow permissions block                |                    84 |
| Actions not SHA-pinned                       | 82, or 75 for release |
| No SBOM                                      |                    84 |
| SBOM not vulnerability-scanned               |                    80 |
| No release provenance/attestation            |                    75 |
| No branch-protection evidence                |                    84 |
| Dirty worktree used for public badge/release |                    80 |
| Audit docs and scoring weights disagree      |                    88 |
| Detector calibration missing                 |                    90 |

This prevents a “perfect” badge from being issued when evidence is incomplete.

## A3. Docs and code scoring weights drift

`docs/audit-rubric.md` says ownership, contracts, proof, and security are each 14 points, and context is 8 (`docs/audit-rubric.md:28-37`). But code weights are:

```rust
("Ownership and navigation surface", 13)
("Contract and boundary integrity", 13)
("Proof lanes and test routing", 12)
("Security and supply-chain posture", 12)
("Jankurai tool adoption and CI replacement", 7)
```

at `crates/jankurai/src/audit/helpers.rs:6-17`.

**Why this matters:** the public standard and executable scoring contract are not identical.

**Add audit rule:** `rubric-code-weight-drift` → max 88.

**Safe fix:** generate docs from a single machine-readable scoring manifest, or make the docs explicitly reference the code-generated table.

---

## A4. Scanning truncation is not surfaced as a finding

Inventory captures only a text sample per file. Default capture is 120,000 characters (`crates/jankurai/src/audit/fs_policy.rs:6-20`), and `read_text_sample` stops appending after that limit while still counting lines (`crates/jankurai/src/audit/fs.rs:259-281`).

**Why this matters:** a very large generated or source file can hide violations after the captured prefix. That is okay for performance, but the report must say “this file was truncated.”

**Add audit rules:**

| Rule                                                  | Severity | Cap |
| ----------------------------------------------------- | -------: | --: |
| `file-truncated-without-finding`                      |   medium |  90 |
| `critical-surface-truncated`                          |     high |  80 |
| `scan-coverage-unknown` / `HLT-047-SCAN-COVERAGE-GAP` |     high |  85 |

**Safe fix:** add `captured_chars`, `total_bytes`, `truncated: true`, and `truncated_paths` to the inventory/report. Hard-cap only if critical paths are truncated.

## A5. Baseline parse failure silently becomes current score

`apply_mode_and_baseline` reads a baseline, parses `score`, and falls back to `report.score` if parsing fails:

```rust
.unwrap_or(report.score as i64)
```

at `crates/jankurai/src/main.rs:2287-2292`.

**Why this matters:** malformed baseline can become a passing ratchet.

**Add audit rule:** `baseline-parse-failure-falls-back-to-current` → max 70.

**Safe fix:** in ratchet/release mode, malformed or missing baseline score must fail closed. Advisory mode can warn.

# B. External standards and control mapping gaps

Jankurai should keep its unique anti-vibe standard, but world-class assurance needs mapping to recognized secure-SDLC controls. NIST SSDF SP 800-218 is the U.S. secure software development framework for mitigating software vulnerabilities, and OWASP ASVS provides a concrete basis for testing web application security controls and secure-development requirements. ([NIST Computer Security Resource Center][1])

## B1. Add a control map

Add a report section:

```json
"control_map": [
  {
    "standard": "NIST SSDF",
    "version": "1.1",
    "control": "PW.4 / RV.1 / RV.2",
    "status": "pass|fail|partial|not_applicable",
    "evidence_level": "policy_gated",
    "evidence_artifacts": [],
    "jankurai_rules": []
  },
  {
    "standard": "OWASP ASVS",
    "version": "5.0.0",
    "control": "v5.0.0-1.2.5",
    "status": "pass|fail|partial|not_applicable",
    "evidence_artifacts": [],
    "jankurai_rules": []
  }
]
```

**Add audit rule:** `external-control-map-missing` / `HLT-041-EXTERNAL-SDLC-MAPPING-GAP` → max 85.

## B2. Add maturity levels separate from score

A single score hides the difference between “good repo hygiene” and “release-grade secure software.”

Suggested levels:

| Level | Meaning                                                             |
| ----- | ------------------------------------------------------------------- |
| `L0`  | inventory only                                                      |
| `L1`  | agent-readable and repairable                                       |
| `L2`  | CI-gated                                                            |
| `L3`  | parsed security evidence                                            |
| `L4`  | release provenance, branch protection, external standards mapped    |
| `L5`  | signed/attested, reproducible, calibrated, independently reviewable |

# C. GitHub Actions, CI, and Git governance gaps

GitHub’s secure-use guidance recommends least-privilege `GITHUB_TOKEN` permissions and notes that pinning actions to a full-length commit SHA is the only way to use an action as an immutable release. ([GitHub Docs][2])

## C1. Missing explicit workflow permissions

`.github/workflows/jankurai.yml` has no top-level or job-level `permissions:` block (`.github/workflows/jankurai.yml:1-10`).

**Add audit rule:** `missing-workflow-permissions-block` → max 84.

**Safe fix:**

```yaml
permissions:
  contents: read

jobs:
  audit:
    permissions:
      contents: read
      security-events: write # only if uploading SARIF
      attestations: write    # only in release attestation job
      id-token: write        # only in OIDC/attestation/signing jobs
```

## C2. Actions are tag-pinned, not SHA-pinned

Examples:

* `actions/checkout@v6` (`.github/workflows/jankurai.yml:12`);
* `dtolnay/rust-toolchain@stable` (`.github/workflows/jankurai.yml:15`);
* `actions/setup-node@v6` (`.github/workflows/jankurai.yml:16`);
* `actions/upload-artifact@v7` (`.github/workflows/jankurai.yml:114`).

**Add audit rule:** `unpinned-github-action-reference` → max 82, release max 75.

**Safe fix:** use full SHA pins with comments documenting the release tag:

```yaml
- uses: actions/checkout@<full_commit_sha> # v6.x.x
```

## C3. Missing workflow timeouts and concurrency

The workflow jobs do not specify `timeout-minutes` or `concurrency`.

**Add audit rules:**

* `workflow-job-timeout-missing` → max 88;
* `workflow-concurrency-missing-for-main` → max 90.

**Safe fix:**

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  audit:
    timeout-minutes: 30
```

## C4. Branch protection is not verified

The file tree cannot prove branch protection, required checks, required reviews, stale review dismissal, force-push restrictions, or CODEOWNERS enforcement.

**Add audit rule:** `branch-protection-unverified` / `HLT-046-BRANCH-GOVERNANCE-GAP` → max 84.

**Safe fix:** query GitHub branch protection via API in a `jankurai github posture` command and store evidence:

```json
{
  "branch": "main",
  "requires_pull_request": true,
  "required_approving_review_count": 1,
  "requires_code_owner_reviews": true,
  "required_status_checks": ["audit", "security-strict", "test"],
  "allows_force_pushes": false,
  "allows_deletions": false
}
```

## C5. CODEOWNERS has one owner for everything

`.github/CODEOWNERS` maps every critical surface to `@bentaylor` (`.github/CODEOWNERS:2-18`).

**Why this matters:** this is fine for a solo project, but world-class governance should distinguish solo-owner projects from independent review readiness.

**Add audit rules:**

* `critical-surface-single-owner` → advisory for solo projects, cap 88 for org/release mode;
* `security-surface-lacks-independent-reviewer` → cap 84 in release mode.

**Safe fix:** support a `solo_project = true` policy field, but require stronger evidence for public release claims.

## C6. Missing Dependabot/Renovate config

The uploaded `.github` tree does not include `.github/dependabot.yml` or Renovate config.

**Add audit rule:** `dependency-update-bot-missing` / `HLT-043-DEPENDENCY-GOVERNANCE-GAP` → max 86.

**Safe fix:** add Dependabot or Renovate for:

* Cargo;
* npm;
* GitHub Actions;
* Docker, if production Docker exists.

# D. Dependency, SAST, and supply-chain gaps

GitHub’s Dependency Review Action scans pull requests for dependency changes and can fail PRs that introduce vulnerabilities or invalid licenses, including severity threshold controls. ([GitHub][3]) CodeQL is GitHub’s code analysis engine for identifying vulnerabilities and errors, and it supports JavaScript/TypeScript, Python, Rust, and GitHub Actions workflows, among other languages. ([GitHub Docs][4]) RustSec documents `cargo audit` for auditing `Cargo.lock` against Rust advisories and `cargo deny` for vulnerabilities, license constraints, sources, and duplicate versions. ([RustSec][5])

## D1. Missing Dependency Review gate

No dependency review action is visible in CI.

**Add audit rule:** `missing-pr-dependency-review` → max 82.

**Safe fix:**

```yaml
- name: Dependency review
  uses: actions/dependency-review-action@<sha>
  with:
    fail-on-severity: high
    deny-licenses: GPL-3.0, AGPL-3.0
```

Or, better, license policy should live in a repo config and Jankurai should parse the result.

## D2. Missing CodeQL/Semgrep SAST lane

No CodeQL or Semgrep workflow is visible.

**Add audit rules:**

* `missing-sast-code-scanning` → max 82;
* `sast-result-not-uploaded-as-sarif` → max 84;
* `sast-result-not-reflected-in-jankurai-score` → max 86.

**Safe fix:** add CodeQL for Rust, TypeScript, Python, and GitHub Actions. Add Semgrep for custom Jankurai-specific repo patterns. Normalize SARIF into Jankurai findings.

## D3. Missing `cargo deny`

No `deny.toml` exists in the archive.

**Add audit rule:** `missing-cargo-deny-policy` → max 84.

**Safe fix:** add `deny.toml` for:

* advisories;
* yanked crates;
* duplicate versions;
* license allow/deny;
* unknown registries/sources;
* banned crates.

## D4. Missing license policy

There is no clear machine-readable license policy for Cargo/npm dependencies.

**Add audit rule:** `dependency-license-policy-missing` → max 86.

**Safe fix:** add license policy in `agent/security-policy.toml` or dedicated `deny.toml`, then parse `cargo deny` and dependency review outputs.

## D5. Missing dependency health / maintainer-risk scoring

World-class dependency audit should not only ask “known CVE?” It should also score:

* abandoned dependencies;
* yanked crates;
* duplicate versions;
* unmaintained advisories;
* new dependency added without rationale;
* dependency with install scripts/postinstall scripts;
* transitive dependency explosion;
* package age and maintainer churn;
* use of Git/path dependencies in release;
* lockfile drift.

**Add rules:**

| Rule                                     | Cap |
| ---------------------------------------- | --: |
| `new-dependency-without-rationale`       |  88 |
| `dependency-with-postinstall-script`     |  82 |
| `git-dependency-in-release`              |  78 |

# E. SBOM, provenance, signing, and release integrity gaps

GitHub artifact attestations create cryptographically signed provenance and integrity claims for build artifacts, including workflow, repository, organization, environment, commit SHA, and triggering event. ([GitHub Docs][6]) Docker Build attestations describe how an image was built and what it contains, with SBOM and provenance as key attestation types; Docker’s SBOM docs also emphasize validating generated SBOMs before pushing images. ([Docker Documentation][7]) SLSA levels are about increasing supply-chain security guarantees, including provenance and hardened build platforms. ([SLSA][8])

## E1. Local attestation is not enough for release

`crates/jankurai/src/commands/publish.rs` describes local SHA-256 attestation and says external Sigstore or GitHub artifact attestation can wrap the same files. That is a good start, but release mode should require external signed provenance.

**Add audit rule:** `release-attestation-local-only` → max 78.

**Safe fix:** in release mode, require one of:

* GitHub artifact attestation;
* Sigstore/Cosign signature and attestation;
* SLSA provenance from a trusted builder.

## E2. Missing release verification step

Generating provenance is not enough. Consumers or CI should verify it.

**Add audit rules:**

* `artifact-attestation-generated-but-not-verified` → max 82;
* `release-signature-generated-but-not-verified` → max 82.

**Safe fix:** release workflow should do:

1. build artifact;
2. generate SBOM;
3. scan artifact/SBOM;
4. sign/attest;
5. verify signature/attestation;
6. publish only verified artifact.

## E3. Missing artifact checksum manifest

Release artifacts should have a checksums file and the checksum manifest should itself be signed/attested.

**Add audit rule:** `release-checksum-manifest-missing` → max 80.

## E4. Missing OpenSSF Scorecard

OpenSSF Scorecard is already mentioned in docs, but not enforced in workflow.

**Add audit rule:** `missing-openssf-scorecard` → max 84.

**Safe fix:** run Scorecard and normalize JSON. Scorecard should be an external challenge to Jankurai’s self-score, not a replacement.

# O. Schema, SARIF, and report-contract gaps

## O1. JSON Schema validator supports only a limited keyword set

**Add audit rule:** `schema-keyword-support-limited` → advisory now, cap 88 if schemas claim full JSON Schema compatibility.

# Smart rollout plan that will not break adopters unnecessarily

## Phase 0: Add evidence fields without failing

Add new fields to reports:

* `evidence_level`;
* `applicability`;
* `confidence`;
* `tool_version`;
* `tool_output_path`;
* `tool_output_sha256`;
* `normalized_findings`;
* `policy_decision`;
* `truncated_files`;
* `external_controls`.

Do not fail on these yet. Show them in Markdown.

## Phase 1: Hard-fail only objective correctness issues

Immediately block:

* missing module / build graph cannot compile;
* malformed ratchet baseline;
* self-generated ratchet baseline in CI;
* required security tool skipped in strict mode;
* dirty worktree for release;
* missing artifact referenced by report.

These are low false-positive.

## Phase 2: Ratchet security posture

Make these advisory first, then ratchet:

* workflow permissions;
* SHA pinning;
* dependency review;
* CodeQL/Semgrep;
* cargo deny;
* SBOM;
* Scorecard.

Require explicit exceptions with owner, expiry, reason, and compensating control.

## Phase 3: Release-grade gates

Only release mode should require:

* signed/attested provenance;
* clean worktree;
* protected branch/tag;
* SBOM + vulnerability scan;
* artifact verification;
* release rollback evidence;
* external control map.

## Phase 4: Calibration before harsh detector caps

Before turning new heuristic detectors into hard caps, require:

* safe fixture;
* risky fixture;
* false-positive fixture;
* rule documentation;
* severity rationale;
* repair guidance.

This keeps “kill vibe coding” from becoming “break good teams with noisy regexes.”

## Bottom line

Jankurai is already strong at the thing most tools miss: **agent-native repairability, anti-placeholder discipline, generated-zone control, proof routing, and merge evidence.** The missing world-class layer is harder assurance:

**A perfect score must mean the code built, tests ran, security tools executed, outputs were parsed, evidence was retained, release artifacts were signed/attested, branch protections were verified, and the audit standard itself was calibrated.**

The best next version of Jankurai should make this invariant impossible to violate:

> No repository can score in the top band based only on markers, docs, command strings, advisory lanes, dirty worktree output, or self-generated baselines. Top-band scores require executed, parsed, policy-gated, replayable, and release-verifiable evidence.

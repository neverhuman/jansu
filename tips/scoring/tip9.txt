I inspected the uploaded archive statically, inventoried the repo, and read the core audit engine, caps, rule registry, detectors, schemas, workflows, action, security lane, Justfile, package config, conformance suite, docs, and policy files. I could not execute `cargo` in this environment because the container does not have Cargo installed, so the build/test comments below are static findings rather than runtime test results.

## Overall verdict

Jankurai is already aiming at the right meta-problem: **make AI-assisted code merges evidence-carrying, reproducible, repairable, and hostile to “vibe-coded” shortcuts.** The existing design has strong foundations: HLT rule families, hard caps, agent routes, proof lanes, generated-zone policy, security evidence, UX evidence, score history, repair queues, and a conformance suite.

The biggest missing best practices are not simply “add more detectors.” The biggest gaps are:

1. **Score trustworthiness:** the score needs evidence maturity, calibration, and confidence limits.
2. **CI integrity:** the current ratchet baseline can compare the candidate run to itself.
3. **Build integrity:** full Rust/TypeScript quality gates are not clearly enforced in CI.
4. **Supply-chain enforcement:** security tools exist, but many are advisory rather than blocking.
5. **Workflow hardening:** actions are tag-pinned, not SHA-pinned; no explicit workflow permissions, timeouts, or concurrency.
6. **Detector calibration:** the conformance suite is intentionally small; the audit engine needs a real false-positive/false-negative benchmark.
7. **Policy drift detection:** docs, policy TOML, cap specs, security script, and CI do not fully agree.
8. **Schema rigor:** many evidence schemas allow extra top-level properties, and the in-repo schema validator supports only a subset of JSON Schema.
9. **Release provenance:** SBOM generation exists as an advisory script step, but release signing, attestations, provenance verification, and SARIF upload are not first-class gates.
10. **Repository hygiene:** the uploaded archive contains 973 AppleDouble `._*` files, which should be ignored and treated as packaging/release contamination if they ever appear in source or artifacts.

For a world-class standard, I would shift Jankurai from a single “100/100 posture score” to a **multi-axis evidence score**: posture, enforcement, detector confidence, calibration, supply-chain integrity, and release readiness.

## What Jankurai is trying to do, and the right “world-class” framing

The goal is not just “lint code.” It is:

> **Prevent AI-generated or rushed code from looking complete unless it has ownership, boundaries, tests, security evidence, data safety, release proof, and repairability.**

That means the score must answer five questions:

1. **Can an agent find the right code?**
2. **Can a human trust the proof evidence?**
3. **Can the system detect common vibe-coded shortcuts?**
4. **Can the release be traced back to source, tests, SBOM, and provenance?**
5. **Can defects be repaired safely without widening blast radius?**

NIST SSDF frames secure software development as practices to reduce vulnerabilities, reduce impact of missed vulnerabilities, and address root causes to prevent recurrence. ([NIST Computer Security Resource Center][3]) OWASP SAMM similarly treats software assurance as a measurable maturity model across the SDLC. ([OWASP Developer Guide][4]) Jankurai should map to that maturity model: not just “does a repo have scanners,” but “are scanners enforced, calibrated, and tied to repair evidence.”

# 1. Scoring model gaps

## Current gap: a single score overstates confidence

The README shows a `100/100` badge at `README.md:1-2` and a public advisory score table where Jankurai is `100` with `0` issues at `README.md:203-210`. The README also correctly says this is “advisory posture evidence, not certification or defect attribution” at `README.md:203-205`.

That caveat is important, but the single badge still creates a trust problem. A flat 100 implies near-perfect audit quality, but:

* The conformance suite says it is **not a broad benchmark** at `conformance/README.md:3-5`.
* It is intentionally small, with 10 fixtures at `conformance/README.md:12-23`.
* Many vibe coverage rows are control-family or partial evidence rather than detector-backed.
* CI currently generates its own ratchet baseline.
* Full build/lint/test/security enforcement is not complete.

## Recommended scoring architecture

Split the score into multiple visible dimensions:

| Dimension                      | Meaning                                                                                   | Should cap total score?    |
| ------------------------------ | ----------------------------------------------------------------------------------------- | -------------------------- |
| **Posture score**              | Existing Jankurai score: docs, owner maps, proof lanes, UX/security artifacts, hard caps. | Yes, but not alone.        |
| **Evidence enforcement score** | Whether evidence is produced by blocking CI, not local/advisory config.                   | Yes.                       |
| **Detector maturity score**    | Whether findings are deterministic, fixture-backed, and calibrated.                       | Yes.                       |
| **Calibration score**          | Precision/recall/false-negative metrics against benchmark fixtures.                       | Yes for public claims.     |
| **Supply-chain score**         | Dependency review, SBOM, signatures, provenance, release immutability.                    | Yes for release readiness. |
| **Build quality score**        | fmt, clippy, tests, typecheck, lint, coverage, mutation/fuzz/property testing.            | Yes.                       |
| **Governance score**           | CODEOWNERS, branch protection evidence, signed releases, waiver expiry, review receipts.  | Yes.                       |

A repository should not be able to show a simple `100/100` unless the evidence maturity and calibration scores are also high.

## New rule: score ceiling by evidence maturity

Add a score ceiling like this:

| Lowest maturity among applicable critical/high rules | Max public score |
| ---------------------------------------------------- | ---------------: |
| Policy-only / docs-only                              |               70 |
| Control-family mapping only                          |               76 |
| Detector exists, no fixture                          |               82 |
| Detector + positive fixture only                     |               86 |
| Detector + positive + negative fixtures              |               90 |
| Detector + fixtures + CI artifact                    |               94 |
| Detector + CI + precision/recall benchmark           |               98 |
| Detector + CI + benchmark + external provenance      |              100 |

This prevents “we mapped 260 risks” from becoming “we can reliably detect 260 risks.”

# 2. Critical scoring integrity gaps

## 2.1 Self-referential ratchet baseline

The current workflow generates a baseline from the candidate contents:

```yaml
# .github/workflows/jankurai.yml
32  - name: Generate CI ratchet baseline
34    jankurai . --json agent/repo-score.json --md agent/repo-score.md
35    cp agent/repo-score.json target/jankurai/baseline-score.json
38  jankurai audit . --mode ratchet --baseline target/jankurai/baseline-score.json ...
```

This defeats the purpose of ratcheting. The README says ratchet enforcement should be baseline-backed at `README.md:346-348`. The workflow should use one of:

* committed `agent/baseline-score.json` from protected main,
* artifact from the last accepted main build,
* signed baseline receipt,
* or explicit `git show origin/main:agent/repo-score.json`.

### Recommended cap

```toml
self_referential_ratchet_baseline = 70
```

### Detector

Detect when:

* `--mode ratchet` appears in CI,
* `--baseline` points under `target/`, `/tmp/`, or a file generated earlier in same workflow,
* same job runs `jankurai` and copies candidate `agent/repo-score.json` to baseline,
* tool catalog itself recommends target-generated baseline.

### Repair

Use:

```bash
git fetch origin main
git show origin/main:agent/repo-score.json > target/jankurai/accepted-baseline.json
jankurai audit . \
  --mode ratchet \
  --baseline target/jankurai/accepted-baseline.json \
  --json agent/repo-score.json \
  --md agent/repo-score.md
```

For a release-grade baseline, sign or attest the accepted baseline.

## 2.2 Tool adoption should not count substring matches as CI evidence

`tool_adoption.rs:70-78` checks whether the lowercased workflow text contains command substrings and uploaded artifact paths. That is fragile.

### Missing audit coverage

Add a `ci-evidence-semantic-gap` rule that requires:

* YAML parsing, not substring search.
* Evidence command appears in `run`, not comments or echo strings.
* Job has no `continue-on-error`.
* Step is not guarded by `if: false`, `if: always() && false`, or branch filters that skip PRs.
* Required artifact is uploaded by an artifact step that runs after the command.
* Job has explicit permissions and timeout.
* Security lane uses strict mode when expected.
* Evidence step exit status is reflected in a receipt.

### Suggested cap

```toml
ci_evidence_is_textual_not_semantic = 84
```

## 2.3 Stable decision fingerprints

`report_fingerprint` currently hashes the full report except the `report_fingerprint` field. The report includes `generated_at`, `run_id`, `started_at`, `elapsed_ms`, and the local `repo` path at `audit/mod.rs:167-190`. That makes `report_fingerprint` unstable across identical reruns.

### Fix

Keep the current fingerprint if useful, but add:

```json
{
  "decision_fingerprint": "sha256:...",
  "evidence_fingerprint": "sha256:...",
  "volatile_fields": ["generated_at", "run_id", "started_at", "elapsed_ms", "repo"]
}
```

The stable decision fingerprint should include:

* standard version,
* auditor version,
* policy fingerprint,
* manifest fingerprints,
* input fingerprint,
* scope,
* caps applied,
* normalized findings,
* score,
* decision.

It should exclude:

* wall-clock time,
* local filesystem path,
* elapsed milliseconds,
* run ID,
* ordering noise,
* absolute paths.

## Make CI rules nuanced to avoid noise

Do not hard-fail every tag reference immediately. Use tiers:

| Reference type                                   | Severity                                   |
| ------------------------------------------------ | ------------------------------------------ |
| Full 40-char SHA                                 | Pass                                       |
| Local action `./path`                            | Pass if path is CODEOWNED and tested       |
| Immutable internal tag with verification receipt | Low/advisory                               |
| Marketplace version tag like `@v4`, `@v6`        | Medium; high in release/security workflows |
| `@main`, `@master`, `@stable`, `@latest`         | High                                       |
| Untrusted action in privileged job               | Critical                                   |

Current `ci.action.mutable-ref` only detects `@main`, `@master`, and `@latest` at `ci.rs:386-388`, and its fix text allows “stable release tag” at `ci.rs:77` and `ci.rs:296`. For “best available standard,” full SHA should be the high-assurance path; tags can be allowed only with an explicit risk acceptance.

# 5. SLSA, SBOM, release provenance, and artifact integrity

SLSA Build v1.2 defines increasing build assurance levels: Build L1 has provenance showing how a package was built, L2 adds signed provenance from a hosted build platform, and L3 uses a hardened build platform. ([SLSA][8])

Jankurai has a good local evidence philosophy, but world-class release auditing should require tamper-resistant release evidence.

## Missing release audit controls

| Control                          | Missing/weak signal                                           | Recommended audit                                                                        |
| -------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Release artifact digest manifest | No visible release workflow producing digest manifest         | Require SHA256 manifest for every release artifact.                                      |
| SBOM attached to release         | Syft exists as advisory in `tools/security-lane.sh:113`       | Block release if SBOM absent or not uploaded.                                            |
| SBOM vulnerability scan          | No Grype/Trivy required                                       | Require scan result and threshold.                                                       |
| Artifact signing                 | No Cosign/Sigstore release signing detected                   | Require signatures for release binaries/packages/images.                                 |
| Provenance attestation           | No SLSA/GitHub artifact attestation workflow detected         | Require provenance and verification receipt.                                             |
| Immutable tags/assets            | Release bad-behavior exists, but no release workflow evidence | Require protected tag evidence and no mutable latest-only asset policy.                  |
| Reproducible package contents    | AppleDouble archive files show packaging issue                | Add release archive hygiene gate.                                                        |
| Crates/npm dry-run package audit | Not visible                                                   | Require `cargo package --list`, `npm pack --dry-run --json`, and package file allowlist. |

## New release caps

```toml

release_without_signed_artifacts = 75
release_without_provenance_attestation = 75
release_without_artifact_digest_manifest = 80
```

# 25. What not to do

To keep the audit smart and avoid causing issues:

1. **Do not make every lexical smell a hard fail.** Use path context, generated/vendor/docs/test exemptions, and confidence tiers.
2. **Do not penalize non-applicable stacks.** Docker rules apply only if Docker exists; RLS rules apply only if multi-tenant DB exists.
3. **Do not treat local config as proof.** Config is readiness; CI artifact plus exit status is proof.
4. **Do not let waivers live forever.** Every suppression needs owner, reason, scope, expiry, and linked evidence.
5. **Do not equate “scanner installed” with “scanner enforced.”** The score should care about blocking behavior.
6. **Do not claim detector-backed coverage from control-family mapping.** Keep policy/control-family/detector-backed/benchmark-backed distinct.
7. **Do not let the audit engine become unreviewable.** Refactor trust-critical giant functions before adding many more rules.
8. **Do not break adoption by hard-failing everything immediately.** Roll new rules out as `observe → advisory → ratchet → hard cap`.

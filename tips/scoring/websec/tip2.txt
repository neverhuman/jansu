Below is the security audit model I would use for a **Vite + TypeScript + React** application. It is “exhaustive” in the practical audit sense: it covers the major known web exploit families, how they tend to appear in this stack, how to detect them, and what practices should be enforced. No list can cover every future CVE or every possible business-logic flaw, so the goal is to make sure your audit process catches both known classes and stack-specific weak points.

## Baseline standards to use

Use **OWASP Top 10:2025** as the top-level risk map. The 2025 categories are: Broken Access Control, Security Misconfiguration, Software Supply Chain Failures, Cryptographic Failures, Injection, Insecure Design, Authentication Failures, Software or Data Integrity Failures, Security Logging and Alerting Failures, and Mishandling of Exceptional Conditions. ([OWASP Foundation][1])

For a real audit, map findings to **OWASP ASVS 5.0.0** as your control checklist and use **OWASP Web Security Testing Guide** as the testing playbook. ASVS gives verifiable requirements; WSTG gives concrete testing methodology. ([OWASP Foundation][2])

# 1. Stack-specific threat model

## React

React escapes normal JSX text rendering, which reduces many classic XSS risks, but it does **not** make an app XSS-proof. The major React danger zones are `dangerouslySetInnerHTML`, user-controlled URLs, direct DOM APIs, unsafe markdown/rich-text rendering, `srcDoc`, `iframe`, `postMessage`, and third-party components. React’s own docs warn that `dangerouslySetInnerHTML` must be used with extreme caution because untrusted HTML can introduce XSS. ([React][3])

## TypeScript

TypeScript is a compile-time type system, not a runtime security boundary. The TypeScript docs explicitly note that type annotations are erased and do not change runtime behavior. That means every server response, URL parameter, `localStorage` value, form value, feature flag, uploaded file, and third-party API response still needs runtime validation. ([typescriptlang.org][4])

## Vite

Vite introduces its own audit surface: dev-server exposure, `server.allowedHosts`, `server.cors`, filesystem serving, plugins, dependency optimization, build-time environment variables, `publicDir`, source maps, and `define` replacements. Vite’s security policy treats network input to the dev/preview server as hostile, lists file-read/HMR/origin-validation issues as in-scope vulnerabilities, and separately notes that app-level flaws such as XSS, CSRF, CSP, and leaked `VITE_` variables are the application author’s responsibility. ([GitHub][5])

Vite also exposes only variables prefixed with `VITE_` to client-side code, but that means anything sensitive accidentally prefixed with `VITE_` is bundled into the browser-visible app. Vite’s docs specifically warn that `VITE_*` variables should not contain sensitive information. ([vitejs][6])

# 3. What can be detected reliably?

“Reliable detection” has limits. You can reliably detect **dangerous conditions**, but not always prove exploitability automatically.

## High-confidence automated detection

These are good candidates for CI failure:

* Known vulnerable dependencies through `npm audit`, OSV-Scanner, Dependabot, or SCA.
* Outdated Vite/React packages with known advisories.
* `dangerouslySetInnerHTML` usage.
* Direct DOM HTML sinks.
* `eval`, `new Function`, string-based timers.
* `localStorage` / `sessionStorage` token usage.
* Missing production security headers.
* `server.cors: true`, `allowedHosts: true`, `server.host: true`.
* `VITE_*SECRET`, `VITE_*TOKEN`, `VITE_*PASSWORD`, or secrets found in `dist`.
* Source maps accidentally deployed publicly.
* `target="_blank"` without `rel`.
* Wildcard CORS with credentials.
* External scripts without SRI.

CodeQL supports JavaScript/TypeScript security query suites, including default and security-extended queries. Semgrep can also be used for JavaScript/TypeScript/React scanning, though its own docs caution that community edition analysis is more limited than cross-file/cross-function platform analysis. ([GitHub Docs][16])

OSV-Scanner can recursively scan source trees for vulnerable package files and supports dependency vulnerability analysis; `npm audit` checks configured npm dependencies and can produce remediation guidance. ([GitHub][17])

## Medium-confidence automated detection

These need human review of scanner output:

* XSS taint flows from route/query/API data into dangerous sinks.
* Prototype pollution.
* Path traversal.
* SSR injection.
* Unsafe redirect flows.
* Insecure CORS reflection.
* Unsafe file upload logic.
* Command injection paths.
* Dangerous package/plugin behavior.

## Low-confidence automated detection

These usually require manual or semi-manual testing:

* Broken access control.
* Tenant isolation flaws.
* Business logic abuse.
* Payment/workflow manipulation.
* Race conditions.
* OAuth/account-linking edge cases.
* Admin privilege escalation.
* Multi-user cache leaks.
* Insecure design.

# 4. Practical audit plan

## Phase 1: Inventory

Create an inventory of:

* All routes and pages.
* All API endpoints.
* All authentication flows.
* All roles and permissions.
* All third-party scripts.
* All Vite plugins.
* All environment variables.
* All public assets.
* All storage locations: cookies, localStorage, sessionStorage, IndexedDB, service worker cache.
* All external domains used by `connect-src`, images, scripts, iframes, fonts, and analytics.

## Phase 2: Dependency and framework audit

Run:

```bash
npm ls vite react react-dom @vitejs/plugin-react react-server-dom-webpack react-server-dom-parcel react-server-dom-turbopack
npm audit --audit-level=high
osv-scanner scan source -r .
```

Also enable Dependabot or an equivalent dependency update system. Dependabot alerts notify you about vulnerable dependencies and can open security update pull requests. ([GitHub Docs][18])

For Vite specifically, keep Vite and Vite plugins current. Vite’s own advisories list several recent file-serving, filesystem-deny, and WebSocket-related vulnerabilities across 2025 and 2026, so Vite version hygiene is important even for “just frontend” projects. ([GitHub][5])

## Phase 3: Static code review

Search for the following patterns:

```bash
grep -RInE "dangerouslySetInnerHTML|innerHTML|outerHTML|insertAdjacentHTML|document.write|DOMParser|createContextualFragment|srcDoc" src
grep -RInE "eval\\(|new Function|setTimeout\\(['\"]|setInterval\\(['\"]" src
grep -RInE "localStorage|sessionStorage|document.cookie|indexedDB" src
grep -RInE "postMessage|addEventListener\\(['\"]message" src
grep -RInE "window.open|location.href|location.assign|location.replace|redirect|returnUrl|callbackUrl|next=" src
grep -RInE "target=['\"]_blank" src
grep -RInE "server\\.host|allowedHosts|server\\.cors|fs\\.allow|fs\\.deny|publicDir|sourcemap|define|envPrefix" .
grep -RInE "VITE_.*(SECRET|TOKEN|PASSWORD|PRIVATE|KEY)" .env* src vite.config.* package.json
```

Add these linting rules:

* `react/no-danger`
* no `eval`
* no string-based timers
* no direct DOM HTML mutation except in reviewed wrappers
* no unsafe `target="_blank"`
* no raw external link component
* no storage of tokens in browser storage
* no direct use of `window.location` for redirects

The React ESLint rule `no-danger` specifically flags `dangerouslySetInnerHTML` and allows you to document exceptional sanitized cases. ([GitHub][19])

## Phase 4: Runtime validation audit

Because TypeScript types are erased, add runtime validation at trust boundaries:

* URL params.
* Query params.
* Form submissions.
* API responses.
* WebSocket messages.
* `postMessage` messages.
* `localStorage` and IndexedDB reads.
* Feature flags.
* CMS content.
* Payment or entitlement state.
* File metadata.

Use a schema library such as Zod, Valibot, ArkType, TypeBox, or JSON Schema. The exact library matters less than consistently validating untrusted input. OWASP recommends validating all untrusted data early, including syntactic and semantic validation, with allowlists, length/range checks, and schema validation where appropriate. ([OWASP Cheat Sheet Series][20])

## Phase 5: Build artifact audit

After `vite build`, inspect `dist`:

```bash
npm run build

grep -RInE "SECRET|TOKEN|PASSWORD|PRIVATE_KEY|BEGIN .*PRIVATE KEY|AWS_|AKIA|VITE_.*(SECRET|TOKEN|PASSWORD|KEY)" dist || true
find dist -name "*.map" -print
find dist -type f \( -name "*.html" -o -name "*.svg" -o -name "*.js" \) -print
```

Review:

* Are source maps publicly deployable?
* Are `.env` values embedded?
* Are test credentials included?
* Did anything from `publicDir` get copied as-is?
* Are third-party scripts loaded from the network?
* Is CSP compatible with the built app?

Vite’s `publicDir` assets are served at the root during development and copied to the build output as-is, so it should never contain secrets, private files, draft assets, or internal-only data. ([vitejs][21])

## Phase 6: Dynamic testing

Use a passive scanner in CI and deeper authenticated testing in staging.

* OWASP ZAP baseline scan for passive checks.
* Authenticated ZAP or Burp Suite testing for staging.
* Manual access-control tests.
* Manual OAuth/session tests.
* Multi-tenant object access tests.
* CSRF tests for cookie-authenticated state changes.
* CORS header tests.
* File upload abuse tests.
* Rate-limit and race-condition tests.

## Phase 7: Security header audit

Check production responses for:

```text
Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options: nosniff
Referrer-Policy
Permissions-Policy
Cross-Origin-Opener-Policy
Cross-Origin-Resource-Policy
Cross-Origin-Embedder-Policy, where needed
```

For CSP, start with Report-Only, collect violations, then enforce. OWASP recommends strict CSP using nonces or hashes instead of broad allowlists wherever possible. ([OWASP Cheat Sheet Series][13])

# 5. Best known practices for this stack

## React practices

1. **Do not use `dangerouslySetInnerHTML` directly.**
   Create one reviewed component, for example `SafeHtml`, that only accepts a branded sanitized value.

2. **Validate all URLs before rendering or navigating.**
   Reject `javascript:`, unsafe `data:`, malformed URLs, and untrusted redirect origins.

3. **Avoid direct DOM mutation.**
   Direct DOM APIs bypass React’s normal rendering protections.

4. **Treat markdown, SVG, and CMS content as hostile.**
   Sanitize and restrict allowed tags, attributes, protocols, and embeds.

5. **Do not store session tokens in `localStorage`.**
   Any XSS bug can read them.

6. **Use safe wrapper components.**
   Have centralized components for links, iframes, external images, rich text, and downloads.

Example pattern:

```ts
// safeHtml.ts
declare const brand: unique symbol;

export type SanitizedHtml = string & { readonly [brand]: "SanitizedHtml" };

export function sanitizeHtml(input: string): SanitizedHtml {
  // Use a vetted sanitizer here, configured with an allowlist.
  // Return only sanitized output.
  return input as SanitizedHtml;
}
```

```tsx
type SafeHtmlProps = {
  html: SanitizedHtml;
};

export function SafeHtml({ html }: SafeHtmlProps) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}
```

Then ban direct `dangerouslySetInnerHTML` everywhere except inside that component.

## TypeScript practices

Use strict settings:

```json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noFallthroughCasesInSwitch": true,
    "useUnknownInCatchVariables": true
  }
}
```

Security rules:

* Use `unknown`, not `any`, for untrusted data.
* Validate untrusted data before narrowing.
* Do not suppress errors with `@ts-ignore` unless reviewed.
* Model authorization-relevant values explicitly.
* Use branded types for sanitized HTML, validated URLs, tenant IDs, user IDs, and permission-checked object IDs.
* Never confuse TypeScript validation with runtime validation.

## Vite practices

Use a safe default Vite config:

```ts
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],

  server: {
    host: "127.0.0.1",
    allowedHosts: ["localhost", "127.0.0.1"],
    cors: false,
    fs: {
      strict: true
    }
  },

  preview: {
    host: "127.0.0.1"
  },

  build: {
    sourcemap: false
  }
});
```

Audit these carefully:

* `server.host`
* `server.allowedHosts`
* `server.cors`
* `server.fs.allow`
* `server.fs.deny`
* `preview.host`
* `build.sourcemap`
* `publicDir`
* `define`
* `envPrefix`
* Vite plugins
* custom middleware
* proxy config

Vite warns that `allowedHosts: true` can expose source via DNS rebinding-style scenarios, and that `server.cors: true` can allow arbitrary websites to request dev-server content. ([vitejs][9])

## Environment variable practices

* Never put secrets in `VITE_*`.
* Never put private API keys in frontend code.
* Do not use `define` to inject secrets.
* Keep `.env.local` out of git.
* Scan built bundles.
* Treat all frontend environment variables as public.
* Use a backend, edge function, or serverless function to call secret-bearing APIs.

## API/backend practices

Even in a frontend-heavy React app, most severe risks are usually backend/API risks.

* Enforce authorization on the server.
* Use parameterized queries.
* Validate request bodies.
* Validate response shape before trusting it in the client.
* Implement CSRF protection for cookie-authenticated state changes.
* Use explicit CORS origins.
* Rate-limit login, invite, password reset, and expensive endpoints.
* Add object-level authorization tests.
* Log security events.

## Cookie/session practices

Use cookies like:

```text
HttpOnly
Secure
SameSite=Lax or SameSite=Strict
Path=/
```

Use `SameSite=None` only when cross-site cookies are truly needed, and then require `Secure`.

## CSP practice

A strong starting policy for a typical app is:

```text
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{RANDOM_PER_RESPONSE}';
  object-src 'none';
  base-uri 'self';
  frame-ancestors 'none';
  img-src 'self' data: https:;
  style-src 'self' 'unsafe-inline';
  connect-src 'self' https://api.example.com;
  form-action 'self';
  upgrade-insecure-requests;
```

Then tighten `style-src`, `img-src`, `connect-src`, and `frame-src` to your real needs.

## Supply-chain practices

* Commit lockfiles.
* Use Dependabot/Renovate.
* Run `npm audit` and OSV-Scanner in CI.
* Review new packages before adding them.
* Avoid abandoned packages.
* Minimize Vite plugins.
* Treat Vite/Rollup/Babel plugins as trusted code execution.
* Pin or tightly control high-risk build tooling.
* Keep Vite, React, TypeScript, and plugin packages current.

## CI security gate

A practical baseline:

```bash
npm ci
npm run typecheck
npm run lint
npm audit --audit-level=high
osv-scanner scan source -r .
npm run build

grep -RInE "SECRET|TOKEN|PASSWORD|PRIVATE_KEY|BEGIN .*PRIVATE KEY|AWS_|AKIA|VITE_.*(SECRET|TOKEN|PASSWORD|KEY)" dist .env* src || true
find dist -name "*.map" -print
```

Add CodeQL and Semgrep in CI. Use ZAP or another DAST scanner against staging, especially for auth, headers, CORS, CSRF, and reflected/stored XSS.

# 6. Minimum audit acceptance criteria

I would not consider a Vite + TypeScript + React app audit-ready unless the following are true:

* No direct `dangerouslySetInnerHTML` outside a reviewed safe wrapper.
* No unsanitized markdown/rich-text rendering.
* No user-controlled `javascript:` or unsafe `data:` URLs.
* No tokens in `localStorage` or `sessionStorage`.
* No secrets in `VITE_*`, `define`, `publicDir`, `dist`, or source maps.
* Vite dev/preview servers are not publicly exposed.
* `server.allowedHosts` is not `true`.
* `server.cors` is not broadly permissive.
* `server.fs.strict` remains enabled.
* Vite, React, and plugins have no known critical/high vulnerabilities.
* All APIs enforce server-side authorization.
* All state-changing cookie-authenticated endpoints have CSRF protection.
* CORS is explicit and tested.
* Production has CSP, HSTS, frame protection, and sane cache headers.
* Dependency scanning runs in CI.
* Static analysis runs in CI.
* Authenticated DAST runs against staging.
* Access-control tests cover every role and tenant boundary.
* Security logs exist for auth, authorization failures, admin actions, and sensitive workflow changes.

The most common serious findings in this stack are usually: **unsanitized HTML rendering, leaked `VITE_` secrets, trusting TypeScript types without runtime validation, client-side-only authorization, unsafe token storage, permissive CORS, exposed Vite dev servers, vulnerable dependencies/plugins, and missing CSP/security headers.**

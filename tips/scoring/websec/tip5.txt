Below is a deliberately harsh checklist. I’m using **“inexcusable”** to mean: the artifact is in an active repo or mainline branch, has no current owner, no current build/runtime path, no documented external compatibility obligation, no dated removal plan, and no test/telemetry proving it is still needed.

Version control already preserves history, so “we might need it later” is not a good reason to keep junk on `main`; the common engineering advice is to delete unused/commented code and retrieve it from history when needed. GitHub also has a real archive mechanism for whole repositories: archiving makes a repo read-only and signals it is no longer maintained, and GitHub recommends closing issues/PRs and updating the README/description before archiving. ([Stack Overflow][1]) Google’s open-source repo management guidance similarly says to update the README and archive repos rather than leaving ambiguous unmaintained projects in place. ([Google Open Source][2])

Source note: I used GitHub issues/docs, Stack Overflow/Software Engineering, SonarSource, GitHub OSPO docs/blog, LinkedIn public posts, and public tool docs/repositories. Quora was blocked from retrieval, and X pages are inconsistently accessible/rendered without a logged-in session, so I did not treat them as authoritative citations. LinkedIn’s public content mostly echoed the standard “dead code / unused variables / methods are code smells” framing. ([LinkedIn][3])

## The exhaustive dead-code / sloppy-repo behavior list

### 1. Archive-folder hoarding

These are the classic repo graveyard behaviors.

1. Keeping `archive/` on `main` as a dumping ground for deleted features.
2. Keeping `old/`, `legacy/`, `deprecated/`, `obsolete/`, `unused/`, `dead/`, `retired/`, `graveyard/`, `junk/`, `trash/`, or `backup/` folders without a current owner.
3. Moving old code into an archive folder instead of deleting it and relying on Git history.
4. Keeping whole product snapshots like `app_old/`, `src_v1/`, `frontend-2021/`, `backend-before-migration/`.
5. Keeping “temporary” archive folders that survive more than one release.
6. Keeping `archive/` code that still appears in search results, confusing maintainers.
7. Keeping retired DAGs, jobs, or scripts because “it is nice to have a reference.”
8. Keeping old JARs, zips, generated blobs, or binaries inside archive folders.
9. Keeping an archive folder with code that no longer compiles.
10. Keeping an archive folder with stale dependencies and vulnerabilities.
11. Keeping an archive folder with examples of bad patterns that future developers might copy.
12. Keeping old code in `docs/archive/` but letting docs still link to it as if valid.
13. Keeping `experimental/` forever after the experiment has ended.
14. Keeping `poc/` or `prototype/` in production repos after the product was built.
15. Keeping abandoned “research” code in application repos.
16. Keeping a second archive repo that is not marked read-only, not documented, and not obviously dead.
17. Archiving code by copying it instead of tagging the deletion commit.
18. Moving dead code to a branch named `archive` and then periodically merging it back.
19. Keeping “old implementation for reference” beside the new implementation.
20. Keeping old folders because deletion PRs are politically hard.

Real examples exist: GitHub issues discuss deleting archive directories because the code and jars were unnecessary and created false-positive search noise. ([GitHub][4]) Public cleanup proposals also identify stale top-level directories, legacy components, deprecated patterns, and generated-code strategy as cleanup targets because they confuse contributors and increase attack surface. ([GitHub][5])

## The few legitimate exceptions

Do not blindly delete something just because it looks dead. Dead-code tools can miss reflection, plugin loading, generated references, external API consumers, and runtime-only paths. Runtime dead-code analysis tools exist because static analysis alone can be insufficient in large systems. ([GitHub][15])

Legitimate exceptions need evidence:

A public API with external consumers. A migration file required by the migration runner. A compliance-required historical artifact stored in the correct archive system, not active source. Generated code with a reproducible generator and current consumers. Test fixtures actively used by tests. Rollback code inside a dated, short-lived rollout window. Platform compatibility code tied to a published support matrix. Security examples intentionally kept in docs and clearly marked non-production.

Everything else should be deleted, archived properly at the repo level, or given an owner, ticket, expiry date, and automated check.
